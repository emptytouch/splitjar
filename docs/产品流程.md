# 产品流程(现状梳理)

> **2026-09-25 写。** 起因是用户实际走了一遍产品后指出:
> 「流程不符合用户操作。比如创作者创建内容以后,用户怎么知道在哪能查看;
> 还有创作者多了以后,创作的内容多了,用户在哪进行选取。」
>
> 这份文档做两件事:**① 把现在真实在跑的流程画出来**(以代码为准,不是以方案为准);
> **② 标出流程里的断点**,以及 W13 补哪一段、不补哪一段。
>
> ⚠️ **以代码为准**:方案 `docs/splitjar-product-spec.md` 写的是**设计意图**,
> 而这里写的是**今天实际会发生什么**。两者不一致的地方**明确标出来**
> (§五),因为那些不一致本身就是问题。

---

## 一、五个角色

| 角色 | 是谁 | 在哪操作 | 拿什么签 |
|---|---|---|---|
| **创作者** | 卖内容的人 | 浏览器(`/` `/create` `/dashboard`) | 浏览器钱包 |
| **买家(人)** | 买内容的人 | 浏览器(`/explore` `/p/:id`) | 浏览器钱包 |
| **Agent** | 机器买家 | **终端**(`scripts/agent-buy.mjs`) | shell 环境变量里的私钥 |
| **服务端** | Vercel Functions | —— | 自己的 Blob/KV 凭证 |
| **链** | `CreatorSplitter` @ Fuji | —— | —— |

⚠️ **创作者和买家是同一个人也可以** —— 代码里没有阻止。演示时是同一个人操作两个钱包。

## 二、⭐ 数据落在哪(理解全流程的钥匙)

**这一张表比任何流程图都重要** —— 因为流程里大部分"为什么这么绕"
的答案都在"这个东西存在哪、谁能读"里。

| 数据 | 存哪 | 谁写 | 谁读 | 备注 |
|---|---|---|---|---|
| `contentId` | **链上** | `createContent` | 全体 | 客户端生成,非自增 |
| `price` / `recipients` / `splits` | **链上** | `createContent` | 全体 | ⚠️ **创建后不可变** |
| `contentHash` | **链上** | `createContent` | 买家(下载后自校验) | `keccak256` |
| `active` | **链上** | `setContentActive` | catalog / 付费页 | 初始 `true` |
| `purchases(contentId, payer)` | **链上** | `pay()` | `/api/unlock`、付费页 | **门禁的唯一依据** |
| **内容文件** | **私有** blob `content/<contentId>` | 创作者浏览器**直传** | 只有 `/api/unlock` 签出的 **60 秒** URL | 不走我们服务器 |
| **预览图** | **公开** blob `preview/<contentId>` | 创作者浏览器**直传** | **任何人**(经 catalog) | ⚠️ **今天恒为空**,见 §五.3 |
| 标题(服务端) | **KV**(contentId → title) | `POST /api/content-meta` | `/api/catalog` | 链上**不存标题** |
| 标题(本机) | **localStorage** `splitjar.content.v1` | 创作者浏览器 | 控制台 / 看板 / 付费页 `?t=` | ⚠️ **按机器**,换台机器就空 |
| 已消耗的付款 | **KV** `payment:<txHash>` | `/api/content/:id` | 同左 | ⚠️ **无 TTL,永久** |
| 一次性 nonce | **KV** `nonce:<nonce>` | `/api/unlock-nonce` | `/api/unlock` | 300 秒 |

### 从这个表能直接读出来的三件事

1. **价格和分账比例上链后不可改。** 合约里**没有改价入口** ⇒
   想改价只能新建一件内容。(这也是 `api/catalog.ts` 能"零次 `eth_call`"的原因。)
2. **内容文件不经过我们服务器。** 浏览器直传 Vercel Blob ⇒
   我们没有它的副本,**服务端也就算不出预览图**(这是 §五.3 的根因之一)。
3. **门禁只认链。** `/api/unlock` 拿 `purchases()` 判断,不看任何本地状态 ⇒
   **换浏览器、换机器、清缓存都不影响"买没买过"**。

## 三、四条主链路

### A. 创作者发布

```
/ 控制台 →「创建付费内容」→ /create
  │
  ├─ ① 选文件            FilePick(任意类型,≤200 MiB)
  ├─ ② 算指纹            computeFileHash → keccak256   [本地]
  ├─ ③ 填标题 / 定价 / 分账比例(合计必须 = 100%)
  │
  └─ 点「发布」(状态机 publishMachine)
        hashing     ── 本地算哈希
        authorizing ── POST /api/upload 签 Upload 授权 → 拿受限 token
        uploading   ── 浏览器直传 → 私有 blob  content/<id>
        creating    ── 钱包签 createContent(contentId, price, contentHash, 收款方, 比例)
        mining      ── 等上链
                        │
                        └─ 成功 → POST /api/content-meta(标题 → KV)
                                → 分享区:付费页链接 + 二维码
```

**要点**

- **合约只认 `contentHash`**,不认文件本身 ⇒ 上链的是**指纹**,不是内容。
- **标题上链之后才写 KV**(它在 `pendingTitle` 里等到挖矿成功)。
- ⚠️ 合约**没有改价 / 改分账 / 转移归属的入口** —— 发出去就定死了。

### B. 买家(人)付费并下载

```
拿到 /p/:id 链接(二维码 / 分享)→ 打开付费页
  │
  ├─ ① 页面读链          getContent(id) → 价格 / 分账明细 / 创作者
  ├─ ② payGate 预检      8 种"提前能查明"的问题,不让你白签名:
  │                     未连钱包 / 链不对 / 内容不存在 / 已下架 /
  │                     已买过 / 归属读失败 / USDC 不够 / AVAX 不够
  │
  ├─ ③ 付款(payMachine)
  │     checking → signing(step1) → pending → signing(step2) → pending → confirming → success
  │                  └ approve USDC(仅当额度不够时才需要)
  │                                  └ pay(contentId)  ← 钱**当场按比例直达各方**
  │
  └─ ④ 下载(unlockMachine)
        nonce  ── GET /api/unlock-nonce   → 一次性 nonce
        sign   ── 钱包签 EIP-712 Unlock{contentId, buyer, nonce, deadline}
        unlock ── POST /api/unlock
                   服务端校验:形状 → 签名 → 时效 → nonce → **链上 purchases()**
                   通过 ⇒ 签一条 **60 秒**的私有 blob URL
        → 取回字节 → 自己起个带扩展名的名字(见 `lib/download.ts` 文件头)
```

**要点**

- **付钱和拿内容是两件事**:`pay()` 只管分账,**门禁在 `/api/unlock`**。
- **已买过的走另一条出路**:`payGate` 直接判 `already-purchased`,
  付费页**渲染下载按钮而不是付款按钮**(§14.2 要求「重复购买直接跳下载页,不报错」)。
- ⚠️ **`/api/unlock` 对"没买"返回 402 不是 spec 写的 401**(§五.2)。

### C. Agent 自主购买

```
终端:export AGENT_PRIVATE_KEY=0x… ; node --use-env-proxy scripts/agent-buy.mjs
  │
  0 自检     ── 私钥形状 / 地址白名单 / 余额
  1 发现     ── GET /api/catalog           ← **与人类共用同一个目录**
  2 读报价   ── GET /api/content/:id       → 402 + 报价(quoteId / expiresAt / sig)
  3 判额度   ── 从 402 里读金额(**不硬编码价格**)
  4 dry-run  ── `--dry-run` 停在这一步之前,一分钱不花
  5 付款     ── approve(如需要)+ pay(contentId)    [与人类**同一个合约同一个函数**]
  6 赎回     ── GET /api/content/:id + X-Payment 头(txHash 等五字段**全是字符串**)
                服务端:验报价 → 查链上付款 → 查是否已消耗 → 写 `payment:<txHash>`(永久)
  7 下载     ── 取回字节,keccak256 与链上 contentHash **比对**
  8 结论     ── 打印 txHash
```

**要点**

- **和人类走的是同一个合约、同一个目录、同一份分账** —— 这是产品主张的核心。
  区别只在**通道**:人类是 EIP-712 签名 + nonce;agent 是 `X-Payment` 头。
- ⚠️ **agent 那笔付款会被永久消耗**(`payment:<txHash>` 无 TTL),
  而**人类那条路不写这个键** ⇒ 人类付款的凭证可以复用,agent 的不行。

### D. 创作者收款与上下架

```
/dashboard
  ├─ 顶部汇总:件数 / 成交笔数 / 累计收入
  ├─ 每件一行:定价 · N 笔 · 已赚 |ActiveToggle 上下架| → 点进付费页
  │            └─ 成交明细:买家地址 + [Agent] 徽章(按地址白名单判定)
  └─ ClaimPending:待领余额 → withdraw()
```

**要点**

- **钱不进 escrow**:`pay()` 当场按比例打给各方。
  `pendingBalance` 只处理**打款失败**的收款方(`TransferFailed` 分支),由他们自己 `withdraw()`。
- **[Agent] 徽章是地址白名单判定的**,不是自动识别(`shared/agentAddresses.json`)。
- 数据来自 `useMyContents` —— 扫 `ContentRegistered` + `ContentActiveChanged`,
  **不逐件 `eth_call`**。

## 五、⚠️ 现状的断点(这份文档的重点)

### 5.1 买家**没有发现路径** ← 你最初提的问题

**事实**:`src/App.tsx` 只有 4 条路由 —— `/` `/create` `/p/:id` `/dashboard`。
买家**必须事先拿到 `/p/:id` 链接**才能买。

**而目录接口一直在跑**(`/api/catalog`),agent 用它,前端**一次没调**。

**根因**:spec §14.1 的路由表**只有 5 条,没有"发现"这条** ⇒
这件事**从来没被排进任何工作包**。

**W13 补**:新增 `/explore`,直接吃 `/api/catalog`。

### 5.2 未付款访问 `/api/unlock` 是 **402**,spec 写的是 401

**已记档的偏差**(`docs/W5-实施计划.md` §九.5)。
402 是**故意的**:401 留给验签/时效/nonce 三类认证失败。
**验收意图仍达成**(合法签名 + 链上没买 ⇒ 拒),只是状态码与 spec 字面不符。
**用户已拍板:保留 402,改文档。**

### 5.3 ⚠️ 预览图**恒为空** —— 这是流程里的一个真实空洞

**事实**:线上两件的 `previewUrl` 都是 `null`。

**根因不是"没实现"**(链路全通,见 `W13-实施计划.md` §1.4),是**没人调用过**:
`usePublishFlow.ts:192,212` 两处写死 `target: 'content'`,前端只有一个选文件入口。

**而它为什么重要**(用户原话):
> 「**预览图是肯定要有的,不然用户是看不到内容的,为啥么要购买?**」

**W13 补**:浏览器 canvas 派生(降采样 + 水印),**创作者不上传预览图**
—— 见 `W13-实施计划.md` §3.5 方案 1。

### 5.4 标题**按机器**存一份,换机器就空

`localStorage` 是创作者本机的。所以:
- 创作者自己在控制台/看板看得到标题 ✅
- **换一台机器、或换个浏览器 ⇒ 标题空** ⚠️
- 买家**永远**拿不到标题,除非 URL 上带了 `?t=`(`/p/:id?t=苹果图`)

**半修**:`POST /api/content-meta` 已经把标题写进 KV(W8 做的),
所以 `/api/catalog` **有标题** ⇒ 从 `/explore` 点进付费页的买家,
拿到的是**真正的标题**,不靠谁的机器。**但创作者自己的看板仍在读 localStorage。**

### 5.5 页签名与落点不符

顶栏「内容」→ `/create`(创建表单),而**内容管理在 `/dashboard`,那个页签叫「收款」**。

**W13 补**:改名(「创建」/「内容与收款」),不拆页。

### 5.6 开发痕迹漏进用户可见区

六处(逐条见 `W13-实施计划.md` §1.2),最刺眼的是控制台底部的
「**W1 完成定义 · 开发计划**」验收清单,以及两处印在界面上的 TODO
(「W2 实测替换」)。

**W13 补**:清掉。

### 5.7 一件**知道但没修**的事:链上没有"列出全部内容"的函数

合约没有列表函数(已从 ABI 核实),所以列表**只能扫事件**。
`DEPLOY_BLOCK → latest` 已经超过备份端点的 50,000 块上限 ⇒
**切窗扫描**(`shared/blockWindows.ts`)。

⚠️ 这**不是缺陷**,是设计后果 —— 但它意味着**内容越多、目录页越慢**。
演示量级(2 件)没问题,要如实知道这个边界。
