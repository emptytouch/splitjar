## 〇、先说一件事:上游 W4 有一条已经不成立了

`开发计划.md` W4 原文:

> - 拒收方 → `pendingBalance` → `withdraw()` 全链路验证
>
> **为什么 `TransferFailed` 要专门验证**:这是 §8.2 相对 v1 的核心改进,而且**演示时讲出来很有说服力**
> ("我们考虑了收款方拒收,不会让付款人被 DoS")。用测试合约造一个拒收方,当场演示资金安全落地。

**这条触发条件是错的,而且 spec 自己已经更正过了。**

`splitjar-product-spec.md` §8.2 的 9/21 更正(§5.1 表格里也同步了):

> 原文写的是"任一收款方是**拒收合约**时整笔支付会 revert"。**这个说法对 ERC-20 不成立。**
> ERC-20 的 `transfer` 只是改余额,**不调用收款方的任何代码** —— 没有 `receive`／`fallback`／回调钩子。
> 所以一个"什么调用都 revert"的合约**照样能收到 ERC-20**。

现有的 Foundry 测试已经把这条钉死了:`contracts/test/CreatorSplitter.t.sol:391`
`test_ERC20_NoHook_RejectingContractStillGetsPaid` —— 那个合约拒收 ETH 成功,收 ERC-20 照单全收,
`pendingBalance` 为零。

**真正能触发 escrow 的是代币侧失败**,与收款方是不是合约无关:

| 场景 | 我们能不能造 |
|---|---|
| Circle **拉黑**收款方 | ❌ 拉黑不了真 Fuji USDC |
| USDC 被**暂停** | ❌ 同上 |
| 收款方是拒收合约 | ⛔ **根本不触发**,ERC-20 没钩子 |

→ **后果:W4 做不出"当场演示拒收方走 escrow"这件事。** 真链上无法触发这条分支,
能触发的只有 `MockUSDC`(`contracts/test/mocks/MockUSDC.sol`,已带 `blacklisted` / `paused` /
`pauseAfterPull`,是 W2 专门为此造的)。

→ **处理方式:在 `开发计划.md` 的 W4 一节追加一条更正,不覆盖原文。**
理由与之前一致:计划与事实分开放,谁被推翻时能看出谁依赖它。这次是**上游被自家 spec 推翻**,
尤其要留痕 —— 否则 W4 会照着错的前提做完,演示时被评委问出来。

## 三、创建页分账编辑器(主要工作量)

### 3.1 要先主动推翻 W3 的一个决定

`src/pages/CreatePage.tsx:20-28` 的注释写得很明确:

> 输入「我的比例」,协作者拿剩下的 —— **合计恒等于 100%,不可能填错**。
> 这比"两个框都让填、再校验合计"更好 …… 在 2 方里把不变量做成结构性的,就不需要校验了 ——
> **让错误不可表示,胜过事后拦截。**

**W4 必须推翻它。** 但不是因为它错了,而是因为 §16.1 的验收项**要求存在一个能填错的界面**:

> - [ ] 创作者能创建一个 3 方分账商品,**`splits` 合计非 100% 时被前端拦下**

单输入框在结构上填不出非 100%,**这条验收就永远无法被证明**。验收项要的是"拦下"这个动作,
不是"不可能发生"这个状态。

→ 所以注释要**改写而不是删**:说清楚为什么 2 方时用结构性保证、为什么 3 方起必须放开成校验。
这是这一版里少数"为了可验收而牺牲一点设计纯度"的地方,值得写在代码里。

### 3.2 编辑器形态

```
┌─ 分账配置 ─────────────────────────────────┐
│  我            0xAbC…1234   [ 70 ] %   ← 只读地址,比例可改
│  协作者 1      0x___…____   [ 20 ] %   🗑
│  协作者 2      0x___…____   [ 10 ] %   🗑
│  ＋ 添加协作者                              │
│  ───────────────────────────────────────  │
│  合计 100% ✓        0.2 USDC → 0.14/0.04/0.02
└────────────────────────────────────────────┘
```

- 第 1 行「我」= 连接的钱包地址,**只读**、无删除按钮
- 第 2..N 行:地址输入 + 比例输入 + 删除
- 「＋ 添加协作者」,到 10 方时按钮禁用并说明原因
- 底部合计条:实时显示合计,**非 100% 时标红并显示差额**("还差 10%" / "超了 5%")
- **同时显示每一方实际能拿多少 USDC** —— 这是演示时最好看的一行,而且它逼着预览用真算法

**默认值 70 / 20 / 10**(三方):§5 功能清单第 1 条和 §3 的用户故事都是这个配置,
不是随便定的。

### 3.3 校验清单(全部实时,提交按钮据此禁用)

| 规则 | 出处 | 拦截还是警告 |
|---|---|---|
| 每项 > 0 | §8.3 | 拦截 |
| **合计 == 10000** | §8.3 | **拦截**(验收项) |
| 地址合法 | §8.1 | 拦截 |
| 地址非零 | 合约 `ZeroAddress` | 拦截 |
| 收款方数 ≤ 10 | 本文决策 2 | 拦截 |
| 地址重复 | 合约**不禁止** | **警告,不拦截** |
| 协作者 == 我自己 | 合约**不禁止** | **警告,不拦截** |

后两条为什么只警告:**合约本来就允许**。`recipients = [A, A, B]` 在合约层面就是"A 拿两份",
完全合法。前端拦死它等于凭空加一条合约没有的规则,而且抹掉了一个真实用法
(同一个人拿两个角色的份额)。给个提示让人知道自己在干什么就够了 ——
**前端不该比合约更严,除了验收项明确要求的那一条。**

### 3.4 ⚠️ 余数:UI 必须和合约逐字一致

合约的规则(`CreatorSplitter.sol:231-242`):前 N-1 方取 `floor(amount × split / 10000)`,
**最后一方取 `amount − 前面之和`**。

`src/lib/units.ts:116` 的 `previewShares` 已经逐字复刻了这条,直接用,**不要另写一个**。
但有两个坑:

1. **"最后一方"会随行序变化。** 用户删中间一行、或新加一行,余数归属就换人了,
   各方的实际金额会差 ≤1 个单位。因为 `previewShares` 是派生的,重算自动正确 ——
   但**界面上要能看出"最后一行是拿余数的那一方"**,否则用户对不上账会以为是 bug。
2. `src/lib/units.ts:111` 的注释写着"合约(`CreatorSplitter._split`)的算法是…" ——
   **合约里没有 `_split` 这个函数**,W2 是在 `pay()` 里内联循环的。
   这条注释会让下一个读代码的人去找一个不存在的东西,**顺手改掉**。

### 3.5 复用现有资产(不要另起一套)

- `parseBps` / `formatBps` / `parseUsdc` / `formatUsdc` / `previewShares` —— `src/lib/units.ts` 全有
- 付费页 `SplitTable`(`PayPage.tsx:50-83`)、看板(`DashboardPage.tsx:131-140`)、
  `usePayFlow` —— **都不用改**,已经是 N 方泛型
- 状态机 `payMachine.ts` —— **不用改**,它只关心"几笔交易",不关心几方

## 四、`contentHash`:W4 能做什么、不能做什么

事实:**事件已经带 `contentHash` 了,参数也已经在调**。W3 传的是
`0x000…0`(`src/pages/CreatePage.tsx:153`),理由是当时没有文件可哈希。

而 §8.1 冻结的定义是 **"内容文件的 `keccak256`"** —— W5 才有文件。所以 W4 面对的是:
**给一个还没有文件的东西填一个文件哈希。** 三个选项:

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A(推荐)** | **维持 `0x0`**,只补测试与 fork 验证证明通路;真哈希 W5 填 | 不发明语义。§8.1 说的就是文件哈希,而 W4 确实没有文件 | 演示时事件里是 0,讲不出"存证" |
| B | 传 `keccak256(contentId, title, price)` —— 对**登记信息**的承诺 | 演示时事件里有非零值,可当场看出"内容被锚定了" | 发明了一个 §8.1 没有的语义,而且 W5 要改。**中间改语义正是 §8.1 警告过的"前端与 Agent 分叉风险"** |
| C | W4 就把文件上传做了 | 一次到位 | **越界,那是 W5 的范围**,W4 只有一天 |

**推荐 A。** 理由不是保守,是 B 的代价被低估了:§8.1 冻结 `contentHash` 时明确的理由就是
"派生规则会让 W3(前端)与 W7(Agent)有分叉风险"。现在为了演示好看换一套派生规则,
就是把这个风险重新引进来 —— 而 W7 还有 2 天就到。

A 之下 W4 仍要做的事:**用一笔真实交易验证非零 `contentHash` 能原样穿过
`createContent` → 事件 → `getContent`**。测试已有(`test_CreateContent_StoresAllFields`),
补的是"真链上事件解码出来也一致"这一层。

> ⚠️ 这一条**建议你拍板**。如果你更看重"演示时事件里有非零值",选 B 也行 ——
> 但必须同时写进 §8.1 的追加更正里,让 W7 的 Agent 脚本知道哈希规则变了。

## 五、escrow 分支:重新表述,以及要不要做成可演示的

### 5.1 已有的coverade(比想象中完整)

`contracts/test/CreatorSplitter.t.sol` 里已经有 5 个,覆盖了 §8.2 那张表的每一行:

| 测试 | 行 | 对应 §8.2 的哪一行 |
|---|---|---|
| `test_ERC20_NoHook_RejectingContractStillGetsPaid` | 391 | 收款方是合约 → **不触发** |
| `test_Escrow_BlacklistedRecipient_FundsGoToPendingBalance` | 421 | Circle 拉黑 |
| `test_Escrow_BlacklistedRecipient_CannotWithdrawWhileBlacklisted` | 446 | 被拉黑期间 `withdraw()` 同样失败 |
| `test_Escrow_WithdrawSucceedsAfterUnblacklist` | 461 | 解封后取走 |
| `test_Escrow_TokenPausedDuringPush_WithdrawAfterResume` | 485 | USDC 暂停 |

**合约层这条分支已经验完了。** W4 不需要重写任何测试,也不需要动合约。

### 5.2 但"全链路验证"这句话还有一半没做

Foundry 测的是合约。**没有验过的是:一个真实钱包,能不能把 escrow 里的钱取出来。**
真链上做不到(拉黑不了真 USDC),所以只能在 fork 上做 —— 这正是 W3 搭的那套台架
(`%TEMP%\splitjar-tools\` 的 anvil + 注入式钱包)能干的第二件事:

1. anvil fork Fuji,部署 `MockUSDC` + `CreatorSplitter(MockUSDC)`
2. 造一件 2 方内容,把协作者地址**拉黑**
3. 买家付款 → 断言 `TransferFailed` 事件 + `pendingBalance[协作者] > 0`,而买家**没被阻断**
4. 用**协作者的钱包**(不是 cast 命令)点一次取款 → 此时 `withdraw()` 必须**失败**
5. 解除拉黑 → 再点一次 → 成功,余额到账

第 4 步是这个演示真正的价值:**它证明的是"被拉黑的钱在解封前动不了",
而不是"钱一定拿得到"。** §8.2 明确要求如实讲这一点("比被评委问出来强")。

上面这五步**照做**,它验的是合约行为。但它是**给评委看的脚本,不是给用户的路径** ——
这句话是 §5.3 的起点。

### 5.3 ⚠️ 通知这件事:escrow 目前**没有收件人**

用户问的是:"拒收的情况下要不要给收款方做通知?"

**先纠正一个词:触发条件不是"拒收"**(ERC-20 无钩子,§〇 已述),而是**代币侧拉黑/暂停**。
但这个问题本身是对的,而且比"要不要做 UI"更准 —— 换成任何触发条件,它都成立:

> **钱进了 `pendingBalance` 而不是收款方钱包,收款方怎么知道?**

现在的答案:**不知道。** 只有两个信号,都不够:

| 现有信号 | 问题 |
|---|---|
| `TransferFailed` 事件 | 在链上。**没有任何人在监听它** —— 没有索引服务、没有告警 |
| `DashboardPage.tsx:214-224` 的「待提取」卡片 | 它读 `pendingBalance[连接的钱包]`,**能显示**;但**没有按钮**,卡片上写着"W4 做提取界面" —— **代码自己已经许了这个承诺** |

**更深一层的问题:收款方在我们系统里没有身份。** 创作者只是在创建页敲了一个地址进去 ——
没有邮箱、没有账号、没有任何联系渠道。所以"通知"这件事在现有架构里**根本没有收件人**。
这不是没做,是**做不了**。能落地的只有两个位置:

| | 落点 | 能做什么 | 能拿到钱吗 |
|---|---|---|---|
| **(a)** | **收款方自己连钱包打开 `/dashboard`** | 看到"你有 X USDC 待领取" + **一键领取** | ✅ 这是唯一能真的把钱取回来的路径 |
| (b) | 创作者看板标注"某协作者有 X 待领取" | 创作者看得到,可以去线下联系对方 | ❌ 合约是 `pendingBalance[msg.sender]`,**创作者不能代领** |

**(b) 单独做是没有意义的** —— 它等于"告诉你有人欠你钱,但你不能取"。

### 5.4 决策 5 为什么改了:一个没人取得出来的 escrow 不算"安全落地"

§8.2 的卖点原话是"付款人不会被 DoS,钱安全落地"。但:

- Foundry 的 5 个测试证明 `withdraw()` **能用**;
- 真链上**没人走得到它** —— 用户界面里没有这个按钮,而收款方连"有钱在等我"都不知道。

**那么"安全落地"就只落在合约里,没落到用户手里。** 演示时被问一句"那协作者怎么把这笔钱拿出来?"
就答不上来 —— 而这恰恰是 §8.2 说"讲出来很有说服力"的那条。

**所以决策 5 改为:做 (a)。** 而且它比我原方案的"fork 脚本"更好,理由很直接:

> 我的原方案是**在 fork 上把这条路演一遍给评委看**;用户的问法指向的是
> **把这条路真的做出来,让评委自己点。** 后者的说服力不是高一点,是不同性质 ——
> 一个证明"我们的合约支持",一个证明"我们的产品能用"。

**成本比看起来小**,因为已有的东西比想象中多:

| 已经有了 | 在哪 |
|---|---|
| `pendingBalance` 的读取 | `DashboardPage.tsx:170-176`,已接好 |
| 「待提取」卡片与文案 | `DashboardPage.tsx:214-224` |
| `withdraw()` 的 ABI 与地址 | `src/lib/splitter.ts`(W2 导出) |
| 写合约 + 等收据 + 失败分类的模式 | `CreatePage.tsx` 的 reducer + `classifyError`,可直接套 |

**要新写的只有**:一个按钮 + "签名中/上链中/成功/失败"四态(可以比 `payMachine` 简得多,
它只有一笔交易、没有 approve 那一步)+ 成功后重读 `pendingBalance`。

> **顺序:编辑器 → 真链 3 方验证 → 领取界面。** 前两项是 W4 的非做不可项,
> 领取界面如果 9/24 没做完,**顺延到 W5,不要挤掉真链验证** —— 真链那一笔同时结清
> §12.2 的两个收尾项(§六),那个不能拖。

## 六、真链验证:顺带结清 §12.2 的两个收尾项

§16.1 要的三条,和 §12.2 欠的两个数,是**同一批交易**。这是 W4 最划算的一步。

### 6.1 要准备什么

#### ⚠️ 11.7.1 实测推翻了一个一直没验过的假设:`WithdrawFailed` **根本不会触发**

契约里 `withdraw()` 写的是:

```solidity
if (!usdc.transfer(msg.sender, amount)) revert WithdrawFailed();
```

照着这句,一直以为"收款方被拉黑"会走到 `WithdrawFailed`(即 `transfer` **返回 false**)。
直到在 fork 上真的拉黑一个人再调 `withdraw()`:

```
cast call <splitter> "withdraw()" --from <被拉黑的地址>
→ execution reverted: Blacklistable: account is blacklisted
  0x08c379a0…            ← Error(string),不是任何自定义 error
```

**原因:`FiatTokenV2.transfer` 带 `notBlacklisted` 修饰符**,拉黑的地址在 modifier
里的 `require` 就挂了,**根本走不到"返回 false"那一步**。所以:

| 走到的分支 | 一直以为 | 实测 |
|---|---|---|
| `contractErrorName()` | `'WithdrawFailed'` | `null`(没有自定义 error) |
| 分类器落到 | `token-blocked`(专门写的文案) | **`reverted`** |
| 用户看到 | "钱被代币合约拦住了" | **"交易被合约拒绝,可以重试一次"** |

最后那行是本该避免的形态:文案在**邀请用户去点一个永远不可能成功的重试**。
分类必须改看**代币侧那句 revert 字符串**,于是:

- `payErrors.ts` 新增 `revertText()`,把 `Error(string)` 的 `args[0]`、`reason`、
  以及裸 `Error.message` 都捞出来(注入式钱包那条路只会给 message);
- `claimMachine.ts` 按它分出三个**互不相同**的失败态 —— 拉黑 / 暂停 / 兜底,
  因为三者的"这一版对你意味着什么"不一样:拉黑是 Circle 的合规决定(时间不由我们定),
  暂停影响所有人且通常短暂。

匹配的是 Circle 自己的措辞(`Blacklistable: account is blacklisted` /
`Pausable: paused`),2018 年至今没变。这是**为我们唯一支持的那个代币**写的,
不是通用 revert 解析 —— 换币种要重看这一处。

#### ⚠️ 11.7.2 顺带发现:不预演就会让用户签一笔注定失败的交易

第一版直接 `writeContractAsync`。驱动脚本记下钱包收到的 JSON-RPC 方法,结果是:

```
钱包收到的方法: eth_chainId, eth_chainId, eth_sendTransaction
1 号账户 nonce: 25448 → 25448      ← 没上链,mock 钱包自己估 gas 时拒签了
```

那次是**幸运**:我们的 mock 钱包会自己估 gas,所以它拒绝签名、nonce 没变。
但 `eth_sendTransaction` 已经被请求了 —— **换成不预估 gas 的钱包,这笔交易就真发出去了**:
弹窗、签名、付 gas、然后 revert。

改成 viem 官方推荐的 `simulate → write` 顺序后:

```
钱包收到的方法: (无)              ← 一个弹窗都没有
1 号账户 nonce: 25448 → 25448
```

预演在 gas 估算阶段就 revert,一分钱不花、一个弹窗不弹。顺带还有个好处:
`simulateContract` 抛的是正经的 `ContractFunctionRevertedError`,
`revertText` 拿得到那句话(裸 message 那条路也能兜住)。

预演不碰钱包,所以它**不能借用 `signing` 的文案**("请在钱包里确认"在这个阶段是假话)
—— 状态机为此单独加了 `checking` 态,面板上明说"这一步不会唤起钱包,也不会花钱"。

#### 11.7.3 死路上也要留一个按钮,但它不能叫"重试"

`isDeadEnd()` 判定三种 `token-*` 以及 `nothing-to-withdraw`。一开始的做法是
**把这些状态下的按钮整个藏掉**(理由是"给了按钮就是骗人"),驱动脚本立刻暴露了问题:
解封之后再回到页面,**没有任何东西可以点**,不刷新就只能干看着。

`PayStatus` 里早就踩过同一个坑,注释写得很清楚:「只在那两处放按钮会让用户
领完币回来发现**没有任何按钮可以点**」。

所以按钮留下,但改口叫 **「重新检查」**,做的事也不同 —— 它只是 `reset()` + 重读
`pendingBalance`,**不重发那笔注定失败的交易**。解封之后按钮会自己变回「领取」,
这条路径在驱动脚本里断言了("不刷新页面也能自己走出去")。

#### 11.7.4 顺手修掉的一处:`shortReason` 会把 revert 显示成光秃秃一个 "Error"

`Error(string)` 这种 revert 的 `errorName` 就是字面的 **`"Error"`**。
原实现先看 `errorName`,于是界面上那行技术细节显示成 `Error` —— 等于没说。
把顺序改成"先看 `args[0]`/`reason`,再看 `errorName`"之后,显示的是
`Blacklistable: account is blacklisted`。这个函数是**付款流程也在用**的,
所以两边一起受益(改动后重跑了创建页的两个驱动,全绿)。

### 11.10 决策:**暂不加测试运行器**(2026-09-23)

`payMachine` / `claimMachine` 要不要加 vitest —— 结论是**暂不加**。记录理由,
因为"还没决定"和"决定了不加"是两件事,后者以后要有人推翻它得先看到当时是怎么算的。

#### 11.10.1 它能测到的只有一层

`payMachine.ts` / `claimMachine.ts` 确实是干净的纯模块(只 import `viem` 类型和
`payErrors`,没拖 React / wagmi),所以技术上"可测"成立。但把 W3–W4 踩过的 bug
逐个对一遍,能拦住的只有一个:

| W3–W4 的 bug | 属于哪一层 | 测试运行器拦得住吗 |
|---|---|---|
| `WithdrawFailed` 在真链上根本不触发(§11.7.1) | 链的事实 | ❌ 得 fork 实测 |
| 真 USDC 接口叫 `blacklist` 不叫 `setBlacklisted` | 链的事实 | ❌ |
| 注定失败的那笔走到了 `eth_sendTransaction`(§11.7.2) | 钱包集成 | ❌ 得靠 mock 钱包 |
| 死路上没有按钮,用户走不出去(§11.7.3) | **组件渲染** | ❌ 要 jsdom + testing-library 才够 |
| `shortReason` 显示出一个光秃秃的 `Error`(§11.7.4) | **纯函数** | ✅ |

**六个里一个。** 而且唯一够不着的那个(死路)恰恰是最接近"用户会真的卡住"的。
根因不复杂:真正抓到 bug 的是 fork 驱动脚本,它测的是**集成层** —— 正好是测试
运行器够不着的地方;而那个脚本持测试私钥、在仓库外,搬不进来。

#### 11.10.2 零依赖的路实测过,卡在一个具体的点上

Node 24 自带类型剥离,`node --test` 能直接跑 `.ts`,理论上一分钱不花。实测:
**卡在无扩展名导入**。`src/lib/claimMachine.ts` 写的是
`from './payErrors'`,Vite / TS 能解析,**Node 的 ESM 解析器不认**,直接
`ERR_MODULE_NOT_FOUND`。

要走这条路,代价是 tsconfig 加 `allowImportingTsExtensions`
(`noEmit: true` 已满足,技术上可行)+ **9 处**相对导入全部改成带 `.ts` 后缀。
为一个 devDependency 让全项目源码偏离惯用写法,不划算 —— 所以**如果**翻转,
也应该是加 vitest,不是走这条。

#### 11.10.3 三条不加的理由

1. **投入产出不划算** —— 一个新依赖(或 9 处源码改动),换"六个 bug 能拦一个"
2. **盖不住真正出问题的那一层**,而那一层的工装因为持私钥进不了仓库
3. **没人跑的测试比没有测试更糟** —— 它制造"有测试兜着"的错觉。W5–W11 还在前面,
   现在加就得一直养着

#### 11.10.4 ⚠️ 翻转条件

**`payErrors.ts` 下次被改动的时候。** 它被付款和领取两条流共用,而
「代币侧失败 ⇒ 不给重试按钮」这条是写进产品方案 §8.2 的**产品承诺** ——
目前这条承诺只活在文档和一个仓库外的脚本里,**仓库里没有任何东西看着它**。

到那时加,加 vitest,测试目标就一个:把 `classifyClaimError` 的分类表
(9 个 `ClaimFailReason` → 各自的 recovery)钉成断言。
