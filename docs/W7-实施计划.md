## 〇、先结掉那个必须做的决策点：x402 走 **B**

开发计划 §W7 要求「先花 1 小时评估『x402 付给合约、合约触发分账』（方案 A）」。
**已用接口层证据结掉，不必再花那 1 小时。** 结论是 **B**，理由如下。

### 0.1 A 在接口层就不成立（不是"试不出来"）

合约 `pay()`（`contracts/src/CreatorSplitter.sol:223`）：

```solidity
if (!usdc.transferFrom(msg.sender, address(this), amount)) revert PaymentFailed();
```

`msg.sender` **必须是买家本人**。而 x402 的 `exact` scheme 结算 = 一笔
**EIP-3009 `transferWithAuthorization`（或 Permit2）的普通 USDC 转账**，从 payer
直付 `payTo`，由 facilitator 广播并代付 gas。三条路：

| # | 做法 | 结果 |
|---|---|---|
| ① | `payTo` 填合约地址 | 钱进得来，但**合约没有任何 ERC-20 收款钩子**去调 `pay()` —— 不分账、不发 `PaymentSplit`、**无从得知 contentId** |
| ② | facilitator 自己调 `pay()` | `msg.sender` 变成 facilitator，它花自己的钱、被记成 payer —— 校验 ③ 直接崩，且 agent 的 USDC 根本没动 |
| ③ | 合约加一个函数去 `call` USDC 的 EIP-3009 | **技术上成立**（见 0.2），但要**改合约 + 重新部署** |

**旁证**：开发计划 §十 坑 3 早就独立写下「服务端代付 / relayer —— **不要做** ——
`payer` 必须是 `msg.sender`，代付直接破坏这个语义」。x402 的 facilitator 广播模型
正是代付，同一条理由。

### 0.2 ✅ 实测：Fuji USDC 确实支持 EIP-3009（所以 ③ 是真的能做）

不能靠"做不到"糊过去，所以去链上验了（`0x5425…Bc65`）：

| 探针 | 结果 |
|---|---|
| `version()` | `2` → FiatTokenV2 |
| `authorizationState(address,bytes32)` | 存在，返回 0 |
| `TRANSFER_WITH_AUTHORIZATION_TYPEHASH()` | 存在，返回 `0x158b0a9e…` |
| `transferWithAuthorization`（**正确编码 9 个参数**） | revert 在 `Blacklistable: account is blacklisted` —— **业务逻辑深处**，说明真的进了这个函数 |
| 对照：不存在的 selector `0xdeadbeef` | revert 出**空的、无原因**的 data |

⚠️ **踩过一次假失败**：第一次只拿**裸 selector** 去 call，`transferWithAuthorization` /
`receiveWithAuthorization` 都报 "reverted for an unknown reason"，差点记成"USDC 不支持"。
**裸 selector 没有参数 → ABI 解码阶段就 revert，证明不了任何事。** 判据要配对照，
两种 revert 的形状完全不同。

⚠️ 同时更正一处措辞：我先前说「合约要实现 ERC-3009 收款侧」，**不准**。
准确说法是**合约去 `call` USDC 的 EIP-3009**（标准的 gasless / meta-tx 支付）。
两者都要求改合约，结论不变，但别照抄旧措辞。

### 0.3 那为什么仍然不做 ③ —— 六条理由

1. **合约不可升级，加函数 = 换新地址。** 无代理，`usdc` 是 `immutable`（`CreatorSplitter.sol:63`）。
   换地址 ⇒ `0xDe9b…72f5` 上的一切作废：演示内容、那笔真实销售、亲手切的下架状态。
   而 README / 方案 / `SPLITTER_ADDRESS` / Vercel 生产环境变量全都引用旧地址。
2. **「真实链上支付」是 §17.3 红线。** 人类路径刚在一个已被证明的合约上稳定下来，
   重新部署 = 把被证明过的资金通道换成没被证明过的。
3. **要复制那段"处理钱"的循环。** 余数归最后一个收款人 + CEI 顺序 + `purchases` 标记
   必须逐字一致。复制 → 两份迟早漂移（正是刚修的那类 bug）；抽出来共用 → 在动
   **已经跑通的人类路径的资金代码**。
4. **签名路径自带一批新失败面**：`validAfter`/`validBefore` 窗口语义、nonce 单次性、
   EIP-712 域的 `name`/`version` 必须从链上读不能猜、ECDSA vs ERC-1271，
   而且 `notBlacklisted` 会**先于任何逻辑** revert。每条都要测。
5. **做成了也仍然不是 x402。** x402 的 `exact` scheme **只有单 payee 转账，没有
   contentId 概念**，更没有 N 方分账。拿到的是「B + 一份额外的合约风险」，
   合规收益 ≈ 0。**这条最要紧。**
6. **x402 的头号卖点"gasless"对我们无价值。** W8 的 agent 无论如何都要持 AVAX。

**时间账**：9/27 是 go/no-go 检查点，9/28 是材料日（W10，§17.3 红线、整天不写代码）。
合约改造 + 重新部署 + 重新验证 + 重造演示数据，吃掉的是 W11 那两天缓冲。
**回退代价还不对称** —— 新合约若 9/27 被发现有问题，回滚意味着白干，
且演示数据处在"一部分在新合约、一部分在旧合约"的不一致状态。

### 0.4 B 具体是什么

**保留 `pay()` 直呼，x402 只做报价/发现层的兼容外壳，并在 README 明说边界。**

⚠️ **而且连"外壳"也不能声称是 x402 实现** —— 查证过 x402 的线上格式：

| | 真 x402 | 我们 |
|---|---|---|
| 支付头（V2） | `PAYMENT-SIGNATURE`，装的是**未广播的签名授权** | `X-Payment`，装的是**已广播交易的哈希** |
| 谁广播 | facilitator（gasless） | agent 自己 |
| 402 体位置 | V2 放进 `PAYMENT-REQUIRED` **头** | 响应体 |
| `network` | CAIP-2，如 `eip155:43113` | 同 |
| 金额字段 | V2 是 `amount`，V1 是 `maxAmountRequired` | 我们采用 V1 命名 |

**信任模型是相反的**（未广播的授权 vs 已广播的哈希）。所以 README 只能写
「**复用 x402 的交互形态与报价字段命名**」，不能写「实现了 x402」。
方案 §9.4 现在写的「**对齐 x402 V2**」是一句过度承诺，**必须追加更正**（见 §九）。

### 0.5 「那 agent 路径的意义在哪里」

**方案自己早就回答过，而且答案里没有 x402。** §1.2 论证 agent 价值用的是四条：

1. 给 Agent 私钥是零成本的（人类要装 App、抄助记词、买币）
2. **Agent 过不了 KYC** → 开不了银行账户、申请不了 Stripe 商户号，**它没有别的付款方式**
3. **Agent 用不了微信/支付宝** → 没有任何面向自主 Agent 的接口，**不是贵，是做不到**
4. **微支付在信用卡体系里数学上不成立** —— 2.9% + **固定 $0.30**，一笔 $0.01 的调用
   固定费是金额的 30 倍

四条要的是：**一个有私钥的机器，在卡组织固定费吃死小微支付的价位上，无人干预地
完成扣款 → 分账 → 交付。B 把这四条全交付了。**

而 §1.2 结尾的「诚实边界」写得比什么都清楚：

> 本产品的差异**不是**做支付基础设施，而是**把 Agent 买家接到真实的创作者内容上，
> 并复用已有的多方分账**。

**所以 B 不是产品主张的妥协 —— B 就是产品主张。** A 反而是往"做支付基础设施"偏，
而方案明确声明那不是差异点。

**具体价值**：① 它是唯一能证明 §1.2 那个论证是"真的"的东西（人类路径证明不了 ——
人类有微信支付，费率论证对人类不成立）；② 它展示竞品给不出的那一屏 ——
今天做 agent 支付的东西**全是单收款人**，我们是**同一笔付款里当场 N 方分账**；
③ 它踩主办方题眼（赛事原文第二问）；④ **§16.1 那七项验收里 x402 一个字都没有**。

{

> ### ⚠️ 2026-09-23 更正：`quote` 里**没有** `issuedAt`
>
> 这一格原来写着 `"issuedAt": 1790…`，**已删掉**。理由见下面的 §1.3 ——
> 一个服务端在验签时拿不回来的字段，进签名就等于**让所有签名静默失效**。
> 实现里 `Quote` 只有 `quoteId` / `contentId` / `expiresAt` 三个字段
> （`shared/agentPay.ts`）。

两种形状并存是刻意的：402 是 x402 握手，其余是我们自己的错误。

⚠️ `extra.assetTransferMethod` **故意不写 `eip3009`** —— 我们不走那条路（§0.3），
写成 `eip3009` 就是撒谎。

### 1.2 `X-Payment` 装什么

```
X-Payment: {"txHash":"0x…","payer":"0x…","quoteId":"0x…","expiresAt":1790…,"sig":"0x…"}
```

⚠️ **这是本方案新定的，方案原文没规定这个组合**（原文只写了 `{txHash, payer}` 加
"把 `quoteId` 一并回显"）。为什么 `expiresAt` 也要回显：坑 2 的设计是
**签名即存储**（不落 KV），而验签需要 `expiresAt` 原文。

### 1.3 ⚠️ 2026-09-23 更正：签名载荷只能有三项，本节的原始公式是错的

本节原来写的是：

```
sig = HMAC(secret, contentId + quoteId + issuedAt + expiresAt + amount)   ❌ 写错了
```

**这个公式会让每一份报价都验不过。** 判据只有一句：

> **验签那一刻，服务端能不能把这个字段重新算出来？**

```
服务端签报价时：知道 amount / issuedAt
agent 回显的 X-Payment：{ txHash, payer, quoteId, expiresAt, sig }
服务端不存报价（坑 2 定的"签名即存储"）
  ⇒ 验签时 amount 与 issuedAt 无从得知 ⇒ 拼不出签名原文 ⇒ 必然不匹配
```

所以载荷只能、也只该是 **`contentId + quoteId + expiresAt`** ——
**方案 §9.4 第 609 行原本写的就是这三项，那一版是自洽的**，
是本节的 §1.1/§1.2 把它改坏了。实现见 `server/quote.ts` 的 `quoteSigningPayload`。

**少了这两项丢了什么（诚实说）：**

| 删掉的字段 | 原意 | 现在的替代 |
|---|---|---|
| `amount` | 让报价为金额背书 | 赎回时核对**链上那笔分账的总额 == 当前链上价格**。更硬：那是既有事实，不是我们自己的声明 |
| `issuedAt` | 给校验 ⑤ 一个**下界** | 下界整个去掉，见 §5.2(b) —— 它**修掉了一个不可恢复的故障** |

> **要往载荷里加字段，先回答"验签那一刻它从哪来"。** 加不回来就是全量静默失效。

这是**刻意的取舍**，不是静默 bug（控制台留了 `console.warn`）。

⚠️ **演示内容 `0x6410fb…ef986f` 仍然得回填** —— 它建于这个端点存在之前，

## 三、`/api/content/:id` 的判定顺序

**先看有没有 `X-Payment`，再决定走哪条路。** 顺序写错会造出一个真 bug。

```
① 解析 contentId（shared/storage.ts 的 isContentId —— 小写严格）
   不合法 → 400 bad_request

② 有没有 X-Payment?
   ├─ 有 → 走 §五 的五条校验 → 200 { url, expiresInSeconds }
   └─ 无 ↓

③ 读链上 getContentInfo(contentId)
   查不到 → 404 content_not_found

④ ⚠️ content.active === false → 403 content_inactive（**不是 402**）

⑤ 内容在售、没凭证 → 402 + 签名报价
```

### ⚠️ 为什么第 ④ 步是 403 而不是 402（方案没写，本方案定）

**给一个已下架的内容发 402 报价，等于邀请 agent 去花 gas 换一次必然的 revert**
—— 合约 `pay()` 的第三行就是 `if (!c.active) revert ContentInactive(contentId)`
（`CreatorSplitter.sol:214`）。人类付费页早就把这条路堵上了（`payGate.ts` 的
`content-inactive`），服务端不能反而敞开。

**第 ② 步必须先于第 ③④ 步**：已下架内容的**已购买家**仍然要能取到内容

## 五、五条校验（§9.4 原文，逐条落地）

```
① txHash 已上链且确认数达标
② 交易中 PaymentSplit 事件的 contentId 与请求一致
③ 事件中的 payer == 请求声明的 payer
④ 该 txHash 未被消费过
⑤ txHash 在报价有效期内
```

### 5.1 ⚠️ ①②③ 一次 `getTransactionReceipt` 就够了（方案没写，本方案定）

**「确认数达标」文档从未规定数字。** 本方案**不引入确认数阈值**，判据是：

```
getTransactionReceipt(txHash)
  ├─ status !== 'success'                      → ① 失败 payment_not_found
  └─ 在 logs 里找 PaymentSplit(contentId == 请求的 contentId)
       找不到                                   → ② 失败 payment_mismatch
       找到 && log.args.payer !== 声明的 payer   → ③ 失败 payment_mismatch
       找到且 payer 相符                         → ①②③ 全过
```

**为什么比"N 个确认"更好**：第 ② 条要求 `PaymentSplit` 日志本身在场，所以收据必然
已存在且成功 —— 三个检查塌缩成一次确定性的读，没有"几个确认才算够"这个拍出来的数字。
代价是没有 reorg 保护，**在 Fuji 演示场景下可以接受**（要真上主网，这里必须改）。

### 5.2 ⑤ 的两处必须写死，否则会假拒真单

**（a）`expiresAt` 定 900 秒（15 分钟），不是 60 秒。**
方案 §9.4 的原话是「**"已用"要记在成功响应之后**，否则 Agent 付了钱但响应失败时无法重试」。
有效期同理：定太短，agent 付完钱、重试时报价已过期 → 付了钱拿不到内容。
agent 要 2 笔交易（`approve` + `pay`），再加 RPC 抖动，15 分钟是能给演示留出救场余地的值。

**（b）下界**不存在**——只有上界。** ⚠️ **2026-09-23 更正（本段原来写的是"下界必须留时钟偏移余量"）**

第 ⑤ 条的实现是 `blockTime ≤ expiresAt`，**没有下界，也没有 `CLOCK_SKEW`**。
`server/quote.ts` 的 `isWithinQuote` 就这一行。

本段原来主张"下界要留 120 秒偏移余量，否则会误杀正常付款"——
**那个诊断是对的，但药方开错了。** 出块者的时钟确实可能让 `blockTime` 早于
`issuedAt`，而**留余量只是把误杀窗口从 2 分钟压到 0**，代价是签名里多一个
`issuedAt`（见 §1.3：它根本进不了签名）。正解是**不要下界**。

**下界的唯一作用是防"拿一笔很久以前的交易配一份今天的报价"——
而那个攻击不存在：**

```
走到第 ⑤ 条 ⇒ ②③ 已要求"必须是你本人、为这件内容发出的 PaymentSplit"
             ⇒ ④ 已保证同一个 txHash 只能兑一次
             ⇒ "能通过 ②③ 的交易"本身就意味着"你付过钱了"
             ⇒ 再早也只是"你付得早、现在才来取" —— 正当，不该拒
```

**而加了下界会造出一个真实且不可恢复的故障（我一度写进《风险》表里）：**

> agent 拿到报价 → 付款 → 赎回时报价已过期 ⇒ 那笔交易**永远**配不上新报价
> （新报价的 `issuedAt` 在未来），而合约 `pay()` 第 215 行的 `AlreadyPurchased`
> **不允许重付** ⇒ **钱换了内容，内容拿不到。**

**现在没有这个问题：报价过期 ≠ 作废。** 再取一份新的就是，旧交易的
`blockTime` 照样满足 `≤ 新 expiresAt`。

⚠️ **顺带更正**：本段原来说那条真实历史交易（`0x9c271f43…4fb153`）
**不能用来测 happy path** —— 那是下界造成的，现在**可以用了**。

⚠️ **`0x6410fb…ef986f` 目前是在架的**（2026-09-23 实测核实）：
链上它的 `ContentActiveChanged` 有两条（`false` → `true`），**终态是 `true`**；
`GET /api/content/0x6410fb…` 实回 **402**（不是 403），catalog 也把它列出来了。
所以 **403 `content_inactive` 这条反例在本机测不到** —— 得先把它下架
（那要发一笔交易），或者另建一件再下架。**别以为已经验过了。**

### 5.3 ④ 防重放：既要原子，又要"记在成功之后"

方案 §W7 明确要求「**同一个 `txHash` 并发请求 → 只有一次成功（KV 写入要原子）**」，
同时 §9.4 又要求「**"已用"要记在成功响应之后**」。**朴素实现做不到两条同时成立**：

- 先记后用 → 一个付了钱但响应失败的 agent 被永久锁死（违反第二条）
- 先用后记 → 并发两次请求都会通过检查（违反第一条）

**解法：短租约 + 成功才落定。**

```
校验开始前：reservePayment(txHash)  → SET NX + TTL 60s
   └─ 失败 → 409 payment_replayed          ← 原子,并发只有一个进得来
校验通过、响应已备好：commitPayment(txHash) → 去掉 TTL / 换长 TTL  ← "记在成功之后"
中途任何一步失败：releasePayment(txHash)   → DEL                     ← 允许重试
```

⚠️ **租约窗口内**（60 秒）如果 Function 崩在 reserve 与 commit 之间，agent 会拿到 409
而不是重试成功。**这是刻意的取舍**：窗口只有 60 秒且会自己过期，
而反过来（先记后用）的失败模式是永久锁死。**60 秒是有界的，永久不是。**

KV key 用**全局** `payment:${txHash}`，不加 contentId —— 一笔交易只可能付一件内容，
跨 contentId 的重放由 ② 拦下。

#### 6.3.2 生产上撞出来的一个真缺口：回执超时是 **6 分钟**

**症状**：在付费页付一笔款，钱包报
`custom eth_sendRawTransaction: nonce too low: next nonce 6, tx nonce 5`
（钱包重播了一笔已上链的交易），而**页面就停在「上链中…」不动**。

**根因**（不是"没有超时"，是"超时太长"）：

```
viem 的 waitForTransactionReceipt 默认 timeout = 180 秒
    ×
全局 react-query 默认 retry: 1（src/main.tsx:11）
    =
360 秒 —— 用户要盯着一个没有任何出口的转圈整整 6 分钟
```

而 `payMachine` 的 `receipt-timeout` 与 `publishMachine` 的 `chain-timeout`
**两条文案本来就是为这个场景写的**（都明说"交易可能已提交、别重复支付、
先去区块浏览器确认"，且**都不给一键重试**）—— 只是它们要 6 分钟才来。

**改法**（2026-09-24）：

| 文件 | 改动 |
|---|---|
| `src/lib/payErrors.ts` | 新增并导出 `RECEIPT_TIMEOUT_MS = 90_000` |
| `src/hooks/usePayFlow.ts` | `useWaitForTransactionReceipt({ hash, timeout, query: { retry: false } })` |
| `src/hooks/usePublishFlow.ts` | 同上 |

**为什么是 90 秒**：Fuji 出块约 2 秒，90 秒 ≈ 45 个区块，远超任何正常确认，
又短到不至于让人以为页面死了。**调小它是安全的** —— 超时**不等于失败**，
误报的代价是"让用户多看一眼浏览器链接"，不是"让用户重付一次"。

**为什么必须同时给 `query: { retry: false }`**：全局的 `retry: 1` 会把超时
**翻一倍**。关掉它**不是在削弱重试** —— `waitForTransactionReceipt` 自己就用
`retryCount: 6` + 指数退避扛 RPC 抖动，外面这层是重复的，它在这里唯一实际起
的作用就是把超时翻倍。

**验过的部分**：`npm run typecheck` ✅；并用真 RPC 实测了机制本身 ——
`waitForTransactionReceipt({ hash: <不存在的>, timeout: 3000, retryCount: 0 })`
**3.0 秒准点抛**，`.name === 'WaitForTransactionReceiptTimeoutError'`、
`instanceof` 命中、`BaseError.walk` 命中 —— 正是 `payErrors.find` 与
`chainReasonOnReceipt` 判的那两样。
⚠️ **没验的**：React 接线那一层（需要在浏览器里制造一笔永不打包的交易），
即"改成 90 秒之后页面确实在 90 秒时给出那条文案"。**如实记。**

#### 6.4.1 关键设计：它**不持私钥、不花钱**

### ⚠️ 2026-09-23 遗留：`deliverBranch` 的**判定顺序**待定（未改，等拍板）

`deliverBranch` 目前是**先查依赖（503）、再验请求形状（400 / 403）**：

```
kvConfigured? blobToken?  →  503   ← 依赖检查在前
parseXPayment             →  400   ← 形状校验在后
verifyQuote               →  403
```

**现象**（§6.1 实测到的那行 503）：本机 KV 不通时，一个**完全合法的**凭证请求
与一个**坏 JSON** 的请求，返回的是**同一个** 503 —— 请求本身错在哪，一句都不说。

**两种读法都有道理**：

- **保持现状**：服务整体不可用时，返回 503 是实话；回 400 会让人以为"改一下头就好了"，
  改完还是撞 503。
- **先验形状**：形状校验是**纯函数**，不依赖任何外部服务、**不可能失败**。
  先做它永远不会有更差的答案，而且能立刻告诉调用方"你的头就是错的"。

**本包没有擅自改** —— 这是顺序的取舍，不是 bug。定下来就是几行搬家。
⚠️ 真改的话注意 `verifyQuote` 那一步：它虽然不碰 KV，但**碰密钥**
（`quoteConfigured()`），所以"形状 → 验签 → 依赖 → 占位"是另一个可能的排法。

### 2.（方案 §9.4）「对齐 x402 V2」→ **过度承诺，需追加更正**

原文（`splitjar-product-spec.md` §9.4）写的是本方案**对齐 x402 V2**。
§0.4 已查证：**信任模型是相反的**（x402 的 `X-PAYMENT` / `PAYMENT-SIGNATURE` 装的是
**未广播的签名授权**，我们装的是**已广播交易的哈希**），且 x402 的 `exact` scheme
**只有单 payee 转账，没有 contentId 概念**，容纳不了我们的 N 方分账。

**应追加的更正**（追加而非改写 —— 见 §12 的规矩）：

> **⚠️ 2026-09-23 更正：本节的「对齐 x402 V2」是过度承诺。**
> 实测与查证后改为 **B**：保留 `pay()` 直呼，**复用 x402 的交互形态与报价字段命名**，
> 但**不实现 x402 的结算**（不做 facilitator、不做 ERC-3009）。
> 原因是信任模型相反 + x402 容不下 N 方分账。**README 里按这个口径写。**
> 详细推演见 `W7-实施计划.md` §〇。
