## 1. 一句话定位

给数字内容创作者一个链上收款工具，**同时服务两类买家**：人类扫码付、AI Agent 自助付。钱按比直达多方钱包，内容 hash 上链存证。

- **对人类买家**：不提醒你在用 Web3 —— 扫码 → 稳定币付 → 解锁
- **对 AI Agent**：**让 Agent 能自己掏钱买内容** —— 请求 → `402` 报价 → 自动付款 → 取内容，全程无人干预

> **v2.1 关键调整**：v2.0 的买家只有人类，而人类买家需要自备钱包——这是产品最大的死结（见 1.1）。v2.1 把 AI Agent 加为**第一类买家**，因为这个死结在 Agent 身上**根本不成立**：给 Agent 一个私钥是它的默认运行形态，不是额外门槛。详见 1.2。

- **产品名**：`收钱罐`（中文名沿用，好记、直白、无商标风险）
- **✅ 英文名**：`SplitJar`（**9/21 定稿**）。中英**各说一件事、不互译**：中文说"收钱"（谁在收），英文说"分账"（钱怎么分）。
- **❌ 旧英文名 `CoinJar` 必须弃用**。CoinJar Pty Ltd（澳洲持牌交易所，2013 年成立）已在美国注册 Class 9/36/42、欧盟注册 Class 36 商标，涵盖"加密钱包 / 加密资产电子转账 / 支付卡 / NFT 钱包"——**与本产品类目完全重叠**。考虑到第 18 节还打算把它当获客名片，越早换成本越低。**全部候选的查证过程见第 22 节。**
- **合约名**：`CreatorSplitter`（纯描述性命名，不沾商标）

### 1.1 钱包出现在漏斗的错误一侧（核心诊断）

v1 把创作者和买家的零门槛混为一谈，这是定位里最大的逻辑漏洞：

- **对创作者成立** —— 她只填标题、价格、上传文件，全程不见助记词
- **对人类买家不成立** —— 买家扫码后**必须已有钱包和 USDC**，这是真实的、未解决的门槛

**人类买家是漏斗的最后一环，却是门槛最高的一环。** 转化率就是产品的天花板：多一次装钱包、多一次买币，转化率塌方。

**"付款方必须持有密钥"这个约束删不掉** —— 链上转账就是要签名，这是物理事实，不是设计选择。唯一能做文章的地方是：**选一个本来就持有密钥的付款方**。人类消费者不是，**AI Agent 是**。

因此 v2.1 的结构不是"绕开这个约束"，而是**把约束挪到它不成立的地方**：

| 买家类型 | 有密钥吗 | 摩擦 | 定位 |
|---|---|---|---|
| 人类消费者 | ❌ 需要装钱包、买币 | 高 | **保留，但不是主战场** |
| **AI Agent** | ✅ **密钥是其默认运行形态** | **≈0** | **新增，主战场** |

人类买家的零门槛靠 v2 的 AA 钱包 / 法币入金解决，明确划入 Out of scope。**v2.1 不再把人类买家的低转化当作待解决的缺陷，而是把它标注为"v2 待解决"，同时用 Agent 买家把产品的价值链真正闭合。**

### 1.2 为什么 Agent 买家是解法，不是噱头

给 Agent 一个私钥是**零成本**的（那就是它的运行形态）；给人类一个私钥要装 App、抄助记词、买币。同样一件事，成本差了两个数量级。

更重要的是，**付款方是 Agent 时，链从"可选"变成"刚需"**：

- **Agent 过不了 KYC** → 开不了银行账户、申请不了 Stripe 商户号。它没有别的付款方式
- **Agent 用不了微信支付 / 支付宝** → 它们**没有任何面向自主 Agent 的接口**，且要求人类身份。**不是贵，是做不到**
- **微支付在信用卡体系里数学上不成立** → 支付网关费率为 **2.9% + 固定 $0.30**（已核实）。一笔 $0.01 的调用，固定费是金额的 30 倍。**在这个约束下，链不是"更便宜"，是"唯一可能"**
- **结算必须程序化** → 没有人来点「确认付款」，扣款、分账、交付必须全自动

这三条让 [第 12 节](#12-链选型论证为什么必须是-avalanche-v1-缺失) 的链选型论证从"事后编的说辞"升级为**场景的物理要求**。这是 v2.0 最弱的一环，v2.1 把它变成了最强的一环。

> ⚠️ **范围限定（务必记住）**：上述三条**只对 Agent 买家成立**。对人类买家，真实替代是微信支付 0.6%，费率论证不适用——详见 §12.1.4。
>
> ✅ **费率数字已于 9/21 核实**，过程与来源见 [费率核实附录](费率核实附录.md)。核实也**推翻了原版的一处普适性论断**，§12.1 已相应重写。

**同时，这也是主办方自己抛出的问题。** 赛事原文开篇第二问即："如果 Agent 能证明'它是谁'，很多事情是不是会简单很多？"赛道 04 明确欢迎"面向 AI 应用的链上协作工具"。踩中主办方的题眼，比自选一个题目更稳。

> **诚实边界**：Agent 支付是 2026 年的热门方向，很可能有对手在做。本产品的差异**不是**做支付基础设施，而是**把 Agent 买家接到真实的创作者内容上，并复用已有的多方分账**。这个组合比纯基础设施更具体、更可演示。

## 2. 目标用户

### 2.1 供给侧：个体创作者

小红书 / 闲鱼上卖 **设计模板、素材包、笔刷字体、设计交付物、预设文件** 的个体创作者 —— 无企业资质、嫌平台抽成高、嫌链上钱包门槛高。

- **首打场景**：单次付费数字内容（产品本身内容无关，任意数字文件均可）
- **核心痛点**：微信支付要企业资质 + 手续费；链上钱包太劝退；想要**无抽成、直接到账、低门槛**；协作者结算麻烦

### 2.2 需求侧 A：人类买家

- **特征**：创作者现有粉丝。**大部分没有钱包、没有 USDC**
- **定位**：**保留路径，但不是主战场**。转化率受限于钱包门槛（见 1.1）
- **它的价值**：证明"人类也能零门槛扫码付"，同时是 Agent 路径的对照

### 2.3 需求侧 B：AI Agent / Agent 运营方（v2.1 新增，主战场）

- **特征**：需要消费数字内容的 AI Agent、工作流、MCP 客户端；以及搭建它们的开发者
- **为什么是主战场**：**密钥是其默认运行形态，无接入摩擦**；且它**没有别的付款方式**（过不了 KYC、微支付在卡体系里不成立）
- **它买什么**：可被机器消费的数据 / 素材 / 参考内容 —— 例如设计 Agent 购买素材包、写作 Agent 购买参考资料

> **已更换 headline 场景（人类侧）**：v1 用"AI 写真"。AI 生成人像在小红书上涉及 AI 内容标注与肖像权，合规风险高、审核易挂。改用**设计模板 / 素材包**——同样是个体创作者刚需，且权属清晰。

## 3. 核心用户故事

博主"阿 May"想卖一套 PPT 模板（9.9）。她打开收钱罐 → 连钱包 → 填标题 / 价格 / 传文件 → 生成专属付费页 + 二维码。买家扫码，稳定币一键付，钱按预设比例直达阿 May 与两位合作设计师的钱包；付完页面立即解锁下载。三个人各自可以提走自己那部分。

> **修正 v1 的两处矛盾**：v1 第 3 节说"设 10% 自动分给**一位**协作者"（两方），第 5 节却说"默认 **70/20/10**"（三方），前后不一致。v2 统一为**三方场景**，且**70/20/10 的三个主体明确是「创作者 / 协作者 A / 协作者 B」——不包含任何平台抽成**（见第 18 节商业模式）。

### 3.1 Agent 买家故事（v2.1 新增）

一个设计类 AI Agent 接到任务："给这份海报找一套配色参考"。它：

1. `GET /api/catalog`，看到阿 May 的配色素材包，价格 0.5 USDC
2. `GET /api/content/:id` → 收到 **`402 Payment Required`** + 报价
3. **用自己的密钥**调用 `CreatorSplitter.pay(contentId)` —— 一笔交易，钱按 70/20/10 自动分给阿 May 与两位合作设计师
4. 带 `txHash` 重试 → `200` + 素材数据
5. 全程**没有任何人介入**

**阿 May 那边看到的是**：看板里多了一条订单，来源标注"Agent"，分账明细照旧。她不需要知道 Agent 是什么，也不需要做任何额外配置。

> 这个故事的意义：**同一套合约、同一个商品、同一份分账，同时服务人和 Agent。** 新增的只是 HTTP 层的一条分支，不是一套新系统。

## 5. MVP 功能清单

1. **`/create` 创作者后台**：连钱包（Core；体验模式用预置演示创作者钱包）→ 创建付费内容（标题 / 价格 / **内容文件** / 预览图）→ 设**多方分账比例**（可编辑输入，默认 70/20/10，可"＋添加协作者"，实时校验合计 100%）
2. **上链**：内容 hash 存证 + 部署 `CreatorSplitter` 分账配置
3. **内容入库**：内容文件上传至**私有存储**，预览图公开（见第 9 节）
4. **生成 `/p/:id` 付费页 + 二维码**（移动优先 H5）
5. **买家端**：扫码 → 连钱包（或体验模式一键付）→ USDC 一键付 → 支付成功解锁动画
6. **合约**：`msg.sender` 校验 → 按比分账（失败转可提取余额）→ 记录购买
7. **`/unlock` 门禁（人类路径）**：校验链上购买记录 → 签发短时效签名 URL → 下载
8. **`/api/catalog` 商品目录（Agent 路径）**：列出可售内容与价格 —— **v2.1 新增**
9. **`/api/content/:id` 机器取用（Agent 路径）**：无凭证返回 `402` + 报价；带有效 `txHash` 返回内容 —— **v2.1 新增，见 9.4**
10. **Agent 演示客户端**：一个能自主发现 → 付款 → 取内容的最小 Agent 脚本 —— **v2.1 新增，演示核心**
11. **`/dashboard` 收入看板**：总收入 / 订单 + 每笔分账明细 + **买家类型标注（人 / Agent）** + 链上查证入口

### 5.1 v1 遗漏的必要分支（现补入）

| 分支 | v2 决策 |
|---|---|
| **重复购买** | 合约内 `purchases[contentId][buyer]` 拦截，已购买者再次支付直接 revert（`AlreadyPurchased`）。前端提前判断并显示"你已购买，去下载" |
| **退款** | **不支持**，明确写入 Out of scope 并给理由（钱已按比分给多方，链上不可逆）。**但必须在付费页购买前显著提示"数字内容，一经售出概不退款"**，否则是误导用户 |
| **下架** | 创作者可 `setContentActive(contentId, false)`，下架后新支付 revert，**已购用户仍可下载** |
| **改价** | **不支持**。价格创建后不可变，避免"以旧价支付"的歧义。要改价就新建一个商品 |
| **收款方转账失败** | 见第 8 节，转可提取余额，不阻断支付。**触发条件是代币侧拉黑/暂停，不是"收款方拒收"** —— ERC-20 无钩子，收款方合约无法拒收（9/21 实测更正，见 §8.2） |

## 6. 演示与提交策略

> **v1 本节的整个前提是错的**：v1 写"评委为'提交即审核、自行体验'，**无现场 demo 机会**"。实际上赛事有 **10/9 公布前 10 入围 → 10/11 项目 demo** 环节。前提修正后，本节重写为**两个阶段**。

### 阶段一：初筛（9/30 提交 → 10/1–10/8 评审 → 10/9 公布前 10）

这一关**只有 10 个名额**，评委大概率在大量作品中快速浏览。目标是**30 秒内让人看懂并愿意点开**。

### 6.1 ⚠️ 删除"回放兜底"设计（v1 第 6 节的诚信红线）

v1 原文：**"异常时回退预录真实交易，界面永不出错"**。

**这条必须删掉。** 如果回退发生时界面仍显示"支付成功"并给出一个链上浏览器链接，而链接指向的是几分钟前预录的交易——评委点进去会看到时间戳对不上、payer 不是自己。这不是鲁棒性设计，是**伪造证据**，在实际有 demo 日的赛制下穿帮代价更高。

替换原则：**目标不是"永不出错"，是"永不骗人"**。

- 交易失败 → **如实显示失败** + 一键重试 + 展示真实报错
- 若确实要提供回放，界面必须**显式标注"演示回放数据，非本次实时交易"**，且**不给 explorer 链接**，或给原始交易链接并注明其真实时间戳
- 工程力气改投到**让真实上链别失败**：演示账户预充值、RPC 多路冗余 + 自动故障转移、gas 预估留足 buffer、支付前预检余额与网络

## 8. 合约设计（`CreatorSplitter`）

> **v1 接口有三处缺陷，已修正**：① `createContent` 的 `creator` 参数可被任意伪造；② `pay` 的 `payer` 参数可被任意伪造；③ "标准 PaymentSplitter 模式"（pull）与"自动分账"（push）语义自相矛盾。

### 8.1 接口

```solidity
// creator 恒为 msg.sender，不接受外部传入
function createContent(
    bytes32 contentId,
    uint256 price,          // USDC，6 位小数
    bytes32 contentHash,
    address[] calldata recipients,
    uint16[]  calldata splits // 基点，合计必须 == 10000
) external;

function pay(bytes32 contentId) external;          // payer 恒为 msg.sender
function setContentActive(bytes32 contentId, bool active) external;  // 仅 creator
function withdraw() external;                       // 领取"待提取余额"
```

> **🔒 已定稿（2026-09-21）。** 接口冻结,9/22 起不再变更。
> 若确需修改,**必须同步更新**：§8.4 事件、§9.4 的 402 报价字段（`payTo` / `method`）、前端付款状态机、Agent 演示脚本。

**调用约定（与接口一同冻结）**

| 项 | 约定 | 说明 |
|---|---|---|
| **`contentId` 生成** | **前端生成随机 `bytes32`** | 不派生自标题/时间。合约已用"重复创建 revert"保证唯一性,32 字节随机碰撞可忽略;派生规则会让 W3（前端）与 W7（Agent）有分叉风险 |
| **`price` 单位** | USDC,6 位小数 | `0.1 USDC` → `100000` |
| **`splits` 单位** | 基点,合计 == 10000 | `[7000, 2000, 1000]` → 70/20/10 |
| **`contentHash`** | 内容文件的 `keccak256` | 仅存证,不参与门禁（见 §9.3） |
| **⚠️ 分账余数归属** | **最后一个收款人拿余数** | 见下 |

**⚠️ 余数必须现在就定死（容易漏）**

`amount × split / 10000` 是整数除法,会截断。例：`amount = 101`,`splits = [7000, 2000, 1000]` → 70 / 20 / 10,**余下 1 个单位卡在合约里**。

**约定：前 N-1 个收款人取 `floor(amount × split / 10000)`,最后一个取 `amount − 前面之和`。** 这样**支付金额恒等于分账之和**,合约不留灰尘。

> 不冻结这条的后果：W2 实现一种、W3 的对账按另一种,测试报出"总数对不上"却查不出原因;或灰尘悄悄累积在合约里,`withdraw()` 也取不走。

### 8.2 分账语义：push + 失败转可提取余额

**v1 的矛盾**：写"标准 PaymentSplitter 模式"（即 OpenZeppelin `PaymentSplitter`，**pull**，各方自行 claim），却又在功能清单里写"**自动分账**"（**push**，即时到账）。二者不可兼得。

**v2 决策：push 为主 + 失败转可提取余额（escrow fallback）。**

- 理由："钱按比**直达**多方钱包"是核心卖点，pull 模式要求协作者主动 claim，对非技术创作者是新增门槛
- 但纯 push 有实际风险：**某一方的转账失败时，整笔支付会 revert**，付款人被 DoS
- 解法：对每个收款方 `try transfer`；失败则记入 `pendingBalance[recipient]`，由其 `withdraw()` 领取
- 代价约 30 行代码，大幅降低 DoS 面，同时保住"自动到账"的体验

> **⚠️ 2026-09-21 W2 实测更正：触发条件说错了，结论不变。**
>
> 原文写的是"任一收款方是**拒收合约**时整笔支付会 revert"。**这个说法对 ERC-20 不成立。**
> ERC-20 的 `transfer` 只是改余额，**不调用收款方的任何代码** —— 没有 `receive`／`fallback`／
> 回调钩子。所以一个"什么调用都 revert"的合约**照样能收到 ERC-20**。
> `contracts/test/CreatorSplitter.t.sol` 的 `test_ERC20_NoHook_RejectingContractStillGetsPaid`
> 用一个这样的合约把这条钉死了：它拒收 ETH 成功，收 ERC-20 却照单全收，`pendingBalance` 为零。
>
> **真实的触发条件是代币侧失败**，与收款方是否是合约无关：
>
> | 场景 | escrow 是否救得回来 |
> |---|---|
> | Circle **拉黑**收款方 | 付款不阻断，份额记账；但**被拉黑期间 `withdraw()` 同样失败**，解封后才能取 |
> | USDC 被**暂停**（如拉款成功后、推送时暂停） | 付款不阻断，份额全记账；恢复后各自取走 |
> | 收款方是普通钱包/合约 | 不触发。ERC-20 没有钩子，收不收得到与它无关 |
>
> **结论不变，理由要换**：escrow 依然值得留（它挡的是"代币侧出问题"这一类），
> 但**不能宣传成"任何情况下钱都拿得到"** —— 被拉黑的钱在解封前是动不了的。
> 演示时如实讲这一点，比被评委问出来强。
>
> 顺带：§8.4 的 `TransferFailed` 事件名是准确的（它描述的是**转账**失败，不是收款方拒收），
> 不需要改。但**它的注释**（"转入待提取余额时触发"）应当按上表理解。

> **⚠️ 追加（2026-09-22，W4 期间）—— 上表那一行已用真 USDC 走通，且发现一个实现陷阱。**
>
> 上表"Circle 拉黑收款方"那一行，**9/22 在 fork 上用真 Fuji USDC 完整验证过了**（收款方
> 自己连钱包点「领取」，不是靠 Forge 断言）。做法是 impersonate 真链 `owner()` 把
> `blacklister` 换成测试账户——**只在 fork 里**。详见 `W4-实施计划.md` §11.7。
>
> ⚠️ **但有一个陷阱，照着 §8.2 的伪代码实现会踩进去**：这里写的是
> "失败则记入 `pendingBalance[recipient]`"，很容易顺势以为拉黑时
> `usdc.transfer()` 会**返回 false**（即走到合约的 `WithdrawFailed`）。
>
> **实测不会。** 真 `FiatTokenV2.transfer` 带 `notBlacklisted` **修饰符**，
> 拉黑的地址在 modifier 里的 `require` 就挂了 —— revert 成一句
> `Error(string): "Blacklistable: account is blacklisted"`，**根本走不到返回值那一步**。
> 后果：只按 `WithdrawFailed` 判断"被代币拦住了"，真链上会落到"交易被合约拒绝，可以重试"
> —— 一句邀请用户无限重试的假话。**分类必须看代币侧那句 revert 字符串。**
>
> （合约层不用改：`withdraw()` 先清零再转账，revert 会把清零一起回滚，
> 所以任何形态的失败都是"钱还在、重试安全"。）

### 8.2.1 escrow 有个产品层面的洞：**通知没有收件人**

这条不属于合约，但属于"这个卖点能不能成立"，所以记在方案里而不是实施记录里。

`pendingBalance[recipient]` 是记账，**但没有任何机制告诉那位收款方"你有一笔钱被暂存了"**：
合约不知道他的邮箱，我们也没有他的联系方式。他能知道这件事的**唯一入口**是
自己连上钱包、打开看板、看见那个数字。

由此有两个必须一起成立的产品决定：

1. **收款方的看板入口不能省。** 它不是"锦上添花的看板"，**它是 escrow 这条路径唯一的出口**。
   W4 最初把领取界面列为"W4 做不完就顺延 W5"，9/22 改成了必做——理由是
   **一个没人取得出来的 escrow 不算"安全落地"**（`W4-实施计划.md` §5.4）。
2. **§8.2 最后那句"如实讲"要落到界面上**，不能只落在文档里。被拉黑的人点「领取」时，
   界面必须说清"是代币合约拦的、钱没丢、解封后能取"，**并且不能给一个重试按钮**
   （重试解决不了拉黑，给了就是骗人）——改给一个「重新检查」，解封后它自己会变回「领取」。

### 8.3 校验与边界

- `recipients.length == splits.length`，且非空
- `splits` 合计 **必须 == 10000**（基点），每项 > 0
- 拒绝零地址
- `contentId` 唯一，重复创建 revert
- `price > 0`
- 已购买者再次 `pay` → revert `AlreadyPurchased`
- `setContentActive` 仅 `creator` 可调

### 8.4 事件（带 indexed 字段，供链下过滤）

```solidity
event ContentRegistered(bytes32 indexed contentId, address indexed creator, bytes32 contentHash, uint256 price);
event PaymentSplit(bytes32 indexed contentId, address indexed payer, address[] recipients, uint256[] amounts);
event ContentUnlocked(bytes32 indexed contentId, address indexed payer);
event TransferFailed(address indexed recipient, uint256 amount);  // 新增：转入待提取余额时触发
```

> 删掉了 v1 的 `ContentUnlocked` 里无意义的 `txHash`（事件本身即在交易内，`tx.hash` 可查），并补上 `TransferFailed`，否则链下无法还原"这笔钱到底到账没有"。

## 9. 内容存储与付费门禁（v1 完全缺失）

> **这是产品的核心价值，不是实现细节。** v1 要求上传"内容文件/预览图"，但技术栈里没有任何存储方案；而如果内容放在公开 URL 上，**付费墙根本不成立——拿到 URL 的人直接白嫖**。

### 9.1 存储

- **内容文件** → **Vercel Blob，私有权限**（不公开可读）
- **预览图** → Vercel Blob，公开可读（付费页要展示）
- 上传经 Vercel Function 中转，避免把写入凭证暴露给前端

> 备选：IPFS（Pinata / Storacha）。优点是"去中心化"叙事更足、与链上存证呼应更好；缺点是 pin 成本与可用性要自己兜。**MVP 选 Vercel Blob，时间富余再换 IPFS 作为加分项。**

> **⚠️ 追加（2026-09-23，W5 期间）—— 上面三条里，前两条要改，第三条要换实现。意图全部保留。**
> 详细推演与实验记录见 `W5-实施计划.md` §〇 / §三 / §四；这里只放结论。
>
> | 原文 | 问题 | 改成 |
> |---|---|---|
> | 内容文件 → 私有 Blob | ✅ 成立 | 不变 |
> | 预览图 → 公开可读 | ❌ **`access` 是 store 级配置，一个 store 装不下两种** | **开两个 store**:私有 store 放 `content/`，公开 store 放 `preview/` |
> | 上传经 Function 中转 | ❌ **Function 请求体上限 4.5 MB**（Serverless/Node；Edge 只有 1 MB），超了在 handler 执行**之前**就 `413`。而"内容文件"没有尺寸约束 | **客户端直传**：服务端用 `handleUpload` 签一个受限 token（限定 pathname、限定 `put`、限定有效期），浏览器拿它直传 Blob |
>
> **第三条为什么不算推翻原意**：原话的理由是「**避免把写入凭证暴露给前端**」——
> 客户端直传同样满足这一条，**写入凭证始终不进前端**。变的只是实现，不是意图。
>
> **第一条为什么要开两个 store**：这条**实测**过，不是推理。私有 store 里
> `put --access public` 会被平台明确拒绝（`Cannot use public access on a private store.`），
> 同一 store 里 `--access private` 的对照组则成功。**`access` 是 store 级、且平台强制。**
> 附带的好处是：**"付费内容被误标成 public"在平台层面做不到** —— 付费墙的这一环
> 不再依赖代码正确性。（推演过程中我为此错过两次，教训见 W5 计划 §0.2.1。）
>
> **落地后的环境变量**（`server/env.ts` 的白名单要登记这两个）：
> `BLOB_READ_WRITE_TOKEN`（私有 store）、`PUBLIC__READ_WRITE_TOKEN`（公开 store）。
> ⚠️ `VITE_` 前缀会被内联进前端产物，**这两个都不能带 `VITE_`**。

### 9.2 门禁（真正有效的付费墙）

```
买家点"下载"
  → 前端让钱包签名一条消息（证明地址所有权）
  → POST /api/unlock { contentId, address, signature }
  → 后端验签 → 读链上 purchases[contentId][address]
  → 未购买 401；已购买 → 返回短时效（如 60s）签名 URL
  → 浏览器凭 URL 拉取文件
```

**要点**：

- 校验发生在**服务端 + 链上**，不是前端隐藏元素——前端隐藏元素可被绕过，**不算付费墙**
- 签名 URL **必须短时效**，否则链接一旦外流等于永久泄露
- 需防重放：签名消息内含 `contentId` + 一次性 nonce + 时间戳

**✅ 签名方案定稿（9/21）：用 EIP-712（`eth_signTypedData_v4`），不用 `personal_sign`**

| | EIP-712 ✅ | `personal_sign` ❌ |
|---|---|---|
| 钱包里显示什么 | **结构化字段**（解锁哪个内容 / nonce / 截止时间） | 一串看不懂的 hex |
| 抗钓鱼 | 用户看得懂自己在签什么 | **不透明签名是钓鱼的标准形态** |
| 跨链/跨应用重放 | **domain 绑定 `chainId` + `verifyingContract`，天然防** | 无任何绑定 |
| 与 Agent 路径一致性 | **同一套心智模型**——ERC-3009 的 `TransferWithAuthorization` 本身就是 EIP-712 | 要额外维护第二套签名逻辑 |

**最后一条是决定性的**：Agent 路径**已经必须**用 EIP-712（ERC-3009 规定），再选 `personal_sign` 等于为演示产品维护两套签名方案，零收益。

```
domain: { name: "SplitJar", version: "1", chainId: 43113, verifyingContract: <CreatorSplitter> }
types:  Unlock {
          contentId: bytes32,
          buyer:     address,
          nonce:     uint256,
          deadline:  uint256   // unix 秒
        }
```

- `verifyingContract` 填**已部署的 `CreatorSplitter` 地址**（不是 `0x0`）——把证明绑死在本应用上
- `buyer` 虽可从签名恢复，但**仍显式入签**：钱包会显示它，且服务端可断言"恢复出的地址 == `buyer` 字段"，多一层校验

**nonce 策略**：服务端签发 + deadline 双保险。`GET /api/unlock-nonce` → 服务端生成随机 nonce 写 KV（TTL 5 分钟）→ 前端签进 EIP-712 → 服务端**验签、校验 nonce、读链通过之后才删除 nonce**。

- **为什么不用纯时间戳**：纯 `deadline` 在窗口内**可被重放**，不是真正的"一次性"
- **⚠️ 顺序与 §9.4 的 402 反重放是同一条教训**——先删再干活，后面失败用户就得重新签名
- **诚实的边界**：这个 nonce 防的是**证明被转移**，不是保护资金——解锁证明**不授权任何链上操作**

> `@vercel/kv` **已于 2024-12 废弃**，KV 已并入 **Upstash Redis（Vercel Marketplace 集成）**，

### 9.3 内容 hash 存证的准确定位

v1 没说清存证到底解决什么。诚实的说法是：

- ✅ 能证明：**某文件在某个时间点已存在，且此后未被修改**
- ❌ 不能证明：买到的就是那个文件、创作者拥有版权、文件不被私下替换

所以存证的价值是**确权与防篡改的时间戳证据**，不是版权登记，也不是门禁。README 里要这样写，别过度承诺。

### 9.4 机器支付路径（Agent 买家）— v2.1 新增

人类买家走 9.2 的"钱包签名"。**Agent 买家走 HTTP 402 报价 → 自主付款 → 带凭证重试**，全程无人干预。

**第 0 步：发现（Agent 怎么知道有什么可买）**

```
GET /api/catalog
← 200 [{ contentId, title, price, currency, previewUrl }, ...]
```

没有这一步，Agent 就得硬编码 URL，演示会显得很假。

**第 1 步：Agent 请求内容，未付款**

```
GET /api/content/:contentId
← 402 Payment Required
{
  "error": "payment_required",
  "contentId": "0x...",
  "price": "0.5",              // USDC
  "decimals": 6,
  "chainId": 43113,            // Fuji
  "payTo": "0x...",            // CreatorSplitter 合约地址
  "method": "pay(bytes32)",
  "quoteExpiresAt": 1758...    // 报价有效期
}
```

**第 2 步：Agent 用自己的密钥调用 `CreatorSplitter.pay(contentId)`，拿到 `txHash`。**

**第 3 步：带付款凭证重试**

```
GET /api/content/:contentId
X-Payment: {"txHash":"0x...","payer":"0x..."}
← 200 + 内容（机器可读格式）
```

**服务端校验（五条缺一不可）**

1. `txHash` 已上链且确认数达标
2. 交易中 `PaymentSplit` 事件的 `contentId` 与请求一致
3. 事件中的 `payer` == 请求声明的 `payer` —— **防冒用他人交易**
4. **该 `txHash` 未被消费过** —— 防重放，用 Vercel KV 记已用 hash
5. `txHash` 在报价有效期内 —— **报价必须由服务端签名，否则本条无法验证**（见下）

> **⚠️ 第 4 条必须有。** 没有它，一个 Agent 付一次钱可以无限次取内容，付费墙形同虚设。而且要注意**"已用"要记在成功响应之后**，否则 Agent 付了钱但响应失败时无法重试。

**⚠️ 第 5 条的隐含前提：报价要签名（9/21 补充）**

如果 `quoteExpiresAt` 是 Agent 从 402 响应里自己读、自己回传的裸字段，那它**可以随便改** —— 第 5 条校验等于空的。

**修法：服务端签发报价时用服务端密钥做 HMAC 签名。**

```
402 响应体：{ contentId, price, ..., quoteId, expiresAt, sig }
  sig = HMAC(secret, contentId + quoteId + expiresAt)
Agent 付款后把 quoteId 一并回显在 X-Payment 里
服务端验签 sig → 才采信 expiresAt
```

- 约 15 行，零新增基建
- **这样就不需要用 KV 记录报价签发时间**（签名即凭证，少一个依赖）
- 第 4 条（KV 防重放）与第 5 条（签名保真）**不重复**：KV 保护"交易一次性"，签名保护"报价真实性"

**必须想清楚的边界**

- **并发请求同一内容**：多笔付款各自有效、各自放行；但**同一个 `txHash` 只能消费一次**
- **付了钱但请求失败**：允许重试，只要 `txHash` 仍在有效期内
- **✅ 合约无需改动**：人类与 Agent 共用同一个 `pay()`，**v2.1 的改动全部落在 HTTP 层**——这是这个方案便宜的关键原因
- **内容格式要分岔**：Agent 要的是原始数据，不是下载页。`/api/content/:id` 返回机器可读格式（JSON / 原始文件流），与人类看的 `/p/:id` 页面分离

**标准化：对齐 x402 V2（⚠️ 已核实，优先级从"可选"上调）**

> **✅ 9/21 核实结果：x402 V2 原生支持 Avalanche，且明确支持 Fuji 测试网（chain ID 43113）。**

这意味着上面的"x402 风格"不必自己发明——**直接用标准即可**：

- **x402**：Coinbase 2025-05 发起，**2026-04 转入 Linux Foundation**（x402 Foundation），40+ 成员含 Visa / Mastercard / Amex / Stripe / Google / AWS / Cloudflare / Circle / Shopify / Solana Foundation
- **x402 V2**（2025-12-11）原生多链：**Base / Solana / Avalanche**，采用 CAIP-2 标识（如 `eip155:43113`）
- 已有开源 SDK（`x402-rs` / `x402-go` / `x402-rails` 等），Avalanche 是一等公民

**为什么值得升级做实**：

1. **省工** —— 有现成实现与客户端生态，比自己手搓 402 分支省事
2. **可信度** —— "x402 兼容" 远强于 "我们自创了一个 402 流程"
3. **🎯 补上 Avalanche 原生性的短板** —— 这正是 [§12.3](#123-反向论证为什么不是随便哪条-evm-链) 承认的弱点。**直接采用一个把 Avalanche 列为一等公民的行业标准，是目前能拿到的最强 Avalanche 契合证据**

**⚠️ 但有一个必须解决的设计问题（不要跳过）**：

x402 在 EVM 上用 **ERC-3009 `TransferWithAuthorization`**，即"签名授权一笔 USDC 转账给某个 payee"。而我们的 `CreatorSplitter.pay()` 是**函数调用 + 合约内分账**，payee 本质是 N 个收款人。

**"x402 付给单一 payee" 与 "合约分账给 N 个 payee" 需要调和。** 可选路径：

- **A（推荐先试）**：x402 付款给合约地址，合约侧触发分账。需解决"这笔钱对应哪个 `contentId`"的映射
- **B**：保留现有 `pay(contentId)` 直呼，x402 只作为**报价与发现层**的兼容外壳
- **C**：完整 ERC-3009 改造 —— **不建议，9 天里风险过高**

> **决策建议**：**9/26 做 Agent 路径时，先花 1 小时评估路径 A 的可行性**。若不能在半天内打通，就回落到 B 并**在 README 明说"报价遵循 x402，结算为主合约直呼"**——诚实说明边界，比含糊地声称"兼容 x402" 好得多。

**MCP 封装（可选，加分项）**
把 `/api/catalog` + 402 流程包成一个 MCP Server，任何支持 MCP 的 Agent 都能直接调用。约半天工作量，但叙事价值高——它把产品从"一个网站"变成"**Agent 可以调用的能力**"，正踩赛道 04 原文的"开发者 SDK、中间件和基础组件"。

## 10. 链下事件索引机制

链上只 emit 事件，链下扫日志还原业务数据，不读合约 storage。

- **方案 A（MVP，零额外基建）**：前端用 `publicClient.getLogs` / `getContractEvents` 按 `creator` 地址 + 合约地址过滤事件，直接渲染 `/dashboard` 看板（真实链上数据）。体验模式的 `demo-pay` 函数在代发交易时**顺手把易读记录（标题/金额/分账比/explorer 链接）写进 Vercel KV**，前端优先读 KV 做漂亮看板；KV 缺失时回退链上 `getLogs` 验证。真钱包模式事件由前端直读，不依赖 KV。

## 12. 链选型论证：为什么必须是 Avalanche（v1 缺失）

> v1 通读下来，Avalanche 只是"一条能部署合约的链"——换成任何 EVM 链方案一字不用改。**这是 Avalanche 黑客松，链选型可替换是重大扣分项。** 本节把链选型从背景板变成产品论点。

### 12.1 第一层论证：为什么必须用链

> **⚠️ 本节已按费率核实结论重写。** 原版把"微支付只有链能做"当作**普适**论断——**站不住**。问题出在两处：① 把支付网关（Stripe）费率误称为"卡组织费率"；② 拿美国卡费率去论证国内创作者场景。现在的措辞是**限定场景**的，反例见 12.1.3。

**论断的适用范围（三重约束，缺一不可）：**

1. **付款方是 AI Agent**（不是人类消费者）
2. **单笔金额极小**（$0.01 量级）
3. **收款方无企业资质**（国内个体创作者）

**只有三条同时成立，"链是唯一选择"才成立。** 少任何一条，论证都会塌（见 12.1.4）。

#### 12.1.1 关键一步：对 Agent 而言，微信/支付宝不是"更贵"，是"不存在"

这是原版论证最致命的漏洞。人类买家的真实替代是微信支付 **0.6%**，拿美国卡费率对比是**对标错配**。

**但对 Agent 买家，这个对比根本不成立** —— 微信支付 / 支付宝**没有任何面向自主 Agent 的接口**，且要求人类身份。Agent 用不了它们，**不是成本问题，是能力问题**。

所以在 Agent 场景里，真正可比的是**卡组织 + 支付网关**：

| 支付方式 | 单笔成本 | 对 $0.01 交易 | 可行性 |
|---|---|---|---|
| 信用卡（Stripe 美国标准，已核实） | **2.9% + $0.30** | 固定费是交易额的 **30 倍** | ❌ 数学上不成立 |
| 链上稳定币（Avalanche C-Chain） | 约 **$0.01**（待实测，见 12.2） | — | ✅ 预期成立 |

> **✅ 已核实**：Stripe 美国标准线上费率为 2.9% + $0.30（2026 年仍适用），数据来源与核实过程见 [费率核实附录](费率核实附录.md)。

#### 12.1.2 两条不可绕过的补充

- **Agent 过不了 KYC** → 开不了银行账户、申请不了商户号
- **结算必须程序化** → 没有人来点"确认付款"，扣款、分账、交付必须全自动

#### 12.1.3 ⚠️ 必须主动写出的反例

**Stripe 稳定币通道：1.5%，无固定费**（已核实存在，2026 已上线）。对 $0.01 的交易，它的费用比链上 gas **还低**。**这是本节论证的真实威胁。**

它为什么帮不到本场景，有两条硬门槛：

- **仅限美国注册企业主体** —— 国内个体创作者无法开通
- **仍需买家连接钱包签名** —— 它没解决钱包门槛，**只是换了一条链**

> **诚实提示**：如果不主动写这个反例，懂行的评委会替你问出来。**主动写 = 你做过功课；被问出来 = 你没想清楚。** 这一条的价值不在于它是弱点，而在于**你展示了你知道它存在**。

#### 12.1.4 ⚠️ 人类买家路径：费率论证不适用

**对人类买家，本节论证不成立。** 人类的真实替代是微信支付 / 支付宝，费率仅 **0.6%**（小微商户可低至 0.38%，走服务商可到 0.2%），链上 gas 优势**可以忽略**。

人类路径的诚实卖点**不是费率**，而是：

> **无企业资质 + 多方可编程分账 + 直接到账**

（微信支付做不到后两点：它不支持把钱自动分给多个协作者，也有提现周期。）

**README 里两条路径的论证必须分开写，不要混为一谈。** 混着写就是原版那个漏洞。

### 12.2 第二层论证：为什么是 Avalanche

第二层才轮到"哪条链"。这里的核心指标从"客单价占比"变成**单笔调用的成本与延迟**——因为 Agent 是按次调用的：

| 链路 | gasPrice（钱包实付） | 一笔 3 方分账的 gas | 单笔成本 | 确认时间 |
|---|---|---|---|---|
| 以太坊主网 | 约 0.086 nAVAX（实测 baseFee 0.084 + 50 分位 tip） | 待实测 | 待实测 | 待实测 |
| **Avalanche Fuji** | **1.0 nAVAX**（实测） | **159,261**（3 方，含 intrinsic，**W2 合约实测**；保守取值仍用 250,000） | **0.00025 AVAX ≈ $0.005**\* | 待实测（需一笔真实交易，见下） |

\* 按 AVAX = $20 **且按保守取值 250,000 gas** 计算。合约实测的 159,261 会给出 $0.0032，
但那个数**偏低不可用**（见下方 9/21 W2 实测块），所以本节一律用 250,000 这个上界。
**不要填任何未实测的数字**：黑客松里编数据比没有数据更糟。

> **✅ gasUsed 的形状已实测（9/21，W2）** —— `contracts/test/Gas.t.sol`，真实合约、逐方测量：
>
> | 收款方数 | `createContent` | `pay()` 执行 | `pay()` 含 intrinsic |
> |---|---|---|---|
> | 1 | 167,665 | 100,332 | 121,908 |
> | 2 | 186,646 | 108,933 | 130,509 |
> | **3（演示配置）** | **210,129** | **137,685** | **159,261** |
> | 5 | 257,096 | 195,188 | 216,764 |
>
> 每个额外收款方约 **+28,750 gas** —— 分账方数量对成本的影响是**线性且平缓**的，
> 这支撑了上面「3 方、5 方、10 方都可行」那一条。
>
> **⚠️ 但绝对数不能用，原因必须写清楚：** 测试用的是 USDC 替身，它**没有代理转发、
> 不发 `Transfer` 事件、不读黑名单存储**，而真实 USDC 三样都有。实测一笔真实 USDC
> 转账要 76,277 gas（含 intrinsic），比替身的 28,752 **每方贵约 26,500**。
> 按此修正，真实 3 方 `pay()` 约 **217,000 执行 / 239,000 含 intrinsic** ——
> 与本节原先抽样到的 250,000 吻合。
>
> **所以 250,000 保留**：它既是抽样上界，也覆盖修正后的估计值。**这个常数是定价门槛的分母，
> 宁可高估** —— 取小了门槛就是假的。
>
> 📌 **收尾项（两项，都要用真实交易）**：
> ① 用真实交易的 `gasUsed` 替换本表的绝对数；
> ② 用**提交到链上到收据可读**的实际耗时替换「确认时间」列的"待实测"。
> ②不能拿"亚秒级最终性"的公开说法顶替 —— 那是链的属性，不是**我们这条支付路径**的观测值，
> 而 §12.1 恰恰把延迟定为 Agent 场景的一级指标。测了再填。
>
> 在那之前，本节的任何成本结论都建立在 250,000 这个上界上，**引用时要说明这一点**。

> **⚠️ 追加（2026-09-22，W4 期间）—— 本节模型得到支持，但"每方 +26,500"这个系数要重推。**
>
> W3 曾在 fork 上用真实 USDC 量到 3 方 `pay()` 只有 128,985，比本节修正后的估计低 46%，
> 当时怀疑模型有问题。**查清了：是那次测量的收款方地址选错了，模型没问题。**
>
> 用的是 anvil 的默认账户（公开测试地址），**真 Fuji 上早就有人给它们转过 USDC**，
> 所以余额槽是"非零→非零"的 SSTORE，只要 2,900 gas；而 `Gas.t.sol` 用全新空账户，
> 是"零→非零"，要 20,000 gas。W4 做了只改这一个变量的对照实验：
>
> | 收款方余额槽 | 3 方 70/20/10 `pay()` gasUsed |
> |---|---|
> | **零槽位**（从没拿过 USDC —— 即真实世界"协作者第一次收款"） | **163,185**（两次跑，完全相同） |
> | 非零槽位（anvil 默认账户） | 128,985 |
>
> 差 34,200 = 2 × 17,100，而 17,100 = `20,000 − 2,900` —— 正是这两个 SSTORE 的价差。
>
> **两条结论：**
>
> 1. **本节"真实 USDC 比替身贵"的判断成立。** 零槽位实测 163,185 vs 替身的 159,261，
>    **真实贵约 3,924** —— 方向与本节所述（替身没有代理转发、不发 `Transfer` 事件、
>    不读黑名单存储）一致。**250,000 继续保留，且余量比原先以为的更足。**
> 2. **但"每个额外收款方约 +26,500"这个系数要重推。** 它来自"真实 USDC 一笔独立转账
>    76,277 − 替身 28,752 = 47,525"，而**那笔独立转账的收款方也是零槽位**，
>    所以 47,525 里有 17,100 是**槽位效应**、不是"真实 vs 替身"的效应。两者被混在了一起。
>
> **收尾项①仍然未完成，范围缩小为：在真链上重推那个每方系数。** 绝对数量级已由
> fork 实测支持（163,185 < 250,000）。⚠️ 以上都是 **fork 实测，不是真链**；
> gas 是确定性的，槽位价差不会因链而异，但按本节自己定的规矩，"不要填任何未实测的数字"
> 对真链那一步依然适用。
>
> 完整推导见 `W3-实施计划.md` §10.7（该节纠正了它自己 §10.4 的错误结论）。

> **✅ gasPrice 已实测（9/21）—— 结果推翻了本节原先的争论。** 原先对 Fuji 43113 直接读链 + 抽样真实交易，得到：

| 口径 | Fuji 43113 | 主网 43114 |
|---|---|---|
| 区块 `baseFeePerGas` | **10 wei**（1e-8 nAVAX，连续 5 块持平） | 84,147,450 wei（0.084 nAVAX） |
| 节点建议价 `eth_gasPrice` | **160 wei**（1.6e-7 nAVAX） | 96,760,086 wei（0.097 nAVAX） |
| **钱包实付** `effectiveGasPrice` | **1,000,000,010 wei ≈ 1 nAVAX** | 约 0.086 nAVAX（按 tip 推算） |
| 脚本自己拼的交易实付 | 160 ~ 176 wei | — |
| **本项目部署交易实付（9/21）** | **160 wei**（1,047,491 gas → 0.000000000168 AVAX） | — |

> **✅ 9/21 补一条实测佐证**：本项目的**真实部署交易**（`0x2d7332bb…552d55`）落链了，
> `effectiveGasPrice` 实测 **160 wei** —— 与"脚本路径"那一行完全吻合。
> 这里要**分清楚**：Foundry 用 keystore 本地签名后发原始交易，走的是**脚本路径**，
> 所以这次部署只花了 `1.68e-10 AVAX`（约等于免费）。
> **但演示时买单的是浏览器钱包，走的是 1 nAVAX 那条路** —— 同样的 gas 要 `0.00105 AVAX ≈ $0.021`。
> 两个数都真实，**别把部署的便宜误当成支付的便宜**。

**三条结论，每条都和原假设不一样：**

1. **附二的「25 nAVAX」是过时值** —— 现在实际付的是 1 nAVAX，小两个数量级。
2. **§12.2.1 第 1 条的「1 nAVAX」量级碰对了，但机制说错了。** 它讲的是**基础费**；真实基础费只有 **10 wei**（Fuji）。那 1 nAVAX 是**钱包自己加的 tip**：实测钱包发出的交易 `effectiveGasPrice` 一律是 1,000,000,010 wei，而**脚本自己拼的交易**只付 160 wei——**同一时刻、同一条链，差 600 万倍。**
3. **⚠️ Fuji 比主网贵约 12 倍。** 反直觉但成立：主网堵，基础费高，钱包随行就市只加极小 tip；Fuji 太空，基础费近乎为零，而钱包仍固执地加 1 gwei tip。**「测试网更便宜」在钱包路径上是假的**——这条要主动写进 README，评委一问就露。

> **⚠️ 由此得到对演示定价的硬约束**：演示是**买家在钱包里点确认**，所以必须按 **1 nAVAX** 算，**不能按节点建议价算**。
> 按节点建议价（160 wei）算，$0.05 的定价会显示「gas 只占 7.7e-7%，轻松过关」——**这个绿灯是假的**（前端一度就这么显示，已修）。
> 按实付价（1 nAVAX）+ 250,000 gas 算，单笔 **0.00025 AVAX**；AVAX = $20 时约 **$0.005**，占 $0.05 定价的 **10.0%**——**正好压在门槛线上，AVAX 涨到 $30 就翻车**。
> 因此演示定价**锁定 0.2 USDC**（占 2.5%，且 AVAX 涨到 $80 仍过关）。**定价门槛与阶梯见 [开发计划](开发计划.md) 5.3。**

实测后据此展开：

- **亚秒级最终性**是 Agent 场景的一级指标，不是体验优化 —— Agent 是**同步等待**的，出块慢的链会让每次调用阻塞数秒
- **极低 gas** 让**分账方数量不再受成本约束**（3 方、5 方、10 方都可行），这是"多方分账"这个卖点能成立的前提
- 若调用量大到一定程度，可论证走 **Avalanche L1 / 子网**做专用结算层 —— **仅作为 v2 演进方向写，本次不做**（见 §19）

#### 12.2.1 ✅ 三条已核实、对论证有利的生态数据（写进 README）

**这三条比 gas 实测更能说明"这不是臆想的场景"**，建议在 README 里与实测数字并列：

1. **Avalanche 已把 C-Chain 基础费下调 96%**（25 nAVAX → 1 nAVAX），2026 Q2 中位交易费同比下降 **99.6%**。**说明"降低小额支付成本"正是 Avalanche 自己在做的事** —— 我们的场景与链的演进方向一致

   > **⚠️ 9/21 实测校正**：这条的量级仍然成立，但**机制的描述要改**。实测主网基础费已是 **0.084 nAVAX**（比「1 nAVAX」还低 12 倍，说明降费还在继续）；而**用户实际付的**不是基础费 —— 钱包会在基础费之上加自己的 tip，Fuji 上实测固定加 **1 gwei**。**引用时建议改成「基础费已降至 1 nAVAX 以下」，不要把它说成用户实付价**，否则 §12.2 的表一摆出来就自相矛盾。详见上一节的三条结论。
2. **官方降费的理由，几乎是我们论证的复述**：降费的公开解释是"当发送 5 美元 USDC 几乎不花钱时，人们才真的会发；当 gas 要 2 美元时，他们不会。" —— **这正是 §12.1 固定费吃死微支付的同一条逻辑**
3. **C-Chain 上 USDC 转账占链上活动最高达 70%，且多为 $10 以下的小额支付** —— **官方链上数据支持"小额稳定币支付是真实需求"**，不是我们编的场景
4. **🎯 最强的一条：HTTP 402 状态码 1990 年代就被预留，却闲置了三十年——原因正是"卡组织手续费让不足 1 美元的支付不经济"。** 这是 Visa 官方在其 Agentic Payments 报告里的原话（见 [Agent 支付生态调研附录](Agent支付生态调研附录.md) 核实记录）。

> **这条几乎是 §12.1 论证的官方复述。** 一个三十年前为微支付预留、却因卡费而无法启用的协议槽位，现在被整个支付行业联手激活——**这不是我们的臆想，是行业的共识性判断**。README 里建议直接引用并标注来源，**这是全篇最有分量的一条外部背书**。

> **怎么用**：README 的链选型一节建议这个顺序 —— ① 先给 12.1 的结构性论证 → ② 再给 12.2.1 的生态数据（证明趋势） → ③ 最后给 12.2 的 gas 实测（证明当下）。**从"为什么该是这样"到"事实正在这样"再到"我实测就是这样"，说服力是递进的。**
>
> **⚠️ 引用这三条时要标来源**（CryptoBriefing / Nansen / Messari 等公开报告），并注明是**我们的解读**，不是官方对本次参赛的背书。

### 12.3 反向论证：为什么不是"随便哪条 EVM 链"

必须在 README 正面回答，否则评委会问。答案分三层，**顺序不能颠倒**：

1. **在 Agent 微支付场景下，链是唯一可行的支付轨道**（12.1，**注意是限定场景**）
2. **而在链里面，单笔成本与延迟是一级约束**（12.2 + 12.2.1 的生态数据）
3. **我们诚实知道替代方案存在**（12.1.3 的 Stripe 稳定币反例），并说清它为何帮不到本场景

> **诚实提示**：本产品仍未用到子网 / HyperSDK / ICM 等 Avalanche 独有原语。12.1 的论证是**场景驱动的**，不是"生态内建"的。这个弱点用论证补，不用改架构补——**9 天里改架构是自杀**。
>
> **⚠️ 另注意**：原版此处的措辞是"**微支付**场景下链是唯一轨道"——**这是过度概括，已被费率核实推翻**。正确表述是"**Agent 微支付 + 无企业资质**场景下"。差别很大：少了限定词，评委拿微信 0.6% 一句话就能驳倒你。

## 13. 竞品与差异化（v1 缺失）

评委会问"为什么不用已有的 X"。README 要能一句话答。

| 竞品 | 它是什么 | 它的短板 | 本产品的差异 |
|---|---|---|---|
| **爱发电 / 知识星球** | 国内创作者收款平台 | **抽成**；需实名/资质；提现周期 | **无抽成、即时到账**；但人类买家门槛高（需自备 USDC），见 1.1 |
| **Gumroad** | 海外数字商品销售 | 抽成 + 费率；**无法服务国内创作者**；不支持链上分账 | 链上直付、**原生多方分账** |
| **微信支付 / 支付宝** | 国内主流支付 | **需企业资质**；手续费；个体创作者门槛高 | 个体创作者零资质可用 |
| **链上 Paywall 工具**（各类） | 单地址收款页 | **不支持多方自动分账**，协作者要手动分 | **分账是核心而非附加** |
| **Agent 支付基础设施**（x402 生态等） | 机器支付的协议/中间件层 | **面向开发者，不面向内容供给方**；不解决钱怎么分给多个创作者 | **不跟它们竞争，而是接入它们** —— 我们提供"可被 Agent 购买的内容 + 自动分账"这一侧 |

**一句话差异（v2.1 升级）**：

> 别人解决"**人**怎么把钱付给**一个**创作者"。我们解决"**人和 Agent 都能付**，而且钱**自动分给一起干活的每个人**"。

v2.0 的差异只有一个（多方分账），v2.1 有两个（**双类买家 + 多方分账**），而且第二个是当下最热、供给最少的一侧。

**⚠️ 诚实提示**：上表是对竞品的快速定性。**报名后应花 1 小时做真实调研**——人类侧的抽成比例、是否支持分账、国内可用性，以及 **Agent 支付生态当前的进展（尽量避免与已有项目正面撞车，或明确说明我们的差异是"内容侧"而非"支付侧"）**。把"定性"换成"带数字的对比"。**不要凭印象写竞品数据。**

### 20.4 W5 落地后的诚实边界（2026-09-23 追加）

> **这一节是追加的，上面 20.1–20.3 一字未动。** 20.1–20.3 记的是**合规定位**（9/21 写的）；这一节记的是**存储与付费门禁真正落地之后**才看得清的**技术**边界。每一条在代码注释里各有一份更细的说明，这里是汇总——**别让它只活在注释里**。

#### 20.4.1 「先上传、后创建」这个顺序的代价

两个顺序都写得出来，选了**先上传**，因为它保证**凡是链上买得到的内容，背后一定有文件**。反过来（先创建后上传）如果上传失败，链上会留下一条买家能付钱、却没有文件的内容——而合约里没有"文件存不存在"这个概念，拦不住。

代价有三条，都必须记：

1. **上传时链上还没登记**，所以服务端第⑤步"链上归属"查不到，只能靠第⑥步 KV 先到先得。风险小是因为 `contentId` 是本地生成的 32 字节密码学随机数、上链前外人不知道——**但这是"风险小"，不是"防住了"**。
2. **创建失败后重试必须跳过上传**：pathname 是确定性的，平台侧 `allowOverwrite: false` 会拒掉往同一条路径的第二次写。所以"文件传上去了没有"必须记在状态里（`publishMachine` 的 `uploaded`），不能等重试时重新判断。
3. **有一种情况程序判断不了**：PUT 的字节已经落地、但响应在回来的路上丢了（传到一半断网）。此时 `uploaded` 是 false，而文件其实在上头；直接重试会在上传那一步被平台以"不能覆盖"拒掉，用户看到的是"又失败了"。**不去猜**（匹配平台的错误文案，猜错就会创建出一条没有文件的内容），而是把这个判断交给用户——界面上有一个明确的「我确定文件已经传上去了，直接创建」出口，写着"只有在你亲眼看到进度条走完了才选这个"。

#### 20.4.2 上传授权签名**没有 nonce**（有意为之）

解锁那条签名有 nonce，这条没有。理由：重放这条签名的唯一后果，是拿到一张指向**同一条 pathname** 的 token——而那个 blob 已经存在了，平台侧 `allowOverwrite: false` 会直接拒掉。**重放造成不了任何后果，nonce 买不到额外的安全。** 所以只靠 `deadline`（5 分钟）兜底，并且**没有**给 `/api/unlock-nonce` 增加第二种用途。

⚠️ **这条推理依赖两个前提**：pathname 确定性、`allowOverwrite` 为 false。**任一变化（比如打开 `addRandomSuffix`）这套说辞立刻不成立**，那时必须补 nonce。

#### 20.4.3 内容文件**不按类型白名单**

`ALLOWED_CONTENT_TYPES.content = undefined`，即不限类型——创作者传什么都有可能（PDF／视频／压缩包），列白名单会把正常用法挡在外面。代价是：**任何人只要拿到 token 就能往私有 store 里放一个 HTML 文件。** 这**不构成对本应用的 XSS 面**，因为那个 store 是私有的（只能通过 60 秒签名 URL 取出），且 blob 域名与本应用**不同源**。

预览图那一侧则**只收 `image/*`**——因为那个 store 是公开的，放进去就是公开可读，没有理由让公开 store 托管任意活动内容。两侧的不对称是有意的，别"顺手统一"。

#### 20.4.4 门禁的失效方向是 **fail-closed**

KV 连不上时，所有函数一律返回"没有"：拿不到 nonce 就签不出合法请求，**门禁因此拒绝服务，而不是放行**。服务端读链同理：`getContentCreator` 只把**明确的 `ContentNotFound` revert** 当作"内容不存在"，**其它任何错误一律往外抛**，由路由回 503——绝不把"RPC 读不到"当成"没买过"，那样一次节点抖动就会让门禁放行。

**要如实说清的代价**：RPC 或 KV 抖动时，产品会降级成"暂时不可用"，**已付费的买家也会下载失败**。这是刻意选的方向（宁可拒绝，不可放行），但它是真实存在的可用性损失。

#### 20.4.5 买家下载到的**文件名就是 contentId**

blob 存在 `content/<contentId>`，取回时是一条普通的签名 GET，没带 `Content-Disposition`。所以买家浏览器保存下来的文件**名就叫 `0x…`，没有扩展名**——原始文件名和 MIME 类型没有在任何地方被保留。

这不是安全问题，是体验问题。可修（把原名记进 KV，或签 URL 时带 `contentDisposition`），但不在 W5 范围内。

#### 20.4.5.1 上面那条**结论对、论证错**（2026-09-23 追加）

上面说"签名 GET 没带 `Content-Disposition`，所以文件名是 `0x…`"。**文件名那半句是对的，理由和修法都不对。**原文不删，更正追加在这里。

**实测发现了什么。** 在部署站点上真的买一份、真的点下载：**文件没有下载，浏览器把它当普通页面打开了**，得手动"另存为"。存下来的文件 483,839 字节，`keccak256` 与链上 `contentHash` 完全一致（`0xfed7e6aa…`）——**内容是对的，交付方式是坏的**。

**为什么。** 前端的 `fireDownload` 写的是：

```ts
a.download = ''      // ← 这行一次都没起过作用
a.target = '_blank'
```

HTML 规范里 `download` 属性**只对同源、`blob:`、`data:` URL 生效，跨源 URL 一律忽略**。而这条链路**永远跨源**：app 在 `splitjar.vercel.app`，blob 在 `*.private.blob.vercel-storage.com`。所以浏览器按普通导航处理，`Content-Type` 又不是可渲染类型，结果就是内联打开一个陌生页面。

⚠️ **原文的盲点在于把后果判轻了。**当时 `UnlockButton.tsx` 里那句注释其实**已经写明**"跨域时 `download` 会被忽略"——但紧接着的结论是"留着它不报错"。忽略它丢掉的不是文件名，是**下载这个动作本身**。

**那文件名为什么还是对的。** 响应没有 `Content-Disposition` 时，浏览器**拿 URL 最后一段兜底**当文件名，而我们的 URL 最后一段正好就是 contentId。**结论碰巧成立，机制完全不是当初以为的那个。**（顺带更正原文没说的一句：浏览器**不会**按 `Content-Type` 补扩展名——实测存下来就是个没有扩展名的 `0x…` 文件。）

**原文建议的修法不可用。**"签 URL 时带 `contentDisposition`"——查过 SDK 了，**没有这个参数**：`PresignGetUrlOptions` 只有 `{ operation, pathname, validUntil, useCache }` 四个。`contentDisposition` 是**上传结果上的只读字段**，不是 presign 的入参。

**真正的修法。** 服务端用 `@vercel/blob` 导出的 `getDownloadUrl(presignedUrl)` 包一层。它就是 `new URL(u)` + `searchParams.set('download','1')`，纯字符串操作、不额外发请求，让 CDN 响应带上 `Content-Disposition: attachment`。

签名安全性已核实：`download` **不在** SDK 的 `PRESIGN_CANONICAL_QUERY_KEYS` 里（那一组只有 put 相关的 `addRandomSuffix` / `allowOverwrite` / `allowedContentTypes` / `cacheControlMaxAge` / `callbackTokenPayload` / `callbackUrl` / `ifMatch` / `maximumSize` / `validUntil`），所以追加它**不会**让签名失效——与 `cache` 同理。

**考虑过并否掉的方案：让 `/api/unlock` 代理字节。** 那样能做到同源、能任意定响应头。但**内容文件没有尺寸上限**，把一个可能几百 MB 的文件塞进 serverless 函数当管道，迟早撞上执行时限和流量限制。**为了一个文件名去牺牲"文件不经过函数"这条 W5 的核心设计，不划算。**

**⚠️ 诚实边界：这条修法我没有验证过。**本机连不上 blob 主机（见 §20.4 之前记的网络限制），而签名 URL 是一次性的、60 秒作废，没法事后复现。**能证明的只有三件事**：`presignUrl` 没有 `contentDisposition` 参数、`getDownloadUrl` 的代码就是加一个 query 参数、`download` 不在签名覆盖范围里。**"加了它浏览器就会下载"这句话是推断，不是实测**——需要重新部署 + 真的再下一次才算数。（这正是 W5 首部署那条教训的翻版：**构建成功、类型通过，都不代表它按你设想的方式工作**。）

**这次验证的正向结论也记一笔。**"上传的字节 → 链上承诺的哈希 → 门禁放行 → 取回的字节"四段现在是**同一个东西**：下载回来的 483,839 字节，其 `keccak256` 等于链上 `contentHash`。链下存储、链上承诺、付费门禁三者第一次被一条完整的证据链串起来，而不只是三个各自能跑的部分。

#### 20.4.5.2 「文件名是 contentId」**不是可接受的代价**（2026-09-23 追加，已修）

§20.4.5 把它记成"体验问题，可修……但不在 W5 范围内"，§20.4.5.1 把"结论碰巧成立"当成结论收下了。**两条都过于宽容，而且 §20.4.5 给的修法方向两条都不对。**原文不删，更正追加在这里。

**用户报的是「本地无法打开」。** 先核对文件：483,839 字节，`keccak256` 与链上 `contentHash` **逐字节一致**，魔数 `89 50 4E 47` 是 **PNG**。**字节从来没错过，坏的只是名字**——Windows 没有扩展名就认不出类型。（用户第一次的描述是"不是图片格式"，同一个成因：它一直是 PNG，只是名字里没有 `.png`。这点很重要 —— **差点去修一个没坏的东西**。）

**§20.4.5 提的两个修法，一个不必要、一个不可能。**"把原名记进 KV"不必要（见下，不需要知道原名）；"签 URL 时带 `contentDisposition`"不可能（§20.4.5.1 已核实：`PresignGetUrlOptions` 根本没有这个参数）。

**真正的修法：把文件名和 pathname 解耦。**§20.4.5.1 默认了"文件名只能由 `Content-Disposition` 决定，而它由 pathname 决定"——**这一步是错的**。字节取回内存之后，名字由前端说了算。四条路：

| 路 | 结果 |
|---|---|
| ① `<a download>` | **被规范忽略**，链路永远跨源（app 在 `splitjar.vercel.app`，blob 在 `*.private.blob.vercel-storage.com`） |
| ② presign 传 `contentDisposition` | **没有这个参数** |
| ③ 扩展名写进 pathname | 要放宽 `PATHNAME_RE`，而那条正则同时是防路径穿越、和保证"一个 contentId 只对应一条 pathname"（从而让 `allowOverwrite` 的逐字节判重有效）的边界；扩展名来自客户端输入；且只对**以后**的上传生效 |
| ④ `/api/unlock` 代理字节 | 内容要穿过 Function，上限 200 MiB 的素材够呛；§20.4.5.1 已否过一次 |

走的是第五条：**`fetch` 回字节 → `URL.createObjectURL()` → `<a download>`**。要害在于 `createObjectURL()` 产出的是 **`blob:` 同源 URL**，而 `download` 属性**只在同源下有用**（正是不走 ① 的原因）。名字与扩展名完全由前端定。

**扩展名从哪来。**MIME 类型在上传时就被存下了（`src/lib/uploadApi.ts` 传了 `contentType: args.file.type || 'application/octet-stream'`），取回字节后读 `blob.type` 即可。`Content-Type` 是 **CORS 安全列表响应头**，所以跨源也读得到、不需要 `Access-Control-Expose-Headers` —— 这是这条修法能成立的前提。查不到就**不给扩展名**（宁可不给也不猜错），但先用几个魔数兜一次底（`octet-stream` 那种上传时 `file.type` 为空的场景，症状与本 bug 一模一样）。

**标题是客户端可控的，所以文件名是边界不是装饰。**标题来自分享链接的 `?t=`，任何拿到链接的人都能改，而它会变成**买家硬盘上的文件名**。`safeFilename()` 去掉路径分隔符与 Windows 非法字符、控制字符、开头和结尾的点与空格、限长（按码点截，免得把字切成半个代理对）、并给 Windows 设备名（`con`/`nul`/`com1`…）加前缀。浏览器也会挡一部分，但**不能靠它**——这是我们的输入、我们的责任。

**代价，如实记。**①**整个文件进内存**，与 §20.4.6 是同一类边界；②**依赖 blob 域名允许跨源 `fetch`**，而这条**本机验证不了**（该域名在本机 `ECONNRESET`）。所以 `downloadWithName()` 返回 `false` 时**必须回退**到老路子（`target="_blank"` 导航）——**最坏情况是维持现状，不会比修复前更差**。

**验证到哪一步。**纯函数用一张表过了一遍（MIME→扩展名 13 例、魔数 4 例、文件名清洗 12 例：穿越路径、Windows 设备名、`..`、200 字符、代理对、控制字符）；**真浏览器**里验了下载落盘的名字（`first test.png`）、无标题时退回 contentId、`octet-stream` 靠魔数兜底、以及 403 时确实返回 `false` 并回退成导航；再把解锁三跳全接管，端到端跑通「点 → EIP-712 签名 → 换 URL → 取字节 → 起名落盘」。

**⚠️ 没验证的：真 CORS 行为。**`page.route().fulfill()` **不强制执行 CORS**，所以"跨源被拦 → 回退"这个失败**模拟不出来**（第一版把它当成一条用例，拿到的是假结论——那次 fetch 其实 200 成功了）。真行为只能在部署后看。**判据**：下载下来的文件叫 `first test.png` 而不是 `0x6410fb09…`。

#### 20.4.6 `computeFileHash` 把**整个文件**读进内存

`file.arrayBuffer()` 一次性载入，**峰值内存约等于文件大小**。200 MiB 的文件（也就是 `MAX_UPLOAD_BYTES` 的上限）在手机上够呛。做成流式增量哈希需要一个增量 keccak 实现——`@noble/hashes` 有，但它是 viem 的**传递依赖**，直接 import 它会在 lockfile 变化时**悄悄断掉**。所以这一版接受这个边界。演示素材的量级（几 MB 到几十 MB）完全没问题。

#### 20.4.7 预检与真传之间**不是原子的**

浏览器在上传前先打一枪预检，把"重试也修不好"的错误如实拿到手（起因是 `@vercel/blob` 的客户端 SDK **不读非 2xx 的响应体**，服务端精心分的 code 一个都到不了前端）。但**预检通过不等于上传会成功**：两者之间隔着一个来回，期间别人可能把这份内容认领走。**预检不是授权，只是"早点把坏消息说清楚"。**

反过来说：预检**故意不查链上归属**（第⑤步）。那是一次真 RPC，失败多半是节点抖动，而"重试"对那种情况本来就是对的答案——预检只负责挑出"重试没用"的那几条。

#### 20.4.8 服务端 SDK 的**一部分**被带进了前端产物

`src/lib/uploadApi.ts` 引入 `@vercel/blob/client` 的 `upload`，于是整个客户端 SDK 进了浏览器产物——而**同一个模块文件里还带着 SDK 的服务端那一半**（`handleUpload`、`generateClientTokenFromReadWriteToken`、凭证解析）。构建产物实测：`BLOB_READ_WRITE_TOKEN`、`BLOB_STORE_ID`、`process.env`、`vercel_blob_client_` 这些**字符串**确实在 `dist/assets/index-*.js` 里，**但没有任何值**（`VITE_` 变量一个都没被内联，也没有任何长随机串）。

判定为**不构成泄漏**，理由是三条一起看的：① SDK 的 `readEnv()` 把 `process.env[name]` 包在 try/catch 里，浏览器里 `process` 不存在也只会返回 `undefined`，不会抛；② 客户端 `upload()` 取 token 走的是 HTTP（`retrieveClientToken` 打我们的 `/api/upload`），**根本不读环境**，所以那段代码不可达；③ 里面只有变量**名**，没有变量**值**。

代价是**体积**：单包 818 kB（gzip 249 kB），构建会警告 chunk 超过 500 kB。要瘦下来得做代码分割，属于工程优化，不在 W5 范围内。

#### 20.4.9 付费页首屏**从来没有跑过校验**（2026-09-23 追加，已修）

**现象。** 已经买过的钱包打开付费链接，首屏是一个「付款 0.05 USDC」按钮——**点了**才告诉他「你已经买过了」。用户报的就是这个。

**根因。** 校验全部写在 `usePayFlow` 的那个 effect 里，而它的头一行是：

```ts
if (state.k !== 'checking') return
```

`checking` 只由 `'start'` 动作产生，而 `dispatch({ type: 'start' })` **只有付款按钮的 onClick 会发**（`usePayFlow.ts` 的 `start`）。首屏是 `idle`，于是那段判断一次都没执行过——里面包括 `already-purchased`、`insufficient-usdc`、`insufficient-avax`、`content-inactive` **全部四条**。

**这不是"漏了一个分支"，是意图与实现岔开了。** 两处旁证：`payMachine.ts` 的 `BlockReason` 注释写着「让用户签完名才告诉他'你早买过了'是在浪费他的时间和 gas」——正是这个 bug 在违反它；`splitter.ts` 里有个 `ContentGate` 类型，注释写着「付费页**首屏**要同时判断'存在 / 已下架 / 我买没买过'」——**全仓库零引用**，是为这件事写的、从没接上。

**实测证据。** 注入 mock 钱包（读方法全部转发真 Fuji RPC，所以链上数据是真的），买家 `0x9750Af96…` 打开 `0x6410fb09…`：首屏文本是「付款 0.05 USDC」；点一下之后才变成「你已经买过了」。浏览器发出的 multicall 里，`purchases(cid, 0x9750Af96…)` 返回的是 `true`——**那次读一直是对的，只是没人看**。

**修法。** 把判断抽成纯函数 `evaluateGate()`（新文件 `src/lib/payGate.ts`），**渲染和 effect 共用同一份**；首屏用**派生态**表达结论，而不是发一个新动作：

```ts
const viewState = state.k === 'idle' && gate.k === 'blocked'
  ? { k: 'blocked', reason: gate.reason } : state
```

**为什么不干脆 dispatch 一个 `blocked`。** 那需要一条「什么时候退回 `idle`」的规则——用户换钱包、切网络、链上读刷新，都得重新放行。状态机会多出一类「卡在 blocked 出不来」的 bug。派生态没有任何需要清理的东西，数据一变它自己就变。

判断函数返回**三种**结果而不是两种：`pending` 必须能表达出来。数据没读齐时放行 = 首屏先显示付款按钮再翻脸；拦下 = 无中生有一个错误。

**顺带补上的一个洞：归属读失败原先会 fail-open。** 原写法是 `if (owned.data === true) 拦下`，于是「读失败」和「没买过」落进同一个分支——**一次 RPC 抖动就会让页面去推销用户已经拥有的东西**。钱不会丢（合约第二次 `pay()` 会 revert `AlreadyPurchased`），但用户会被引导去签一笔注定失败、白花 gas 的交易。

改成 fail-closed：**只有明确读到 `false` 才放行**，其余一律进新增的 `ownership-unknown`。它和 `already-purchased` **必须分开**——把「查不到」说成「你已经买过了」，会告诉一个从没买过的人去看下载链接，而 `/api/unlock` 会返回 402。同一个文件里另外两个读方向本来就是对的（`usdcBalance` 读失败当 0 → 拦住；`allowance` 读失败当 0 → 多走一次 approve，无害），只有归属这一个错了会朝危险的那边倒。

**两处刻意的「不做」。**

1. **`wallet-not-connected` 和 `wrong-chain` 不透出到首屏。** 付费页自己就为这两条渲染了 `ConnectButton`，再透出去会多画一份「先连接钱包」跟按钮叠在一起。（本来也到不了：没连接时页面不渲染付款按钮，`checking` 根本进不去。）
2. **`isReading` 不看闸门。** 它保持 `exists.isLoading || content.isLoading`。否则对一个还没连钱包的人，`content` 那次读压根没启用（`enabled: exists.data === true` 要等人连上），页面会渲染出一个「内容不存在」的**死结论**。骨架屏更诚实：我们确实还不知道。

**删掉了一个抢视线的按钮。** 闸门把「你已经买过了」提到了首屏，于是「下载内容」和「重新检查」两个同样醒目的红按钮叠在一起。判据取自状态机自己的声明（`describeBlock(reason).recovery.k === 'download'`），不另写一份 reason 清单：出路是「下载」时，那个付款/重试按钮就没有存在理由。余额不足是 `faucet`、已下架是 `none`，那些场景里「再查一次」有意义，**照旧渲染**。

**验证到哪一步。** `splitjar/src/lib/payGate.ts`、`usePayFlow.ts`、`payMachine.ts`、`PayPage.tsx` 四个文件；`tsc` / `lint` / `build` 均通过。行为用 mock 钱包打真链验了三组：① 买家 → 首屏「你已经买过了」+ 下载按钮，**零次钱包调用**；② 非买家（创作者钱包，USDC 恰好等于价格、有 AVAX、无授权）→ 正常「付款 0.05 USDC」，**零次钱包调用**（这组是防回归：别为了修 ① 把正常买家也拦了，或者变成一进页面就自动弹钱包）；③ 在网络层只把 multicall 里 `purchases` 那一格的 `success` 置成 false → 首屏「查不到你的购买记录」+ 重试，**没有付款按钮**。

**没验证的**：改动**尚未部署**，以上都是本机 dev server 的结果。另外「已购买」那一态现在仍会显示「数字内容，一经售出概不退款」的提示——对一个已经付过钱的人，这条是噪音。留着没动，因为它是 §5.1/§19 要求的购买前提示，删它要单独论证。
