## 三、付款状态机(计划点名"最容易做错")

### 3.1 为什么先用判别联合

上游要求"每一种失败都必须映射到一个**明确的界面状态**,不能都落到'处理中'然后卡死"。

用 `useReducer` + 判别联合,而不是散落的 `useState`:

- **非法状态不可表示**。`{ k: 'confirming' }` 没有 `hash` 字段 → 编译不过,不可能渲染出"确认中但不知道在确认哪笔"。
- **零新依赖**。不引 xstate —— 这是个 7 状态的线性流程,不是状态图爆炸的场景。
- `noUnusedLocals` + 穷尽性 `switch` 一起,漏处理某个状态会编译报错。

### 3.2 类型定义

```ts
// src/lib/payMachine.ts

/** 校验阶段就拦下的问题 —— 还没到签名,不该让用户白签一次 */
export type BlockReason =
  | 'wallet-not-connected'
  | 'wrong-chain'
  | 'content-not-found'
  | 'content-inactive'
  | 'already-purchased'
  | 'insufficient-usdc'
  | 'insufficient-avax'      // R3:买家无 AVAX 付 gas

/** 签名/上链阶段的失败 */
export type FailReason =
  | 'user-rejected'          // 拒签或关弹窗
  | 'insufficient-usdc'
  | 'insufficient-avax'
  | 'insufficient-allowance' // 第 2 笔才发现授权不够
  | 'already-purchased'
  | 'content-inactive'
  | 'content-not-found'
  | 'reverted'               // 未归类的合约 revert
  | 'rpc-timeout'
  | 'receipt-timeout'        // ⚠️ 见 3.5 —— 这个不等于失败

export type PayState =
  | { k: 'idle' }
  | { k: 'checking' }
  | { k: 'blocked'; reason: BlockReason }
  /** 首次购买是两笔:step 1 = approve,step 2 = pay */
  | { k: 'signing';  step: 1 | 2 }
  | { k: 'pending';  step: 1 | 2; hash: `0x${string}` }
  | { k: 'confirming'; step: 2; hash: `0x${string}` }
  | { k: 'success';  hash: `0x${string}` }
  | { k: 'failed';   step: 1 | 2; reason: FailReason };
```

### 3.3 状态转换表

| 当前态 | 事件 | 次态 |
|---|---|---|
| `idle` | 用户点付款 | `checking` |
| `checking` | 校验通过 | `signing(1)` |
| `checking` | 校验拦下 | `blocked(reason)` |
| `signing(1)` | 拿到 approve hash | `pending(1, hash)` |
| `signing(1)` | 用户拒签 | `failed(1, 'user-rejected')` |
| `pending(1)` | 收据 success | **`signing(2)`** ← 不停留,直接进第 2 笔 |
| `pending(1)` | 收据 reverted | `failed(1, …)` |
| `pending(1)` | 收据超时 | `failed(1, 'receipt-timeout')` |
| `signing(2)` | 拿到 pay hash | `pending(2, hash)` |
| `pending(2)` | 收据 success | `confirming(2, hash)` |
| `pending(2)` | 收据 reverted | `failed(2, 按 revert 选择器分类)` |
| `confirming(2)` | 达到确认数 | `success(hash)` |
| `failed(*)` | 用户点重试 | `checking`(重跑校验,不直接重签) |

### 3.4 两笔交易怎么让用户不误解

**这一版最容易招差评的地方**:用户点一次"付款",钱包弹两次。第二笔一定要说清:

- 第 1 笔:`signing(1)` → 文案「**第 1/2 步:授权 USDC**(不转账,只是允许合约代扣)」
- 第 2 笔:`signing(2)` → 文案「**第 2/2 步:确认支付 0.2 USDC**」

§8.1 的 `approve` + `transferFrom` 是**冻结接口有意为之**,不是实现偷懒。文案要把"授权不花钱"讲明白,否则用户以为被扣两次。

### 3.5 ⚠️ 收据超时 ≠ 失败(最容易写错的一条)

`waitForTransactionReceipt` 超时只说明**我们没等到收据**,不说明交易没上链。此时:

- **不能显示失败**,也不能简单给"重试" —— 交易可能已经成功,重试会再弹一次钱包
- 文案:「交易可能已提交。请稍后在[看板/explorer]确认,不要重复支付。」
- 给 explorer 链接(hash 已知)

**兜底是合约本身**:`purchases[contentId][buyer]` 让第二次 `pay()` revert `AlreadyPurchased`。
所以就算用户真重试,钱不会被扣两次。**这一点值得在演示时讲** —— 它是"状态机不确定时,链是最终裁判"的具体例子。

### 3.6 每种失败态的文案与出路

| reason | 文案 | 可否重试 |
|---|---|---|
| `user-rejected` | 你取消了签名 | ✅ 重试 |
| `insufficient-usdc` | USDC 不足,还需 X | ❌ 给 faucet 指引 |
| `insufficient-avax` | AVAX 不足付 gas | ❌ 给 faucet 指引 |
| `insufficient-allowance` | 授权额度不足,请重新授权 | ✅ 重试 |
| `already-purchased` | 你已购买过 | ❌ 给下载入口 |
| `content-inactive` | 该内容已下架 | ❌ 无 |
| `content-not-found` | 内容不存在,检查链接 | ❌ 无 |
| `reverted` | 交易被合约拒绝 + 原始错误 | ✅ 重试 |
| `rpc-timeout` | 网络繁忙,请重试(**不得显示成功**) | ✅ 重试 |
| `receipt-timeout` | 交易可能已提交,请先查证 | ⚠️ 不给一键重试 |

### 3.7 与 wagmi 的接法

用 `useWriteContract` + `useWaitForTransactionReceipt`,**不用** `useSendTransaction`(后者不解析 ABI,拿不到自定义错误)。

两笔交易的串联放在 `usePayFlow` 这个 hook 里:`pending(1)` 收到成功收据后,reducer 派发 `{ type: 'approve-confirmed' }` → 进入 `signing(2)`,由 `useEffect` 触发第二笔 write。

**自定义错误的提取**是这一层的关键:writes 的 error 要过一遍 ABI 解出 `AlreadyPurchased` 等,再分类成 `FailReason`。viem 的 `BaseError.walk()` 拿 `ContractFunctionRevertedError`。

## 六、三处需要注意的技术事实

### 6.1 `shared/chain.ts` 里不能写 `import.meta.env`

该文件两端共用,服务端没有 `import.meta`。所以:

```ts
// shared/chain.ts —— 纯常量,两端都能读
export const DEPLOYED_SPLITTER = '0xDe9b3090263e20ebD5b3795F0199B500f6da72f5' as Address
export const DEPLOY_BLOCK = 58_513_443n   // 看板 getLogs 的 fromBlock 起点
```

前端 `import.meta.env.VITE_SPLITTER_ADDRESS ?? DEPLOYED_SPLITTER`,服务端 `serverEnv(...) ?? DEPLOYED_SPLITTER`。
前端 `lib/rpc.ts` 已有 `?? 'https://…'` 的先例,照它写。

> `DEPLOY_BLOCK` 顺手也是 W5/W8 服务端事件索引的起点。

### 6.2 wagmi v3 的 `useBalance` 不支持 `token`

ERC-20 余额(U**S**DC)必须走 `useReadContract` + `erc20Abi.balanceOf`;AVAX 余额才用 `useBalance`。
(开发计划 W1 已记录,W3 读 USDC 会直接撞上)

### 6.3 看板的 `eth_getLogs` 范围

2026-09-21 实测:**公共 Fuji RPC 不限制范围**,10 万块一次查完都成功。
所以从 `DEPLOY_BLOCK` 起扫即可,无需分页、无需索引器。部署至今约 1.9 万块。

### 状态机的失败路径(可以主动造)

10. **拒签**:点付款后在钱包里点取消 → 必须落在 `failed(user-rejected)`,不是卡在"处理中"

## 十、实施记录（2026-09-22）

本节是**事后追加**的：上面 §一–§九 是开工前写的计划,原样保留;这里记实施时
真实发生了什么 —— 偏离、缺陷、验证结果。**计划与事实分开放,不互相覆盖。**

### 10.1 实施时的偏离（三条,计划里没有）

| 项 | 计划里怎么写 | 实际怎么做 | 为什么 |
|---|---|---|---|
| `checked-ok` | 隐含"总要先 approve" | 带上 `needsApprove` | 授权额度够就跳过 approve —— 买过一件之后再买另一件只需一笔。不加这个字段,文案会谎报"第 1 / 2 步",用户会以为流程没走完 |
| 文案与出路 | 放在 `PayStatus.tsx` | 全部移到 `payMachine.ts` | "这个失败能不能重试"是**逻辑**不是样式。散在组件里就会出现两处各写一份、迟早不一致 |
| 分账预览 | 未提及 | **不连钱包也显示** | 两行写的是"我 / 协作者",只有比例,不需要知道地址。原先挂了 `address`,没连钱包时这张卡片是半空的 |

### 10.2 实施中发现并修掉的缺陷（五条）

1. **⚠️ `pending` 状态丢了步数上下文**（最严重的一条）
   §3.4 要求"每一步都写明第几笔/共两笔,第 1 笔明说不转账",而 `stepCopy`
   只在 `signing` 分支被调用。但用户**盯得最久的恰恰是 `pending`** ——
   第 1 笔上链要几秒。也就是说:最需要解释的那一段,是唯一没解释的一段。
   点一次付款钱包弹两次,第一笔等待时界面读起来像"钱已经付了"。
   修法:`payMachine` 新增 `pendingCopy(step, needsApprove)`,与 `stepCopy` 同一个位置。
2. **创建页空表单一开始就飘红** —— 一个字没敲就显示"标题不能为空"。
   校验照跑(`parsed.ok` 一直拦提交),推迟的只是**显示**:失焦一次才算碰过。
3. **三处 JSX 文本里的字面 `**`** —— 按 markdown 写的强调直接渲染成了
   `**抽样上界**`。`ChainProbe.tsx`、`CreatePage.tsx` ×2。
4. **分账预览被 `&& address` 挡住** —— 见 10.1 第三行。
5. **`/favicon.ico` 404** —— `index.html` 没有任何 icon 声明,浏览器就去要默认路径。
   补一个内联 SVG data URI。

### 10.3 验证方法与结果

**方法:本地 fork 真跑,不是读代码。** `anvil --fork-url <Fuji 公共 RPC> --chain-id 43113`,
合约用 `DEPLOYED_SPLITTER` 在 fork 上的**真实部署**,USDC 用**真实 Fuji USDC**
(`0x5425…Bc65`),再注入一个 `window.ethereum`(EIP-1193)由本地测试私钥签名 ——
于是付费页的连钱包状态可以整个走通,**不需要真币、也不碰真链**。

> ⚠️ 注入的是 EIP-6963 的 `announceProvider` 事件,**不是只挂 `window.ethereum`**。
> wagmi v3 走 6963 发现钱包,只挂 provider 的话连接器列表是空的,界面显示
> "没检测到浏览器钱包扩展"。

- **校验拦截时钱包一次都没被唤起。** 这是"拦住是为了不让人白签"的唯一证法 ——
  看界面说没说要付款是看不出来的,得数 `eth_sendTransaction` 的调用次数。
  已购买、余额不足两种拦截都是 **0 次**。
- **合约不留灰尘。** 全部付款跑完后,splitter 自己的 USDC 余额 = **0**,
  收款方余额之和 = 买家付出的总额。§3 的"余数归最后一个收款人"在真链状态上成立。

### 10.4 ⚠️ gas 实测:与方案 §12.2 的估计**对不上**

实测只有 128,985 —— 低了约 46%。** 而且实测的 3 方数(128,985)**低于** §12.2
那张表里替身 3 方的执行数(137,685),按那张表的模型这不可能。

我**没有能自洽解释这个差距**,所以**没有动 §12.2**。目前的判断:

- 那笔 45,047 的独立 `transfer` 的收款方是**冷**槽位,而 `pay()` 里的推送

   方案里那句"不要填任何未实测的数字"对这条同样适用。
3. 真正的 3 方场景是 W4,届时用真链交易复核一遍再填表。

### 10.7 ⚠️ §10.4 的结论是错的 —— 2026-09-22 晚 W4 期间查清

**§10.4 说"实测比 §12.2 的模型低 46%,按那张表的模型这不可能"。这个警报是假的,
错在我的测量方法,不在方案。** 原文保留在上面(计划与事实分开放),这里给结论。

**问题出在收款方地址上。** §10.4 那次用的是 anvil 的默认账户(0x7099…79C8 / 0x3C44…93BC),
这些地址是公开的测试地址,**真 Fuji 上早就有人给它们转过 USDC**。fork 出来时余额非零,
于是 USDC 的余额槽是**非零→非零**的 SSTORE,只要 2,900 gas。

而 W2 的 `Gas.t.sol` 用的是全新空账户,槽位是**零→非零**,要 20,000 gas。

W4 期间做了个对照实验,只改这一个变量,其他全一样:

| 收款方余额槽 | `pay()` 3 方 70/20/10 gasUsed |
|---|---|
| 零槽位(从没拿过 USDC 的地址) | **163,185**(跑两次,完全相同) |
| 非零槽位(anvil 默认账户) | **128,985** |

差 **34,200 = 2 × 17,100**,而 17,100 = `20,000 − 2,900` —— 正是 EVM 这两个 SSTORE
价差,**一个字节都不多**。变量就此锁定。

**这同时解释了 §10.4 里那三个"互相矛盾"的数:**

| §10.4 记的数 | 真实成因 |
|---|---|
| 2 方首笔 131,044 | 协作者是**零槽位** → 113,944 + 17,100 |
| 2 方后续 113,944 | 两位都是非零槽位(最便宜的一档) |
| 3 方 128,985 | 三位都是非零槽位 —— **和本次对照实验复现的 128,985 完全相同** |

也就是说 §10.4 那三个数**是在两个不同的槽位制度下量出来的**,放在一张表里比,
当然推不出自洽的模型。不是方案的问题,是我把苹果和橘子放一起了。

**对 §12.2 的结论(修正 §10.4 的建议,方向不变、理由要换):**

1. **模型是对的。** 零槽位(即"收款方第一次收到 USDC",也就是真实世界最常见的情形)
   实测 **163,185**,而 W2 用 MockUSDC 量到 159,261 —— 真实 USDC 贵约 3,924,
   **方向与 §12.2 说的一致**(替身没有代理转发、不发 `Transfer` 事件、不读黑名单)。
2. **250,000 保留**,理由比 §10.4 写的更强:实测 163,185 在它下面,且有足够余量。
3. ⚠️ **§12.2 里"每方 +26,500"这个修正系数需要重新推导。** 它是拿一笔独立的
   真实 USDC 转账(76,277)去减替身转账(28,752)得来的,而**那笔独立转账的收款方
   也是零槽位**,所以 47,525 的差额里有 17,100 是槽位效应、不是"真实 vs 替身"的效应。
   这个系数本文不动,留 §12.2 的收尾项①在真链上重推。
4. **本文所有 gas 数字的适用范围要说清楚:都是 fork 实测,不是真链。** 但 gas 是确定性的,
   槽位价差这种量级的东西不会因链而异 —— 真正需要真链确认的是 §12.2 收尾项②(延迟),
   那个才是时间相关的。
