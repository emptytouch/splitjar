### 0.1 ⚠️ 方案 §9.1「上传经 Function 中转」在 >4.5 MB 时直接 413

Vercel Function 的**请求体上限是 4.5 MB**(Serverless / Node 运行时;Edge 只有 1 MB)。
超了会在 handler 代码执行**之前**就被拒掉,返回 `413 FUNCTION_PAYLOAD_TOO_LARGE`。

「内容文件」没有尺寸约束 —— 一个 PDF、一段视频随便就超。所以 §9.1 的字面设计
**只对小文件成立**。

> **但这条不推翻它的意图,只推翻它的实现。** §9.1 写「上传经 Function 中转」的理由是
> 「**避免把写入凭证暴露给前端**」。而 Vercel 官方的**客户端直传**模式同样满足这一条:
> 服务端用 `handleUpload` 签发一个**受限 token**(限定 pathname、限定 `put` 操作、
> 限定有效期),浏览器拿它直传 Blob。**读写成凭证始终不进前端。**
>
> 所以:意图保留,实现换成客户端直传。详见 §四。

### 0.2 ✅ 方案 §9.1 要的「内容私有 + 预览图公开」,**一个 store 装不下**(已实测)

> **📌 这一节来回改过两次,最终由实验定案。** 过程见 §0.2.1 —— 两次都是
> "从代码推",两次结论相反,而**只有实验算数**。别跳过 §0.2.1,那里有一条
> 比结论更值钱的方法论教训。

§9.1 要求内容文件走**私有** Blob、预览图走**公开** Blob。**访问模式是 store 级的,
由平台强制。一个 store 装不下两种。**

**实测(2026-09-23,真 store):**

| | 操作 | 结果 |
|---|---|---|
| 实验组 | 私有 store 里 `put --access public` | ❌ `Cannot use public access on a private store. The store is configured with private access.` |
| 对照组 | 私有 store 里 `put --access private` | ✅ Success → `...ijzyjopokzxxbts8.**private**.blob.vercel-storage.com/...` |

**两条一起看才算数**:报错是明确的模式冲突,不是"什么都干不了";
对照组证明 store 本身是好的,URL 主机名里那个 `private` 就是 store 的模式。

**为什么读 SDK 会被带偏**(两次都栽在这):`access` 确实是个每次调用都要传的**必填参数**
(`constructBlobUrl(storeId, pathname, access)`),看上去像逐文件选择。
**但它的作用是让客户端拼对主机名** —— store 的模式才是权威,而且**服务端会强制**。
SDK 展示的是"客户端发出去什么",不是"服务端允许什么"。**这两件事不是一回事。**

→ **结论:决策 A 成立,必须开两个 store。** §1.1 的比较有效,且"结构性安全"的论据
**比原先写的更强**:不是"我们约定内容只放私有 store",而是
**平台会拒绝把内容标成 public** —— 刚刚亲眼看到它拒绝。

#### 0.2.1 两次都错了:完整记录与方法论

**第一次(错法:把推断写成结论)**

原文写的是「访问模式是 store 级、创建时固定」,结论**碰巧对了**,但依据是:
「类型定义里 URL 模板是 `$storeId.**public**.blob.vercel-storage.com` ——
访问模式嵌在主机名里,所以它不可能是逐文件属性」。
一个看起来确定的结论,底下是一条**没标注"待验证"的推断**。

**第二次(错法:用更严谨的推理,得出相反的错结论)**

我去读**实现**(不是类型),看到:

```js
// chunk-YYMLUMXS.js:338
function constructBlobUrl(storeId, pathname, access) {
  return `https://${storeId}.${access}.blob.vercel-storage.com/${pathname}`;
}
```

于是判定:模板里那个 `public` 是 `${access}`,是**变量**;
`parseStoreIdFromDelegationToken()` 的 payload 里**只有 `storeId`、没有 `access`**;
`access` 还是 required —— 「**如果访问模式真是 store 级,SDK 没有理由让调用方每次显式传它**」。
据此把结论**反转**成"逐文件",还写了 §0.2.1 记录第一次错在哪。

**两次的毛病是同一个:都是在读代码,不是在测量。**
第二次读得更深、推理更漂亮,结论**反而更错** —— 因为它仍然只看到客户端,
没看到服务端。**"推理更严谨"不等于"更接近事实"。**

**⚠️ 而且第二次差点被我当成"已实测"记下来 —— 差点栽在一场假阳性上:**

第一次跑实验时,私有 store + public 报的是
`Access denied, please provide a valid token for this resource.`
—— 这**看起来正是**我预言的 `BlobAccessError`。我几乎就写下了"逐文件被推翻"。

**是"顺手跑的对照组"救了它**:对照组(私有 store + private)**报了完全一样的错**,
连 `list` 都失败。同一个报错说明**根本不是模式问题,是凭证没通过**
(store 建了但没连到项目)。建了连接、重跑之后,才拿到上面那个明确得多的
`Cannot use public access on a private store`。

**教训两条**:

1. **读代码得到的是"假设",不是"证据"** —— 只有真跑一遍才是证据。
   §11.7.1(`WithdrawFailed`)是同一类错:当时也是"我确信合约会返回 false"。
2. **任何声称"验证了 X"的实验,必须同时跑一个"应该成功"的对照组。**
   只跑预期失败的那一半,"因为凭证错而失败"和"因为规则禁止而失败"长得一模一样。
   → 这和我自己驱动脚本里那三条假阳性断言是同一个坑
   (`W4-实施计划.md` §11.7):**没有对照组的断言,是在给未知盖章。**

### 0.3 ✅ `@vercel/kv` 废弃,但 **`env.ts` 里那两个名字不用改**

`@vercel/kv` **已于 2024-12 废弃**,KV 已并入 **Upstash Redis(Vercel Marketplace 集成)**。
新项目该用 `@upstash/redis`。

**原以为的待办是"改名"(`KV_REST_API_*` → `UPSTASH_REDIS_REST_*`)。查完发现不用改**
—— `@upstash/redis` **1.39.0** 的 `Redis.fromEnv()` 实现里写得很清楚:

```js
// nodejs.js:6327
const url   = process.env.UPSTASH_REDIS_REST_URL   || process.env.KV_REST_API_URL;
const token = process.env.UPSTASH_REDIS_REST_TOKEN || process.env.KV_REST_API_TOKEN;
```

**两套名字都认**,`UPSTASH_*` 优先,`KV_REST_API_*` 作为回退。这条回退不是巧合
—— Vercel Marketplace 的 Upstash 集成**注入的恰恰是 `KV_REST_API_*`**(保留
`@vercel/kv` 时代的兼容名),SDK 是为了让两条路都能用才这么写的。

→ **所以:保留 `env.ts` 里现有的 `KV_REST_API_URL` / `KV_REST_API_TOKEN` 即可,
`fromEnv()` 直接就能跑。** 三个工作流(nonce W5、限额 W6、防重放 W8)都不用改。

> **诚实标注**:「集成注入的是 `KV_REST_API_*`」这一条来自搜索摘要(Vercel 站被网络策略挡,
> 读不到一手文档);但 **`fromEnv()` 两套都认** 这条是**一手代码证据**,独立成立。
> 也就是说:**即使注入的名字猜错了,代码照样能跑** —— 这条结论不依赖那个猜测。

### 1.1 决策 A 的展开:为什么从 ② 改成 ①

> ✅ **本节有效。** 前提("预览图必须另找一个公开的落脚点")已由实测确认(§0.2)。
> ① = 两个 store,② = 单私有 store + 公开代理路由。
> **① 已被采纳**;② 的做法留在本节末尾,作为第二份 token 落不了地时的退路(§9.4)。

**⚠️ 这一条颠倒了。** 2026-09-23 起初倾向 ②(单 store + 公开代理路由,理由是"少一个
store、少一份凭证"),把 ② 的处理步骤逐条写完之后改判 ①。**改判过程记在这里,
因为"当时怎么算的"比结论本身更该留住。**

#### ① 的代价 vs ② 的代价

| | ① 两个 store | ② 单 store + 公开代理路由 |
|---|---|---|
| 建 store | 2 个 | 1 个 |
| 凭证 | 2 份 token | 1 份 |
| `env.ts` | 多 1 行 | — |
| 新增公开端点 | **无** | **1 个能读到私有 store 的公开路由** |
| 预览图延迟 | Blob CDN 直出,**不过 Function** | 过一次 Function(有冷启动) |
| 运行成本 | 0 | 每次未命中缓存 = 一次 Function 调用 |
| 私有内容可达性 | **除 `/api/unlock` 外没有任何 HTTP 路由够得着**;且**"把它标成 public"这件事平台会拒绝**(实测,§0.2) | 取决于那段代码永远写对 |

**结论:②省的是一份凭证,买的是"付费墙靠代码正确性维持"。**
而 §17.3 把门禁列为红线 —— 砍了产品就是空壳。这个交换不划算。

**⚠️ 而且实测把 ① 的优势又拉大了一档**:§0.2 那个实验证明了 private store 会
**主动拒绝** `access: 'public'`。也就是说,**"内容被误标成公开"这个最坏形态不是
"我们约定不这么做",而是平台层面做不到** —— 写错代码也漏不出去。
这是 ② 无论如何给不了的(代理路由的越权读取,平台不管,只能靠代码)。

#### ⚠️ ② 的失败模式是静默的,这才是改判的真正理由

如果那个公开路由**任何地方**从客户端输入推导 pathname(`?path=`、`[...path]` catch-all),
有人请求 `content/<id>` 就**通过公开端点下载到了付费内容**。

恶劣的地方在于:**所有测试照样全绿** —— 正常的预览请求完全正常,只有越权请求不一样。
它在"已经输了"之后才看得出来。

> **另一条诚实边界**:`contentId` 是写进链上 `ContentRegistered` 事件的,
> **所以任何读链的人都能枚举全部 contentId**,也就等于能看全部预览图。
> 这没问题(预览图本来就公开),但它正是"预览路由绝不能同时够得着付费内容"的理由。

#### ① 引入的新失败模式(实测后:比原先写的更轻,而且**最坏方向不可能发生**)

上传路由必须**按资产类型选对 token**:预览图用公开 store 的 token,内容用私有 store 的。

原以为用错会**静默 404**。**实测否掉了这个担忧** —— 平台会直接拒绝:

| 写错的方向 | 实测结果 |
|---|---|
| 公开的东西写进**私有** store | ❌ 报错 `Cannot use public access on a private store.` —— **上传当场失败**,不会静默 |
| **私有内容**写进**公开** store | 同理拒绝(同一机制,`access` 与 store 配置必须一致) |

两个方向都是**上传时就报错**,不是"写进去了但读不到"。
而且**最坏的那个方向(付费内容被标成 public)在平台层面做不到** ——
不是"我们约定不这么写",是这条路径不存在。

→ 所以 ① 的风险敞口就是"上传报错、当场发现",而不是"付费墙悄悄没了"。

#### ② 的完整做法(留档,万一 ① 在 Hobby 上撞限制)

路由 `api/preview/[contentId].ts`(`vercel.json` 的 rewrite 是 `/((?!api/).*)`,
已排除 `/api/*`,能正确命中)。处理步骤:

1. **校验 `contentId`** —— 必须匹配 `^0x[0-9a-f]{64}$`,否则 400。
   **把它当标识符,永远不当路径片段。**
2. **服务端查映射** —— KV 把 `contentId` 换成 pathname。查不到 → 404。
   **客户端只提供 id,不提供 pathname。**
3. **前缀硬断言** —— 查出的 pathname 必须以 `preview/` 开头。不满足 → 500
   (映射被写坏了,不是用户的错)。
4. **取流** —— `get(pathname, { access: 'private' })`。`access` 在这里**必填**。
   返回 `null` → 404。
5. **回响应** —— `Content-Type` 取 `blob.contentType`
   (**不设的话浏览器拿到 `application/octet-stream`,图不显示**)、
   `Content-Length` 取 `blob.size`、`ETag` 取 `blob.etag`,body **流式转发**
   (`get` 返回的就是 `ReadableStream`,不自动缓冲,不吃内存)。
6. **条件请求** —— `If-None-Match` 命中 etag 回 304
   (Blob 的 `get` 本身返回 `statusCode: 304`、`stream: null`,照转)。
7. **只允许 GET/HEAD**,其余 405。
8. **不需要**验签、读链、nonce —— 它本来就公开。

**缓存是 ② 的成本解法**:预览图不可变(contentId 变了就是另一件内容),所以给长缓存,
Function 就不是每次浏览都跑,而是每个边缘节点跑一次:

```
Cache-Control: public, max-age=31536000, immutable
+ 给 CDN 的那条(s-maxage / CDN-Cache-Control)
```

⚠️ Vercel 到底按哪个头缓存 Function 响应,**得实测**。
→ 若最终选 ②,这一条加进 §七 零号验证;选 ① 则不需要。

## 三、存储布局

```
KV / Redis                          ← 决策 D(已定)
  nonce:<nonce>                     ← 一次性 nonce,TTL 5min
  pathname:<contentId>              ← contentId → blob pathname 的映射

Blob(私有 store)                    ← ✅ 决策 A 已定(实测:access 是 store 级,§0.2)
  content/<contentId>               ← 内容文件,**永不可公开读**

Blob(公开 store)                    ← ✅ 配套的第二个 store
  preview/<contentId>               ← 预览图,CDN 直出,不经任何 Function
```

**为什么是两个 store**:`access` 是 **store 级**配置且**平台强制**(实测,§0.2),
所以"私有内容 + 公开预览"在一个 store 里表达不出来。
第二个 store 的凭证命名**尚未落地**,见 §9.4。

> **退路(留档,§1.1 末尾有完整做法)**:若第二个 store 在 Hobby 上落不了地,
> 改成"单私有 store + `api/preview/[contentId].ts` 代理路由"。
> 那样 `preview/` 前缀就要担起"前缀硬断言"的支点作用。

⚠️ `content/` 与 `preview/` 的 pathname 前缀**两个形态下都要保留** —— 它是
`pathname:<contentId>` 映射表里区分"这行指向付费内容还是预览图"的唯一依据。
**别因为落在两 store 形态就把前缀简化掉。**

**⚠️ 为什么 `contentId → pathname` 的映射不能进合约。**

合约里有一个 `contentHash`(`keccak256`),它已经上链、**人人可读**。
诱惑是"顺手把 pathname 也存链上"。不要:

1. **链上数据是永久的公开数据。** 把一个存储位置写进链上,等于把"我们的存储
   长什么样"永久固化。而方案 §9.1 明确留了"时间富余再换 IPFS"的口子 ——
   一旦 pathname 上链,换存储就要动合约、要重新部署。
2. **`contentHash` 本身不泄漏位置**,它是文件内容的哈希,不是定位符。
   这一点要**保持住** —— 它正是"存证"和"门禁"能共用一个字段的原因。

所以:链上只留 `contentHash`(存证),定位信息全在链下(门禁)。

## 五、`/api/unlock` 门禁

```
POST /api/unlock { contentId, buyer, nonce, deadline, signature }
  1. 验 EIP-712 签名(user 的 domain,不是 USDC 的 —— 见 §六)
  2. 断言:恢复出的地址 == buyer 字段
  3. 校验 deadline 未过期
  4. 校验 nonce 存在且未被用过
  5. 读链 purchases[contentId][buyer]   ← 未购买 → 401
  6. 通过 → issueSignedToken + presignUrl,60s
  7. ⚠️ 最后才删 nonce           ← 顺序错了会怎样见 §六
```

**校验发生在服务端 + 链上,不是前端隐藏元素。** 前端隐藏元素可被绕过,不算付费墙
(§9.2 原话)。

**HTTP 语义上要分清两个 401**:「签名不对」和「没买」是两回事。
两者都返回 401 会让排查变得很痛苦(而且会诱导把"签名错"当成"没付款"去查链)。
倾向:签名类问题返回 **400/403**,只有**「链上确认未购买」返回 401**。

### 5.1 ⚠️ 服务端读链是新的信任面

前端读链走的是浏览器里的钱包 RPC;服务端读链走的是**我们配的 RPC**
(`RPC_PRIMARY` / `RPC_BACKUP`)。这意味着:

- **RPC 说谎,门禁就判错。** 对这个演示产品可以接受,但要在文档里说清 ——
  它不是"经过验证的付费墙",是"读一个我们信任的 RPC 的付费墙"。
- 读链要**确认拿到的是当前链上的值**,不能吃 CDN 缓存。这是 `presignUrl` 的
  `cache: false` 选项存在的原因(见 §六末尾)。

## 六、EIP-712 与 nonce:两处必须严格对齐的地方

签名方案已于 9/21 定稿(§9.2),**W5 是第一次真正落地它**,所以对齐点要写死:

```
domain: { name: "SplitJar", version: "1", chainId: 43113,
          verifyingContract: <已部署的 CreatorSplitter> }
types:  Unlock { contentId: bytes32, buyer: address,
                 nonce: uint256, deadline: uint256 }
```

- ✅ **`contentId` 天然对齐**:合约里它就是**前端随机生成的 `bytes32`**
  (`contracts/src/CreatorSplitter.sol`),不是 uint256、不需要转换。
  这条省掉了一个本来很容易踩的转换坑。
- ⚠️ **`verifyingContract` 填已部署的 `CreatorSplitter`,不是 `0x0`** ——
  把证明绑死在本应用上。
- ⚠️ **两套 EIP-712 domain 会同时存在**:①USDC 的(Circle 定义,Agent 路径用)
  ②我们的(SplitJar)。**用错 domain 的症状是"签名永远验不过",报错很隐晦。**
  前端签名侧与服务端验签侧必须引用**同一个** domain 常量 —— 这正是它该放进
  `shared/` 的理由(两端共用,单一事实来源)。

### 6.1 ⚠️ nonce 的删除顺序(§9.2 已经写下的教训)

> 「**先删再干活,后面失败用户就得重新签名。**」

所以顺序是:**验签 → 校验 nonce → 读链 → 全部通过 → 才删 nonce**。
任何一步失败都不应消耗掉 nonce —— 否则用户要为一次 RPC 抖动重新签一次名。

**这个 nonce 防的是"证明被转移",不是保护资金** —— 解锁证明不授权任何链上操作。
这个边界要说清,免得把它包装成一个它做不到的安全承诺。

#### 4.2 🔴 这就是阻塞:**`handleUpload` 用不了 OIDC**

读 `@vercel/blob` 2.8.0 的 `client.d.ts:332` —— `HandleUploadOptions` 的全部字段是:

```ts
interface HandleUploadOptions {
  body: HandleUploadBody;
  onBeforeGenerateToken: (...) => Promise<...>;
  onUploadCompleted?: (body: UploadCompletedEvent['payload']) => Promise<void>;
  token?: string;      // ← 只有这一种鉴权
  request: RequestType;
}
```

**没有 `storeId`,没有 `oidcToken`。** 文档原话:

> `token` — A string specifying the **read-write token** to use when making requests.
> Defaults to `process.env.BLOB_READ_WRITE_TOKEN`.

而决策 B(客户端直传)**正是走 `handleUpload`** —— 也就是说
**预览图的上传签不了名**,因为手上没有公开 store 的 read-write token。

> 对比:`put` / `get` / `list` 等**都**支持 `storeId` + `oidcToken`(`index.d.ts:319-321`)。
> **唯独 `handleUpload` 不支持** —— 而这恰好是我们要用的那个。
> 另一条路是 `handleUploadPresigned` + `issueSignedToken({storeId, oidcToken})`,
> 它能用 OIDC,但那是**第二套上传 API**(presigned 流程,且带 `@deprecated` 标记的迁移痕迹)
> → 意味着私有/公开两条上传路径要写两遍。**不划算。**

**⚠️ 顺带记一个陷阱**(私有 store 也有风险):
`token` 在 **「OIDC 可用 且 设了 `storeId`」** 时会被**静默忽略**
(`index.d.ts:319`:"Ignored when Vercel OIDC token is available and either
`process.env.BLOB_STORE_ID` or `options.storeId` is set")。
现在私有 store 只传 `token`、不传 `storeId`,所以安全 ——
**但哪天有人往项目里加了个 `BLOB_STORE_ID`,私有 store 的 token 就会被无视,
静默地去打公开 store。** 这条要写进 W5 的代码注释。

#### 4.3 ✅ 为什么控制台**没有**那个入口:`vercel api` 给出的证据

**不是操作问题 —— 那条路不存在。** 用 `vercel api /storage/stores/{id}` 读两个 store
的连接元数据,差别一目了然:

| | `envVarPrefix` | `environmentVariables` | `isTokenExpired` |
|---|---|---|---|
| `splitjar`(CLI 建) | `BLOB` | `["BLOB_READ_WRITE_TOKEN"]` | `false` |
| `splitjar-public`(控制台连) | `PUBLIC_` | `["PUBLIC_STORE_ID", "PUBLIC_WEBHOOK_PUBLIC_KEY"]` | `true` |

**两种连接方式给的变量集不一样**:
CLI 连接 = **token 方式**,注入 read-write token;
控制台连接 = **OIDC 方式**,注入 `STORE_ID` + `WEBHOOK_PUBLIC_KEY`
—— **它的变量清单里根本没有 read-write token 这一项**。
所以控制台里找不到"补一份 token"的按钮,是设计如此。

#### 4.4 ✅ 替代做法:**按环境**绕开碰撞(已端到端实测)

`vercel blob create-store --debug` 暴露了它的内部两步:

```
POST https://api.vercel.com/v1/storage/stores/blob                       ← 建库
POST https://api.vercel.com/v1/storage/stores/{storeId}/connections     ← 注入 token(碰撞发生在这里)
GET  https://api.vercel.com/v3/env/pull/{projectId}/{environment}?source=vercel-cli:blob:store-add
```

**关键洞察:碰撞是「按环境」判断的。** 私有 store 的 token 只在
production + preview,所以 **`--environment development` 不撞**。

**实测(用一次性 store `probe-throwaway` 跑通,随后已删除):**

1. `vercel blob create-store <name> --access public --yes --environment development`
   → `Success!` + `+ BLOB_READ_WRITE_TOKEN (Updated)`
2. `vercel env pull` 后看那个值 → 格式是 **`vercel_blob_rw_…`**(长期静态 token)
3. 用它 `vercel blob put --access public --rw-token <值>` → **`Success!`**
   → 证明抠出来的确实是可用的 read-write token

**⚠️ 顺带一个坑**:`vercel blob empty-store` / `delete-store` 也会撞
`VERCEL_OIDC_TOKEN and BLOB_STORE_ID must both be set, or both be unset`
—— 必须显式带 `--rw-token`。

#### 4.5 三条路 → **已选甲并执行**(2026-09-23)

| | 做法 | 评价 |
|---|---|---|
| **甲** | 用 §4.4 验证过的手法:把 `splitjar-public` 连到 **development**(不撞)抠出 token,再 `vercel env add PUBLIC__READ_WRITE_TOKEN` 到 production/preview/development,最后**移除** development 上那个通用名 | ✅ **推荐**。机制已端到端实测;**两条上传路径共用同一套 `handleUpload` 代码**;长期凭证,本地开发可靠。代价:动一次你的 Vercel 环境变量(**可回滚**),且这份 token 是手工加的,连接若重做会静默失效 |
| **乙** | **完全不碰平台**:改用 `handleUploadPresigned` + `issueSignedToken({storeId, oidcToken})` 走 OIDC | 零平台改动,且是 Vercel 现在的推荐方向。代价:**换一套上传 API**(`handleUploadPresigned` 还带 `@deprecated` 迁移痕迹,未经我们验证)→ 实现风险高;本地开发每次都要 `vercel env pull` 拿 12 小时有效的 OIDC token |
| **丙** | 放弃两个 store,走 §1.1 的代理路由 | **唯一不需要任何凭证工作的路**。代价见 §1.1:最坏情况从"上传报错"变成"静默越权读取" |

**推荐甲。** 理由不是"省事",而是**甲只有一套上传代码,乙有两套**;
而这个项目的规矩是"必须实测,不能靠推理" —— 甲的手法刚刚实测过,乙的 API 没有。

**✅ 已选甲并执行完毕(2026-09-23)。** 实际步骤:

```bash
# 1. 连到 development —— 那里没有碰撞(私有 store 只在 prod+preview)
vercel blob create-store splitjar-public --access public --yes --environment development
#    → 注入 BLOB_READ_WRITE_TOKEN 到 Development

# 2. 抠出真值(development 那份是非敏感的,能拉)
vercel env pull .env.local --environment development
#    → PUBLIC__READ_WRITE_TOKEN 的值:vercel_blob_rw_… (len 62)

# 3. 用我们自己的名字加到三个环境
for e in production preview development; do
  vercel env add PUBLIC__READ_WRITE_TOKEN $e --no-sensitive
done

# 4. 移除 development 上那个通用名 —— 否则 dev 指向公开 store、prod 指向私有 store,错位
vercel env rm BLOB_READ_WRITE_TOKEN development --yes
```

**⚠️ 前置条件:旧 store 必须先删。** 同名 store 会 `409`:
`A blob store named "splitjar-public" already exists.` 所以流程是
**删旧 store → 重建 → 抠 token**(旧的是空的,0 blob,删除无数据损失)。

#### 4.6 ⚠️ 执行中踩到的两个坑(都会重犯,记下来)

**坑一:`vercel env ls` 显示的"值"是假的。**

它给每条变量显示的都是 `eyJ2IjoidjIiLCJjIj…`,**包括刚加进去、真值是
`vercel_blob_rw_…` 的那条**。一度让人以为"加错了值"。
**只有 `vercel env pull` 出来的是真值。** 要核对值,别用 `env ls`。

**坑二:`vercel env add` 默认把 Production/Preview 标成 Sensitive,而 Sensitive 拉不下来。**

`env pull` 拿到的会是占位符 `[SENSITIVE]` → **本地开发直接废掉**。
加 `--no-sensitive` 才能拉。验证方式:

```bash
vercel env pull .env.local --environment production
grep PUBLIC__READ_WRITE_TOKEN .env.local   # 必须是 vercel_blob_rw_…,不能是 [SENSITIVE]
```

> 这也解释了本地踩过的那个怪错:
> `VERCEL_OIDC_TOKEN and BLOB_STORE_ID must both be set, or both be unset`
> —— `vercel env pull` 拉下来 `VERCEL_OIDC_TOKEN` 却没拉 `BLOB_STORE_ID`,两个不配对。

#### 4.7 记录:碰撞的不止一个变量

Vercel 连接一个 store 会注入**多个**名字固定的变量,**都会撞**:
`BLOB_READ_WRITE_TOKEN`、`BLOB_STORE_ID`(配合运行时 `VERCEL_OIDC_TOKEN` 做鉴权)、
`BLOB_WEBHOOK_PUBLIC_KEY`。**所以要么整组换名,要么整组不碰。**

**已经确认不存在的解法(2026-09-23 实测):**

- **控制台补 token** —— 见 §4.3,那条路在设计上就不存在(变量清单是封闭的两项)。
- `vercel blob create-store --help` **没有**自定义变量名/前缀的参数 —— 只有
  `--access` / `--environment` / `--region` / `--yes`。**"CLI 加个 flag"这条路堵死。**
- **给已连接的 store 补一条 dev 连接** —— `POST /v1/storage/stores/{id}/connections`
  一律返回 `This project is already connected to the target store in one of the
  chosen environments`,换什么字段名都一样;而且**删掉 `PUBLIC__STORE_ID` 也不放行**
  (连接记录与变量彼此独立)。所以只能删 store 重建。

**为什么两份 token 都需要**(不是重复):私有 store 要它来①签直传 token
②在 `/api/unlock` 里读;公开 store 要它来签预览图的直传 token。公开读走 CDN,不需要凭证。

### 5. ⚠️ 「未付款 → 401」实际是 **402 `not_purchased`**(2026-09-25 实测追加)

**WBS 原文写的是 401** —— 见本文件上面「三条验收」与「反例」两处,
`docs/开发计划.md` §W5 与 `splitjar-product-spec.md` §16.1 也照抄了 401。
**线上实测不是 401。** 用一个**零余额的一次性地址**签一份格式完全合法的 unlock
消息打生产环境,逐条对比(**只签名,不发交易,不消耗任何人的凭证**):

| 用例 | 文档期望 | 实测 |
|---|---|---|
| 签名篡改一位 | 401 | ✅ `401 bad_signature` |
| `deadline` 已过期 | 401 | ✅ `401 deadline_expired` |
| 合法签名 + 链上确实**没买** | **401** | ⚠️ **`402 not_purchased`** |
| 空 body / 畸形 JSON | 400 | ✅ `400 bad_request` |

**这个 402 是故意的,不是漏改。** 两处判据:
- `api/unlock.ts` 里"链上没买"那支显式返回 402,并且与 `503 upstream_unavailable`
  (RPC 读不到)分开 —— 注释写明「这里**绝不能**写成 `paid = false`。RPC 读不到 ≠ 没买」。
- `shared/api.ts:66` 明确写着「⚠️ 与 `not_purchased` 的 402 **不是一回事,别合并**」——
  401 留给**验签 / 时效 / nonce** 三类「你这个请求本身不成立」,
  402 留给**「请求成立,但该付钱」**。语义上 `402 Payment Required` 更准。

**结论:保留 402,改文档。**(2026-09-25 用户拍板)

⚠️ **验收的意图仍然达成** —— 上表第三行证明确实是**链**在把关(签名完全合法、
但链上说没买 ⇒ 拒),付费墙不是前端障眼法。**只是状态码与 spec 字面不符**,
所以评委若照 `spec §16.1` 打这一条,会看到 **402 而不是 401**。
需要在 §16.1 那条上追加一句更正(按本项目规矩**追加、不覆盖**)。
⚠️ 本文件上面两处原文**保持原样留档**,不要就地改写。

**顺带澄清一条容易被误判成漏洞的**:同一个 nonce 在**成功之前可以重复使用**。
`api/unlock.ts` 第 ④ 步用的是 `peekNonce`(**看**,不是**用**),
真正的消耗(`consumeNonce`)发生在签发 URL 那一步**之后**。所以"没买的人拿同一个
nonce 打两次、两次都是 402"是**正确行为**:
第 ④ 步的语义是**绑定**(这个 nonce 是不是发给这份内容的),**不是防重放** ——
防重放由消耗那一步负责。

**证据在哪**:`scripts/verify-unlock.mjs` 的第 6 步(负对照)就是上表第三行。
该脚本现场生成一个**零余额的一次性私钥**,只签名,不花任何钱。
