# W14 实施计划 —— Agent 购买通道(对话框购买 + 授权扫货)

> **2026-09-25 写。** 用户拍板的范围:
> 「用户既可以通过对话框购买,也可以通过授权 agent 去进行购买。
> 只需要告诉 agent 边界,比如价格,比如要买的是什么,购买几条,agent 就可以自主扫货。」
>
> 本文件含**两个包**:包 A = 对话框购买(W14)、包 B = 授权 agent 扫货(W15)。
> 两者是同一个产品面(用 agent 买内容),但**判据、风险、依赖完全不同**,验收分开。

## §〇 前置:三件必须先说清的事

### 0.1 ⚠️⚠️ 本计划要求**放开决策 2 的一个子集 —— 需你签字**

**决策 2 原文**:「私钥不进服务端」(理由:一个网页按钮绝不该能替用户花光他的钱)。

包 B 会让**服务端持有会话密钥**,因此**必然触碰这条线**。区别在于:

| | 前三次被否掉的方案 | 包 B |
|---|---|---|
| 服务端拿到什么 | **用户主私钥** | **会话密钥** |
| 能动多少钱 | **全部** | **额度封顶** |
| 能买什么 | **任意** | **白名单内** |
| 有效多久 | **永久** | **到期即废** |
| 用户能否撤销 | ❌ | ✅ 一键 |

**并且关键的一点:约束不由我们的代码保证,由链上账户合约强制** ——
即使我们的服务端被攻破或被我们自己写错,越界操作会被**链上 revert**。
这不是"我们承诺不越界",是"我们越界了链上不认"。

> (agent 跑在用户本地,不碰决策 2,但用户要装东西)。

## §一 两件事分别是什么

| | 包 A · 对话框购买 | 包 B · 授权扫货 |
|---|---|---|
| 用户说什么 | 「买苹果图」 | 「0.5 以下的图,最多买 3 张,今天之内」 |
| agent 做什么 | **找**,然后**用户自己确认付** | **找 + 买**,全程无人 |
| 钱包弹几次 | **1 次** | **0 次**(授权时 1 次) |
| 钱从谁的地址出 | 用户 | 用户(**同一个地址**) |
| 新基建 | **零** | **智能账户 + 会话密钥 + bundler** |
| 依赖 | 无 | ⚠️ 见 §四.0 spike |

**两件事的关系**:包 A 是"把找的过程变成对话",
包 B 是"把付的过程也交出去"。**包 A 不依赖包 B,包 B 依赖包 A 的搜索能力。**

| 已有 | 复用方式 |
|---|---|

## §三 包 A · 对话框购买 + 商品卡(W14)

### 3.1 位置与形态

放在 `/explore`(W13 建)顶部的对话框。**不新开页面** ——
"逛"和"问"是同一件事的两种入口,分开两个页面会让用户不知道去哪。

```
┌─ /explore ────────────────────────────────┐
│  ┌─ 想找什么?例如「0.5 以下的图」────────┐ │
│  └────────────────────────────────────────┘ │
│  ┌─ agent ────────────────────────────────┐ │
│  │ 找到 2 件符合「图」的内容:              │ │
│  │  ┌────────┐  ┌────────┐                │ │
│  │  │[预览图]│  │[预览图]│  ← 商品卡       │ │
│  │  │苹果图  │  │newTest │                │ │
│  │  │0.2 USDC│  │0.1 USDC│                │ │
│  │  └────────┘  └────────┘                │ │
│  └────────────────────────────────────────┘ │
└────────────────────────────────────────────┘
```

**点卡片 ⇒ 走现有付费流程**(`/p/:id` 或就地弹窗),
**agent 不参与付款**。这是包 A 与包 B 的分界线。

### 3.2 ⭐ 意图解析:建议用 LLM,但必须有降级

「0.5 以下的图」用规则匹配能做,但"图"和"0.5 以下"要各写一套,脆弱且越写越多。

**建议:一个 LLM 调用做意图解析,输出结构化查询。**

```
输入:「0.5 以下的图」
输出:{ keyword: "图", maxPrice: 500000, limit: null }
```

- ⚠️ **服务端只做解析,不碰任何私钥** ⇒ **不涉及决策 2**
- ⚠️ 新依赖:`ANTHROPIC_API_KEY` 服务端环境变量 + 每次调用的成本与延迟
- ⭐ **降级路径(必须有)**:没配 key / 调用失败 / 解析不出来
  ⇒ **退化成普通搜索框**(关键词匹配标题 + 价格区间控件)。
  **对话框消失,但搜索仍然可用** —— 不许因为 LLM 挂了就不能找东西

⚠️ **不要写成"我实现了一个 agent"** —— 它是一次意图解析,
不是自主决策。文案上要如实(见 §七.5)。

### 3.3 工作项

1. `/explore` 加对话框组件(输入 + 消息流 + 结果区)
2. `api/parse-intent.ts` —— LLM 解析,输出结构化查询(带降级)
3. 前端筛选器(关键词匹配 title / 价格区间 / 数量上限)
4. 复用 `/explore` 的卡片组件渲染结果
5. 点卡片 → 现有付费流程(**不改**)
6. 降级路径 + 空结果文案

### 3.4 判据

- [ ] 说「买苹果图」⇒ 出苹果图的卡片
- [ ] 说「0.5 以下的」⇒ 只出价格 ≤ 0.5 USDC 的
- [ ] **拔掉 `ANTHROPIC_API_KEY`** ⇒ 退化成搜索框,仍能搜到内容(不白屏)
- [ ] 点卡片 ⇒ 付款流程与从广场点进去**完全一致**
- [ ] 链上 0 件内容时:明确说"还没有内容",不是空列表

## §四 包 B · 授权 agent 扫货(W15)

### 4.0 ⚠️ 第 0 步是 spike,不是实现

**在写任何产品代码之前,先花半天验证这一条链能不能通:**

```
ZeroDev Kernel 智能账户(Fuji)
  → 注册一个 session key,带 rate-limit + contentId 白名单 + validUntil
  → 用 Pimlico bundler 发一个 UserOp
  → UserOp 里调 CreatorSplitter.pay(contentId)
  → 链上成功,且【故意越界一次】(超额/白名单外)确认被 revert
```

**四件事任一不成立,本包方案要重做:**

| 要验的 | 不成立的话 |
|---|---|
| ZeroDev Kernel 在 Fuji 上能部署 | 换 Biconomy Nexus / Safe,或本包取消 |
| Pimlico bundler 能发 Fuji 的 UserOp | 同上。⚠️ 已在文档层面确认支持,但**没实测** |
| session key 策略能在链上拦住越界 | **包 B 的正当性全靠这条** —— 拦不住就不该开决策 2 的口子 |
| `pay()` 能被 UserOp 正常调用 | 合约不改(它不关心调用者是不是 CA),但要实测 |

⚠️ **没有跑通这个 spike 之前,不要开始 §4.2 之后的任何工作。**

### 4.1 授权表单(用户自己设边界)

用户填,不是我们定:

| 字段 | 例子 | 落到哪 |
|---|---|---|
| 关键词 / 类别 | 「图」 | 筛选条件(不直接上链) |
| **单件价格上限** | 0.5 USDC | ⭐ **翻译成 contentId 白名单**(见 4.2) |
| **最多买几件** | 3 | session key 的 rate-limit |
| **总预算** | 2 USDC | **USDC allowance** |
| **有效期** | 24 小时 | session key 的 `validUntil` |

⚠️ **总预算 ≠ 单价上限 × 件数** 时要说清哪个先到算哪个(两个都是硬顶)。

### 4.2 ⭐⭐ 核心:「价格上限」只能翻译,不能直接表达

**这是本包最重要的一个技术判断。**

ZeroDev 有 `ParamOperator.LESS_THAN` 可以约束**调用参数**,
但 `pay(contentId)` **只收 contentId,不收价格** —— 价格是合约自己从存储里读的。
**所以链上没法直接说"价格 ≤ 0.5"。**

翻译:

```
「价格 ≤ 0.5」
  → 授权那一刻,拉 /api/catalog,筛出 price ≤ 500000 的全部 contentId
  → 把这份【contentId 白名单】放进 session key 策略
  → agent 只能买白名单里的 ⇒ 等价于"只买得起 ≤ 0.5 的"
```

**成立的前提**:`price` 注册后**不可变**(合约无改价入口)⇒
白名单里的价格永远是筛的时候那个价格,**不存在"卖家事后抬价"**。
⚠️ 这一点是本方案成立的地基,如果哪天合约支持改价,本方案立刻失效。

⚠️ **代价如实认**:白名单是**授权那一刻的快照**。
之后新发布的内容不在里面 ⇒ **"授权扫货"天然是一次性采购任务,不是长期订阅**。
文案上要这么写,不要暗示"一次授权永久自动买新的"。

### 4.3 四层强制(全部在链上)

| 边界 | 强制者 | 越界后果 |
|---|---|---|
| 总预算 | **USDC 合约**(allowance) | transferFrom 失败 |
| 买哪些 | session key 策略(contentId 白名单) | UserOp 校验失败 |
| 买几件 | session key 策略(rate-limit) | UserOp 校验失败 |
| 有效期 | session key 策略(`validUntil`) | UserOp 校验失败 |

⚠️ **"agent 代码里判断"不算强制,那是自律。**
本包里 agent 代码**也会**判断一遍(为了体验:不发起注定失败的交易),
但**真正的边界是上面四层**。两者都要有,不能只有前者。

### 4.4 执行流

```
用户填表单 → 签一次(approve USDC 总额 + 注册 session key)
   │
   ▼
服务端 agent(持有会话密钥)
   ├─ GET /api/catalog            ← 与人类同一个目录
   ├─ 按表单条件筛(contentId ∈ 白名单 且 未买过)
   ├─ 逐件:pay(contentId) via UserOp
   │     ⚠️ 串行,每件等确认 —— 买 N 件 = N 笔链上交易
   └─ 全部完成 ⇒ 报告:买了几件、花了多少、剩多少
```

⭐ **用用户地址签 ⇒ `purchases` 记用户 ⇒ 用户之后自己在网站上就能下载,不需要 agent 转交。**
这是本方案比"agent 自己钱包买"好的**根本原因**。

### 4.5 撤销

- 一键撤销 session key(链上)+ 清服务端存储
- ⚠️ **页面刷新/关掉浏览器不影响** —— agent 在服务端跑,这是 X 的固有性质
- ⚠️ 撤销后**已花的钱不可退**,只是不能再花

### 4.6 工作项

1. **§4.0 的 spike**(半天,先行)
2. 智能账户接入(连接器 / 升级流程)。⚠️ **EOA 与 CA 地址不同,资产要迁**
3. 授权表单 UI
4. session key 注册 + 策略构造(含 4.2 的翻译层)
5. 服务端 agent 执行器
6. 进度展示 + 完成报告
7. 撤销入口
8. 会话密钥的服务端存储(⚠️ **这是新增的一类秘密**,要进 `server/env.ts` 白名单)

### 4.7 判据

- [ ] 授权「≤0.5 USDC,最多 3 件,24 小时」⇒ agent 只买得起符合条件的
- [ ] ⭐ **故意把 agent 改成买白名单外/超额的** ⇒ **链上 revert**(这条验的是强制力,不是功能)
- [ ] 到期后 session key 失效
- [ ] 撤销后立即不能再花
- [ ] 买完后**用户自己**在网站上能下载(不需要 agent 转交)
- [ ] 买 3 件 = 3 笔 `PaymentSplit` 事件,且都带 `[Agent]` 徽章
- [ ] 超时/失败有明确报告,不是一个转圈

## §六 明确不做

## §七 风险

### 7.1 ⚠️ 最大风险:4337 这条链在 Fuji 上跑不通

已在文档层面确认 Pimlico 支持 Fuji,**但没实测**。
⇒ §4.0 的 spike 就是为这个。**跑不通就停,不要硬上。**

### 7.2 ⚠️ 智能账户地址不同 ⇒ 资产要迁

EOA 和合约账户地址不同。演示可以指定一个钱包,
但"让用户换钱包"是真实门槛,文案上不要说成"无缝"。

### 7.3 ⚠️ 赎回一次性,失败即作废

`payment:<txHash>` **无 TTL、永久**。agent 拿同一个 txHash 重试**会被拒**。
⇒ 下载失败(网络抖动/写盘失败)⇒ **那笔钱废了,得重买**。
agent 执行器必须**第一件事就是把内容存下来**,再报告成功。

### 7.4 ⚠️ 扫货是 N 笔链上交易

买 10 件 = 10 笔,串行等确认,大概几十秒。gas 在 Fuji 便宜,**时间省不掉**。
超时要能续,不能全丢。

### 7.5 ⚠️ 文案不许夸大

包 A **不是"我实现了 agent"**,是一次**意图解析**。
包 B 是**受限委托**,不是"agent 自己决定买什么"。
两处都要如实写 —— 说大了,评委一问就露。

### 9.3 包 A 改版:降级按原因分开 + 问答排成记录(2026-09-26,用户当场拍板两条)

#### 9.3.1 为什么"按原因分开"不是文案洁癖:改版前实测到的事实

改版前的行为是:降级之后**问句框留在屏幕上**,空着、没禁用、占位符照旧邀请你打字。

#### 9.3.2 记录流:做的是"记录",**故意不做成对话气泡**

计划 §3.3 第 1 条写「输入 + **消息流** + 结果区」,本次按此实现;
但**不用气泡样式**,理由写在 `src/components/IntentSearch.tsx` 文件头:

- 气泡的视觉约定是"两个人在说话",而这里**没有第二个人** —— 模型做一次翻译就退场,
  没有第二轮、没有记忆。画成气泡就是在暗示有个 agent 在陪聊。
- 所以每行左侧是一个**陈述动作的标签**(`你` / `解析` / `没能解析` / `没能问上`),
  不是说话人名字。`解析` 是一个动作,不是一个人。
- ⚠️ **计划内部有一处自相矛盾,已按 §3.2 走**:§3.1 那张示意图上框里写着 `agent`,

  (本文档是决策记录,追加不改写),以本节为准。
  探针里加了一条断言钉住这个选择,防人"顺手"改回去。

每次问**追加**一条,问答绑在同一个 `<li>` 里(问与答在结构上就分不开)。
重试也是追加 —— 探针场景 3b 断言重试后记录变成 2 条而第一条没被抹掉。

⚠️ **如实记一处冗余**:解析成功时,记录里那行「解析 关键词「苹果」· ≤ 0.5 USDC」
和下面结果区回显那行「找到 1 件 · 关键词「苹果」· ≤ 0.5 USDC」**说的是同一件事**。
不合并的理由是两者语义不同 —— 记录里那行是**当时模型理解成了什么**(快照,不再变),

### 9.4 换模型厂商:Anthropic → 智谱 GLM(2026-09-26,用户要求)

用户问「可以用其他模型代替么?比如智谱的」⇒ 换。理由有两条,省钱不是主要的:

1. **输入是中文**(「0.5 以下的图」这类句子),国产模型在这上面不差。
2. **拿 key 的摩擦小** —— 国内手机号即可,不用外卡、不用翻墙。
   ⚠️ 但**本机 `vercel dev` 仍然要走 `127.0.0.1:7897`** —— 那是本机出网的唯一机制,
   与用哪家厂商无关。

#### 9.4.1 ⭐ 只改了"厂商相关"的那几个常量 —— 这是当初选**兼容端点**的回报

智谱提供 **Anthropic 兼容端点**:`https://open.bigmodel.cn/api/anthropic/v1/messages`。
它同样用 `x-api-key` 头、同样认 `anthropic-version: 2023-06-01`、消息体字段名一致。

⇒ 换厂商**动到的只有这些**:

| 改动 | 从 | 到 |
|---|---|---|
| 端点常量 | `https://api.anthropic.com/v1/messages` | `https://open.bigmodel.cn/api/anthropic/v1/messages` |
| 模型名 | `claude-sonnet-5` | `glm-5.3` |
| 服务端变量名 | `ANTHROPIC_API_KEY` | `INTENT_LLM_API_KEY` |

**没动的**:请求头两项、请求体那六个字段名、以及 `readToolInput` 里
「从 `content` 数组里按 `type === 'tool_use'` 取块,不认位置」的那段逻辑。

⚠️ 常量名 `ANTHROPIC_VERSION` **保留**了 —— 因为那个 HTTP 头就叫 `anthropic-version`,
它描述的是**线上协议**而不是厂商,兼容端点也认这个值。

⚠️ 另一处**刻意保留的不对称**:变量名走中立名(见 9.4.2),而**模型名写死在代码里**。
理由是两者变动的时机不同 —— 密钥是"每套部署各自一份",必须能配;模型是"我们要它用哪个",
改它应该是一次**被 review 的代码改动**,而不是某天有人在控制台里打错一个字。

#### 9.4.2 变量改名的理由:代价不对称

名字里带厂商 ⇒ **每换一次服务商,就要在 Vercel 上把那个变量删掉重加、再重新部署一遍**;
中立名字则永远不用动。而"用哪家"是会变的,"这里放的是那条端点的模型密钥"不会变。

⚠️ 同理,`shot/probe-intent-search.mjs` 里那个字符串提成了常量 `LLM_KEY_VAR` ——
这次改名时它在三处各写死一份,**靠 `grep` 才找全**。

⚠️ 有一处**必须跟着改、不改就是真 bug**:`src/components/IntentSearch.tsx` 的降级文案
把变量名**写死在给用户看的字符串里**。不改的话,界面会指着一个不存在的变量让人去配。
`probe-intent-search.mjs` 场景 3 有一条断言钉住它。

#### 9.4.3 ⚠️ 换过去之后**没验**的那一件(以及为什么它风险可控)

`tool_choice: {type:'tool', name}` 这种**强制**工具调用,是兼容层最容易打折的地方。
公开资料指出智谱端点在某些工具相关行为上与 Anthropic 标准布局**有差异**
(它自己的服务端搜索工具返回块类型与字段名就和标准不同)。

⇒ **必须实测这一条**,不能靠推断。已知的失败方式:`content` 里没有 `tool_use` 块
⇒ `readToolInput` 返回 `null` ⇒ 回 `unparseable` ⇒ **前端降级成手动筛选**。
试错成本低 —— 但**"成本低"不等于"验过了"**。

⚠️ 而且:**真调模型那一跳仍然一次都没执行过**(本机和换厂商之前的线上都没 key)
—— 与 §9.2.3 记的是**同一条缺口**,换厂商没有让它变小。
拿到 key 之后第一件事就是补这次冒烟,顺序是:① 连通性 → ② **`tool_choice` 是否生效** → ③ 中文解析质量。

`ANTHROPIC_API_KEY` **漏写在 `.env.example` 的 ② 组清单里**(`server/env.ts` 登记了,

2. **模型名 `glm-5.3` 是否存在。** 账务检查很可能排在模型校验**之前**,
   所以"没报模型不存在"**不等于**"模型名对"。充值后第一件事就是看这一条
   —— 若报模型不存在/无权限,改 [api/parse-intent.ts](../api/parse-intent.ts) 里 `INTENT_MODEL` 那一行。

#### 9.4.7 ⚠️ 一处环境事实:`vercel dev` 读 `.env`,**不读** `.env.local`

本次踩到:key 写进 `.env.local` 之后,`/api/health` 里那条仍是 `configured: false`
⇒ 函数进程根本没拿到。**同一个 key 换到 `.env` 立刻就 `configured: true`。**

⇒ 本机要配服务端变量,**写 `.env`**(仓库本来就是这么写的,见 `.env.example` 第一行),
`.env.local` 是 `vercel env pull` 的产物、不是给 `vercel dev` 读的。
⚠️ 两个文件都在 `.gitignore` 的 `.env` / `.env.*` 规则下,都不会入库。

#### 9.5.2 ⭐ 九个模型的实测对比(判据是纪律,不是延迟)

测法:[`../shot/smoke-intent-llm.mjs`](../shot/smoke-intent-llm.mjs)(新增),
六条纪律用例,含「看看有什么」这种**应当四字段全空**的。

| 模型 | 延迟 | 结果 |
|---|---|---|
| **`deepseek-ai/DeepSeek-V4-Flash`** | 0.9~3.4s(偶发 26s) | ✅ **6/6 全对,零编造** ← 选它 |
| `inclusionAI/Ling-mini-2.0` | **0.47~0.89s 极稳** | ❌ 丢关键词(「关于苹果的」丢「苹果」),凭空填 `limit` |
| `zai-org/GLM-5.3` | 8.5~30s | ✅ 准,但超时 |
| `zai-org/GLM-4.5-Air` | 5.8s | ❌ 工具调用被当**文本**吐在 `_broken` 里 |
| `stepfun-ai/Step-3.5-Flash` | 4.5s | ❌ 只回 thinking,没有 `tool_use` |
| `Qwen/Qwen3.5-4B / 9B / 27B` | 9.6 / 15.0 / 27.4s | ⚠️ 内容对,但 `maxPrice` 回成**数字**不是字符串 |

本仓库会正确地判成 `unparseable` 降级(因为 `_broken` ≠ 工具名)。**兜底生效了。**

#### 9.5.3 ⚠️ 超时 6 秒 → 20 秒:这是本次暴露出来的**真正问题**

⭐ **`tool_choice: {type:'tool'}` 强制工具调用,实测生效** —— §9.4.6 记的那条悬案结了:

```
HTTP=200   content 块 = thinking | tool_use   stop_reason = tool_use
input = {"keyword":"苹果","limit":3,"maxPrice":"0.5"}
```

⚠️ **第一个块是 `thinking`,`tool_use` 在第二位。** 硅基流动的兼容层会稳定地先吐
thinking 块 —— 所以 `readToolInput` 那条「**认 `type`,不认行置**」的纪律在这家是
**硬需求**,不是风格偏好。写成 `content[0].input` 会直接烂掉。

**但代价是延迟。** 带 thinking 的模型这一跳实测 **8.5~30 秒**,而超时是 6 秒 ——
症状不是报错,是**功能看起来时灵时不灵**(长问句降级、短问句偶尔成功)。

⇒ `vercel.json` 给这个函数配 `maxDuration: 30`,超时提到 20 秒,留 10 秒给降级路径。
⚠️ **这两个值必须一起看** —— 超时 ≥ `maxDuration` 等于把降级路径删掉。

#### 9.5.4 ⚠️ 推翻我自己:`.env` 挤掉 `.env.local`,不是代理的问题

§9.4.7 那条「`vercel dev` 读 `.env` 不读 `.env.local`」是**对的**,但**不完整**,
而我不完整地理解了它一次:

换硅基流动时先出现 `/api/catalog` 的 `title` **全变 `null`**。我推断是
「我加进 `.env` 的 `HTTPS_PROXY` 让境内请求绕道境外代理」—— **推错了**,
直连 vs 走代理实测 1.7s vs 2.1s,两者都正常。

真因是:**只把 `INTENT_LLM_API_KEY` 放进 `.env`、把 KV/BLOB/HMAC 留在 `.env.local`**
⇒ `vercel dev` 只读 `.env` ⇒ **`KV_REST_API_URL` / `KV_REST_API_TOKEN` 根本没进函数进程**。
判据是本机 `/api/health`:`configured` 从 **1/9** 变成 **6/9**(把六个变量合并进 `.env` 之后)。

⇒ **本机要用的服务端变量必须全部在 `.env` 里**,不能一半在 `.env`、一半在 `.env.local`。
⚠️ 而这个故障**不报错**:`server/kv.ts` 那层是静默降级的,看起来像"数据丢了"。

#### 9.5.5 我在这轮里犯的两个工具错误(如实记)

两条是**同一类**:把自己的测试工具问题当成产品缺陷。

1. **内联中文被 shell 弄坏。** 直撞智谱拿到 `400 {"detail":"There was an error parsing the body"}`,
   我据此说"body 没被当合法 JSON 收下"。真因是 Git Bash 里内联的 `-d '…中文…'`。
2. **同一个坑再踩一次,而且这次差点据此选错模型。** 用 shell 循环里的中文字面量打本机端点,
   模型收到的是「有没有讲逻辑的」而我以为发的是「有没有讲区块链的」⇒ 产出「香蕉」「卡通图」,
   我一度当成 DeepSeek 的质量问题。**是调试日志里模型复述的那句话把它戳穿的。**

⇒ **纪律:从 shell 内联传中文的测试一律不可信。** 中文要么写在脚本文件里(UTF-8),
要么经环境变量传。`smoke-intent-llm.mjs` 的用例现在**写死在文件里**,并留了注释说明原因。
