# W14 实施计划 —— Agent 购买通道(对话框购买 + 授权扫货)

> **2026-09-25 写。** 用户拍板的范围:
> 「用户既可以通过对话框购买,也可以通过授权 agent 去进行购买。
> 只需要告诉 agent 边界,比如价格,比如要买的是什么,购买几条,agent 就可以自主扫货。」
>
> 本文件含**两个包**:包 A = 对话框购买(W14)、包 B = 授权 agent 扫货(W15)。
> 两者是同一个产品面(用 agent 买内容),但**判据、风险、依赖完全不同**,验收分开。

## §〇 前置:三件必须先说清的事

### 0.1 ⚠️⚠️ 本计划要求**放开决策 2 的一个子集 —— 需你签字**

**决策 2 原文**:「私钥不进服务端」(理由:一个网页按钮绝不该能替用户花光他的钱)。

包 B 会让**服务端持有会话密钥**,因此**必然触碰这条线**。区别在于:

| | 前三次被否掉的方案 | 包 B |
|---|---|---|
| 服务端拿到什么 | **用户主私钥** | **会话密钥** |
| 能动多少钱 | **全部** | **额度封顶** |
| 能买什么 | **任意** | **白名单内** |
| 有效多久 | **永久** | **到期即废** |
| 用户能否撤销 | ❌ | ✅ 一键 |

**并且关键的一点:约束不由我们的代码保证,由链上账户合约强制** ——
即使我们的服务端被攻破或被我们自己写错,越界操作会被**链上 revert**。
这不是"我们承诺不越界",是"我们越界了链上不认"。

> ⚠️ **这一条需要你明确同意才能开工。** 不同意 ⇒ 只能走 §六 的 Y 方案
> (agent 跑在用户本地,不碰决策 2,但用户要装东西)。

## §一 两件事分别是什么

| | 包 A · 对话框购买 | 包 B · 授权扫货 |
|---|---|---|
| 用户说什么 | 「买苹果图」 | 「0.5 以下的图,最多买 3 张,今天之内」 |
| agent 做什么 | **找**,然后**用户自己确认付** | **找 + 买**,全程无人 |
| 钱包弹几次 | **1 次** | **0 次**(授权时 1 次) |
| 钱从谁的地址出 | 用户 | 用户(**同一个地址**) |
| 新基建 | **零** | **智能账户 + 会话密钥 + bundler** |
| 依赖 | 无 | ⚠️ 见 §四.0 spike |

**两件事的关系**:包 A 是"把找的过程变成对话",
包 B 是"把付的过程也交出去"。**包 A 不依赖包 B,包 B 依赖包 A 的搜索能力。**

## §二 与已有代码的关系(先摸清再动手)

| 已有 | 复用方式 |
|---|---|
| `GET /api/catalog` | **两个包都吃它**。⚠️ 它**不收任何参数**(`export async function GET()`),搜索/筛选必须在调用方做 |
| `/explore` 商品卡 | 包 A 的卡片**直接复用**(W13 做) |
| `payGate` 预检(8 种) | 包 A 点卡片后走**完全现有**的付费流程,不改 |
| `payMachine` 付费状态机 | 同上 |
| USDC `approve` 机制 | 包 B 的**总预算**就是它,零新基建 |
| `payment:<txHash>` KV | 包 B 的 agent 赎回走这条,⚠️ **无 TTL** ⇒ 赎回失败即作废(见 §七.3) |

⚠️ **`/api/catalog` 没有搜索参数**是两包共同的第一个要解决的问题。
演示量级(链上 2 件)前端筛完全够,**先不加 query 参数** ——
加了就要处理分页、排序、缓存,而收益在 2 件内容上看不出来。

## §三 包 A · 对话框购买 + 商品卡(W14)

### 3.1 位置与形态

放在 `/explore`(W13 建)顶部的对话框。**不新开页面** ——
"逛"和"问"是同一件事的两种入口,分开两个页面会让用户不知道去哪。

```
┌─ /explore ────────────────────────────────┐
│  ┌─ 想找什么?例如「0.5 以下的图」────────┐ │
│  └────────────────────────────────────────┘ │
│  ┌─ agent ────────────────────────────────┐ │
│  │ 找到 2 件符合「图」的内容:              │ │
│  │  ┌────────┐  ┌────────┐                │ │
│  │  │[预览图]│  │[预览图]│  ← 商品卡       │ │
│  │  │苹果图  │  │newTest │                │ │
│  │  │0.2 USDC│  │0.1 USDC│                │ │
│  │  └────────┘  └────────┘                │ │
│  └────────────────────────────────────────┘ │
└────────────────────────────────────────────┘
```

**点卡片 ⇒ 走现有付费流程**(`/p/:id` 或就地弹窗),
**agent 不参与付款**。这是包 A 与包 B 的分界线。

### 3.2 ⭐ 意图解析:建议用 LLM,但必须有降级

「0.5 以下的图」用规则匹配能做,但"图"和"0.5 以下"要各写一套,脆弱且越写越多。

**建议:一个 LLM 调用做意图解析,输出结构化查询。**

```
输入:「0.5 以下的图」
输出:{ keyword: "图", maxPrice: 500000, limit: null }
```

- ⚠️ **服务端只做解析,不碰任何私钥** ⇒ **不涉及决策 2**
- ⚠️ 新依赖:`ANTHROPIC_API_KEY` 服务端环境变量 + 每次调用的成本与延迟
- ⭐ **降级路径(必须有)**:没配 key / 调用失败 / 解析不出来
  ⇒ **退化成普通搜索框**(关键词匹配标题 + 价格区间控件)。
  **对话框消失,但搜索仍然可用** —— 不许因为 LLM 挂了就不能找东西

⚠️ **不要写成"我实现了一个 agent"** —— 它是一次意图解析,
不是自主决策。文案上要如实(见 §七.5)。

### 3.3 工作项

1. `/explore` 加对话框组件(输入 + 消息流 + 结果区)
2. `api/parse-intent.ts` —— LLM 解析,输出结构化查询(带降级)
3. 前端筛选器(关键词匹配 title / 价格区间 / 数量上限)
4. 复用 `/explore` 的卡片组件渲染结果
5. 点卡片 → 现有付费流程(**不改**)
6. 降级路径 + 空结果文案

### 3.4 判据

- [ ] 说「买苹果图」⇒ 出苹果图的卡片
- [ ] 说「0.5 以下的」⇒ 只出价格 ≤ 0.5 USDC 的
- [ ] **拔掉 `ANTHROPIC_API_KEY`** ⇒ 退化成搜索框,仍能搜到内容(不白屏)
- [ ] 点卡片 ⇒ 付款流程与从广场点进去**完全一致**
- [ ] 链上 0 件内容时:明确说"还没有内容",不是空列表

## §四 包 B · 授权 agent 扫货(W15)

### 4.0 ⚠️ 第 0 步是 spike,不是实现

**在写任何产品代码之前,先花半天验证这一条链能不能通:**

```
ZeroDev Kernel 智能账户(Fuji)
  → 注册一个 session key,带 rate-limit + contentId 白名单 + validUntil
  → 用 Pimlico bundler 发一个 UserOp
  → UserOp 里调 CreatorSplitter.pay(contentId)
  → 链上成功,且【故意越界一次】(超额/白名单外)确认被 revert
```

**四件事任一不成立,本包方案要重做:**

| 要验的 | 不成立的话 |
|---|---|
| ZeroDev Kernel 在 Fuji 上能部署 | 换 Biconomy Nexus / Safe,或本包取消 |
| Pimlico bundler 能发 Fuji 的 UserOp | 同上。⚠️ 已在文档层面确认支持,但**没实测** |
| session key 策略能在链上拦住越界 | **包 B 的正当性全靠这条** —— 拦不住就不该开决策 2 的口子 |
| `pay()` 能被 UserOp 正常调用 | 合约不改(它不关心调用者是不是 CA),但要实测 |

⚠️ **没有跑通这个 spike 之前,不要开始 §4.2 之后的任何工作。**

### 4.1 授权表单(用户自己设边界)

用户填,不是我们定:

| 字段 | 例子 | 落到哪 |
|---|---|---|
| 关键词 / 类别 | 「图」 | 筛选条件(不直接上链) |
| **单件价格上限** | 0.5 USDC | ⭐ **翻译成 contentId 白名单**(见 4.2) |
| **最多买几件** | 3 | session key 的 rate-limit |
| **总预算** | 2 USDC | **USDC allowance** |
| **有效期** | 24 小时 | session key 的 `validUntil` |

⚠️ **总预算 ≠ 单价上限 × 件数** 时要说清哪个先到算哪个(两个都是硬顶)。

### 4.2 ⭐⭐ 核心:「价格上限」只能翻译,不能直接表达

**这是本包最重要的一个技术判断。**

ZeroDev 有 `ParamOperator.LESS_THAN` 可以约束**调用参数**,
但 `pay(contentId)` **只收 contentId,不收价格** —— 价格是合约自己从存储里读的。
**所以链上没法直接说"价格 ≤ 0.5"。**

翻译:

```
「价格 ≤ 0.5」
  → 授权那一刻,拉 /api/catalog,筛出 price ≤ 500000 的全部 contentId
  → 把这份【contentId 白名单】放进 session key 策略
  → agent 只能买白名单里的 ⇒ 等价于"只买得起 ≤ 0.5 的"
```

**成立的前提**:`price` 注册后**不可变**(合约无改价入口)⇒
白名单里的价格永远是筛的时候那个价格,**不存在"卖家事后抬价"**。
⚠️ 这一点是本方案成立的地基,如果哪天合约支持改价,本方案立刻失效。

⚠️ **代价如实认**:白名单是**授权那一刻的快照**。
之后新发布的内容不在里面 ⇒ **"授权扫货"天然是一次性采购任务,不是长期订阅**。
文案上要这么写,不要暗示"一次授权永久自动买新的"。

### 4.3 四层强制(全部在链上)

| 边界 | 强制者 | 越界后果 |
|---|---|---|
| 总预算 | **USDC 合约**(allowance) | transferFrom 失败 |
| 买哪些 | session key 策略(contentId 白名单) | UserOp 校验失败 |
| 买几件 | session key 策略(rate-limit) | UserOp 校验失败 |
| 有效期 | session key 策略(`validUntil`) | UserOp 校验失败 |

⚠️ **"agent 代码里判断"不算强制,那是自律。**
本包里 agent 代码**也会**判断一遍(为了体验:不发起注定失败的交易),
但**真正的边界是上面四层**。两者都要有,不能只有前者。

### 4.4 执行流

```
用户填表单 → 签一次(approve USDC 总额 + 注册 session key)
   │
   ▼
服务端 agent(持有会话密钥)
   ├─ GET /api/catalog            ← 与人类同一个目录
   ├─ 按表单条件筛(contentId ∈ 白名单 且 未买过)
   ├─ 逐件:pay(contentId) via UserOp
   │     ⚠️ 串行,每件等确认 —— 买 N 件 = N 笔链上交易
   └─ 全部完成 ⇒ 报告:买了几件、花了多少、剩多少
```

⭐ **用用户地址签 ⇒ `purchases` 记用户 ⇒ 用户之后自己在网站上就能下载,不需要 agent 转交。**
这是本方案比"agent 自己钱包买"好的**根本原因**。

### 4.5 撤销

- 一键撤销 session key(链上)+ 清服务端存储
- ⚠️ **页面刷新/关掉浏览器不影响** —— agent 在服务端跑,这是 X 的固有性质
- ⚠️ 撤销后**已花的钱不可退**,只是不能再花

### 4.6 工作项

1. **§4.0 的 spike**(半天,先行)
2. 智能账户接入(连接器 / 升级流程)。⚠️ **EOA 与 CA 地址不同,资产要迁**
3. 授权表单 UI
4. session key 注册 + 策略构造(含 4.2 的翻译层)
5. 服务端 agent 执行器
6. 进度展示 + 完成报告
7. 撤销入口
8. 会话密钥的服务端存储(⚠️ **这是新增的一类秘密**,要进 `server/env.ts` 白名单)

### 4.7 判据

- [ ] 授权「≤0.5 USDC,最多 3 件,24 小时」⇒ agent 只买得起符合条件的
- [ ] ⭐ **故意把 agent 改成买白名单外/超额的** ⇒ **链上 revert**(这条验的是强制力,不是功能)
- [ ] 到期后 session key 失效
- [ ] 撤销后立即不能再花
- [ ] 买完后**用户自己**在网站上能下载(不需要 agent 转交)
- [ ] 买 3 件 = 3 笔 `PaymentSplit` 事件,且都带 `[Agent]` 徽章
- [ ] 超时/失败有明确报告,不是一个转圈

## §六 明确不做

- ❌ **服务端持有用户主私钥** —— 任何时候都不做(决策 2 的红线,不在本次放开范围内)
- ❌ **agent 用自己的钱包买再转交** —— `purchases` 记 agent ⇒ 用户自己下载不了 ⇒ 与"用户买的"不符
- ❌ **声称兼容 x402** —— 我们**复用形态不实现结算**(`exact` 方案是 EIP-3009 直转 `payTo`,我们不是)
- ❌ **改合约** —— 已部署冻结,本包**零合约改动**;4.2 的翻译层就是为绕开这一点
- ❌ **给 `/api/catalog` 加 query 参数** —— 演示量级不需要
- ❌ **长期订阅式授权**(反复给新内容买)—— 4.2 的快照限制决定了做不了
- ❌ **Y 方案(本地 agent)** —— 除非 §0.1 被否

## §七 风险

### 7.1 ⚠️ 最大风险:4337 这条链在 Fuji 上跑不通

已在文档层面确认 Pimlico 支持 Fuji,**但没实测**。
⇒ §4.0 的 spike 就是为这个。**跑不通就停,不要硬上。**

### 7.2 ⚠️ 智能账户地址不同 ⇒ 资产要迁

EOA 和合约账户地址不同。演示可以指定一个钱包,
但"让用户换钱包"是真实门槛,文案上不要说成"无缝"。

### 7.3 ⚠️ 赎回一次性,失败即作废

`payment:<txHash>` **无 TTL、永久**。agent 拿同一个 txHash 重试**会被拒**。
⇒ 下载失败(网络抖动/写盘失败)⇒ **那笔钱废了,得重买**。
agent 执行器必须**第一件事就是把内容存下来**,再报告成功。

### 7.4 ⚠️ 扫货是 N 笔链上交易

买 10 件 = 10 笔,串行等确认,大概几十秒。gas 在 Fuji 便宜,**时间省不掉**。
超时要能续,不能全丢。

### 7.5 ⚠️ 文案不许夸大

包 A **不是"我实现了 agent"**,是一次**意图解析**。
包 B 是**受限委托**,不是"agent 自己决定买什么"。
两处都要如实写 —— 说大了,评委一问就露。
