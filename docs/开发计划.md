## 一、拆分原则（为什么这样切）

1. **按"可独立验证的产出"切,不按"前端 / 后端 / 合约"切。**
   黑客松的死因几乎从来不是"某个模块写不出来",而是**最后两天集成不通**。因此每个工作包的完成定义都是**一个能被外人看到的可验证结果**（一笔 explorer 上的交易、一个 401 响应、一段能跑的脚本）,而不是"写完了 XX 模块"。

2. **接口先冻结,再并行。**
   合约接口（§8.1）是一切下游的契约。它冻结之前写前端是浪费——付款页的状态机完全取决于 `pay()` 的 revert 条件。**冻结成本 = 1 小时,不冻结的成本 = 2 天返工。**

3. **门禁必须早于 Agent 路径。**
   两者表面无关,实则**共用同一个"内容交付"原语**（读私有内容 → 校验权限 → 给内容）。门禁先跑通,Agent 路径就只是把"验签"换成"验 txHash"。反之先做 Agent,门禁还得再解决一次同样的存储问题。

4. **三层范围映射到工作包。** 保底层 = W1–W6 + W10;核心竞争力层 = W7–W9;加分层 = W12。**任何时候砍掉的工作包必须整个属于加分层。**

5. **每天结束时,主干必须能跑。** 不允许出现"重构到一半明天再说"的状态过夜。

**9/21 同日补完的部署骨架**（原排在 W6/W8,提前铺空壳）

**起因**：核查"这个结构部署到 Vercel 行不行"时发现,方案里依赖的三样 Vercel 能力（Blob private、KV、Functions）**都只是"已核实存在",从没实测过组合**。等 W6 建 store、W8 接 KV 时才发现构建配置不对,离交稿就只剩几天。**空壳不承载业务逻辑,纯粹是把部署风险从 W8 提前到 W1。**

**定下的四条边界**（写进 README,后续工作包必须遵守）：

| 目录 | 是什么 | 关键约束 |
|---|---|---|
| `shared/` | 两端共用的纯逻辑（链、USDC 地址、W2 起的 ABI） | **从 `viem` 取依赖,不从 `wagmi`** —— 否则 React 被拖进服务端 |
| `api/` | Vercel Functions,**一个文件 = 一个公开路由** | 只有入口文件放这里 |
| `server/` | 只在服务端跑的辅助代码 | **不放在 `api/` 里** —— 否则会被暴露成公开端点 |
| `scripts/` | 本地脚本（W9 的 Agent 演示客户端） | **必须是第三处**：放 `src/` 会打进产物泄漏私钥,放 `api/` 会变成公开接口 |

**两份 tsconfig,故意的**：`tsconfig.json` 带 DOM（前端）;`tsconfig.api.json` 不带（服务端）。
已实测验证：往 `server/` 塞一句 `document.title`,编译**当场报 TS2584**。这就是拆两份的全部理由 —— 否则服务端代码误用浏览器 API 会静默通过,运行时才炸。

**环境变量加了登记表**（`server/env.ts`）：`VITE_` 前缀会被内联进前端产物,而在此之前**代码里没有任何东西阻止有人手滑把 `QUOTE_HMAC_SECRET` 写成 `VITE_QUOTE_HMAC_SECRET`** —— 那一下就把签名密钥公开了。现在想读服务端密钥只能走 `serverEnv()`,它只认登记过的名字。`.env.example` 也按「前端可见 / 仅服务端」分成两组,中间那条线是红线。

**验证状态**：
- ✅ 两份 typecheck + `vite build` 全过
- ✅ `api/health.ts` 已实际执行,返回 200 JSON（`ready: false, 0/7` —— W1 符合预期）
- ⚠️ **`vercel.json` 的 rewrite 规则未经真实部署验证**（Vercel 文档站被网络策略挡了,没能核实官方的 SPA 配方）。写的是负向先行断言 `/((?!api/).*)`,**在两种优先级规则下都正确**。首次部署后必须验证两件事:① `/api/health` 返回 JSON ② `/` 返回页面

### 5.1 第 3 项：签名方案 → **选 EIP-712,不选 `personal_sign`**

**用途**：§9.2 的人类门禁——买家证明自己拥有某地址,服务端据此读链上 `purchases[contentId][address]`。

| | EIP-712 ✅ | `personal_sign` ❌ |
|---|---|---|
| 钱包里显示什么 | **结构化字段**（解锁哪个内容 / nonce / 截止时间） | 一串看不懂的 hex |
| 抗钓鱼 | 用户看得懂自己在签什么 | **不透明签名是钓鱼的标准形态** |
| 跨链/跨应用重放 | **domain 绑定 `chainId` + `verifyingContract`,天然防** | 无任何绑定 |
| 与 Agent 路径一致性 | **同一套心智模型**——ERC-3009 的 `TransferWithAuthorization` 本身就是 EIP-712 | 要额外维护第二套签名逻辑 |

**第 4 条是决定性的。** Agent 路径**已经必须**用 EIP-712（ERC-3009 规定的）,再选 `personal_sign` 等于为一个演示产品维护两套签名方案,没有任何收益。

**签名结构（定稿）**

```
domain: { name: "SplitJar", version: "1", chainId: 43113, verifyingContract: <CreatorSplitter> }
types:  Unlock {
          contentId: bytes32,
          buyer:     address,
          nonce:     uint256,
          deadline:  uint256   // unix 秒
        }
```

- `verifyingContract` 填**已部署的 `CreatorSplitter` 地址**（不是 `0x0`）——把证明绑死在本应用上
- `buyer` 虽可从签名恢复,但**仍显式入签**：钱包会显示它,且服务端可断言"恢复出的地址 == `buyer` 字段",多一层校验

> **⚠️ 陷阱一：两套 EIP-712 domain 会同时存在,别搞混。** ① **USDC 的 domain**（Circle 定义,用于 `TransferWithAuthorization`）② **我们的 domain**（SplitJar + `CreatorSplitter`,用于解锁证明）。**用错 domain 的症状是"签名永远验不过",而且报错很隐晦。**
>
> **⚠️ 陷阱二（更具体）：USDC 的 domain 参数必须从链上读,不能硬编码。** FiatToken 在不同网络上 `name()` / `version()` 可能不同,硬编码主网值在 Fuji 上会**静默失败**。做法：读合约的 `eip712Domain()`（EIP-5267）,或分别读 `name()` + `version()`。**W2 部署后第一件事就是把它打出来存档。**

**Nonce 策略（定稿）：服务端签发的一次性 nonce + deadline 双保险**

```
GET  /api/unlock-nonce   → 服务端生成随机 nonce,写 KV：
                           unlock:{nonce} = { contentId, issuedAt },TTL 5 分钟
前端  签 EIP-712（含 nonce + deadline = now + 5 分钟）
POST /api/unlock { contentId, address, signature, nonce }
      服务端 ① 验签 → ② 校验 nonce 在 KV 且 contentId 匹配
             → ③ 读链上 purchases[][] → ④ 通过后【才】删除 nonce
             → ⑤ 返回 60s 短时效签名 URL
```

- **为什么不用纯时间戳**：纯 `deadline` 方案在 5 分钟窗口内**可被重放**,不是真正的"一次性"
- **⚠️ 顺序：成功之后才消费 nonce。** 这是 §9.4 的 402 反重放**同一条教训**——先删再干活,一旦后面失败用户就得重新签名。这里后续只是链上读（幂等）,**所以"成功后消费"是安全的**
- **诚实的边界**：这个 nonce 防的是**证明被转移**,不是保护资金——解锁证明**不授权任何链上操作**,重放它最多让人拿到自己已付费的文件。**别过度设计。** 真正必须防的是"签名被挪用到别的 `contentId`",而 `contentId` 已在签名消息内

**⚠️ W1 必须验证**：**Core Wallet 能正确渲染 `eth_signTypedData_v4`。** 若渲染有问题,降级方案是退回 `personal_sign` + 页面里用人类可读文案复述签名内容——**但这必须在 W1 就发现,不能等 W5**。

## 十、三个关键坑的解法（9/21 核实）

### 坑 1：私有存储（原 R1）—— 🟢 已解除,不是风险

**查证结论**：Vercel Blob **private store 所有套餐都可用**,Hobby 免费额度内,私有与公开**同价**。

| 细节 | 影响 | 行动 |
|---|---|---|
| **访问模式创建时固定,之后不可改** | 建错只能重建 store | **W0 建 store 时必须直接选 private** |
| 私有读取必须经 Function 中转 | 会产生 Fast Data Transfer 计费 | 演示量可忽略,不用管 |
| 超出 Hobby 额度 → 访问暂停（403） | 演示量小,不构成风险 | 知道即可 |

**加密兜底方案不必做**（内容 AES 加密后放公开存储,付费后下发密钥,效果与私有存储等价）。留作极端情况备选,不占排期。

---

### 坑 2：402 报价防篡改 —— ✅ 可解,约 15 行,零新增基建

**问题**：报价里的 `quoteExpiresAt` 若由 Agent 自己说了算,§9.4 校验第 5 条（"在报价有效期内"）就是空的——Agent 可以声称任意有效期。

**修法**：

```
服务端签发报价时,生成 quoteId + expiresAt,用服务端密钥做 HMAC 签名
  → 402 响应体里带上 { quoteId, expiresAt, sig }
  → Agent 付款后,必须把 quoteId 回显在 X-Payment 里
  → 服务端验签 sig,才采信 expiresAt
```

**三个附带好处**

1. **不需要用 KV 存报价签发时间** —— 签名本身就是凭证,少一个存储依赖
2. 第 5 条校验从"无法验证"变成"真的有意义"
3. 报价从**一段 JSON 变成一个签过名的凭证**,对 x402 的叙事更顺

**注意**：这条与 §9.4 第 4 条（`txHash` 防重放用 KV）**不冲突也不重复**——签名保护的是"报价的真实性",KV 保护的是"交易的一次性"。

### 12.1 为什么 `"types": ["vite/client"]` 可以删

我一度以为它是**刻意设的边界**：白名单只放 `vite/client`，于是 `process`、`Buffer`
这类 Node 全局在前端代码里应该是类型错误。**2026-09-23 实测：挡不住。**

往 `src/` 放个探针写 `process.env.FOO` / `Buffer.from("")` → `tsc --noEmit -p tsconfig.json`
**退出码 0，一条错不报**（且确认该文件在 program 里，不是没被收进来）。

原因：`types` 数组只管 `node_modules/@types/*` 的**自动引入**；任何依赖的 `.d.ts` 里
只要有一句 `/// <reference types="node" />`，`@types/node` 就会被拉进整个 program。

**两条后果，一条比一条重要：**

1. 删它是**无损**的 —— `src/vite-env.d.ts` 里的 `/// <reference types="vite/client" />` 已经够用。
2. ⚠️ **方案 §20.4.8 讨论"服务端 SDK 的一部分被带进前端产物"时的安全性论证，
   不能把类型检查算进去。** `process.env` 在 `src/` 里是合法的，"构建通过"证明不了
   前端没碰 node-only 的东西。这条要回填进方案。

### 12.4 🔴 前置：闸门顺序是反的，会破坏「下架不影响已购」

**2026-09-23 决定要上下架功能时查出，必须先修，否则新功能一上线就违反自己的产品语义。**

需求（用户原话）：「下架的内容，不影响已付款，继续下载。」

**服务端已经满足。** `api/unlock.ts` 的六道检查里**没有任何一步看 `active`**，
只有第 ⑤ 步 `hasPurchased(contentId, buyer)`。所以签名换 URL 这条路
对已下架内容照常放行 —— 这一半是对的，而且是**故意**对的。

**前端闸门是反的。** `src/lib/payGate.ts` 的判断顺序：

```
:96   if (i.active !== true)   → blocked 'content-inactive'     ← 先
:110  if (i.owned === true)    → blocked 'already-purchased'    ← 后
```

对**一个已下架、且我买过**的内容：`:96` 先命中 → `content-inactive`，
而 `describeBlock` 给它的出路是 `recovery: { k: 'none' }`（`payMachine.ts:240`）
→ **没有下载按钮**。买家付过钱，却连下载入口都没有。

**最能说明问题的是那段文案自己**（`payMachine.ts:240`）：

> `title: '该内容已下架'`
> `hint: '创作者已停止售卖，如果你之前买过仍可下载。'`
> `recovery: { k: 'none' }` ← **承诺了下载，却没给下载按钮**

**修法**：把归属判断提到 `active` 之前，并把 fail-closed 那条也一并前置：

```
if (i.owned === true)  → already-purchased   // 已购：下架与我无关，直接去下载
if (i.owned !== false) → ownership-unknown   // 查不到：给重试，不猜（§payGate 原注释的理由）
if (i.active !== true) → content-inactive    // 明确没买过 + 已下架：这才是真拦
```

⚠️ **第二条放在 `active` 前面是有意的**：如果只把 `owned === true` 提前、
把 `ownership-unknown` 留在后面，那么「已下架 + 归属读失败」会落到
`content-inactive`（死路 `none`），而那个用户**可能真的买过**。
死路对他比 `ownership-unknown` 的「重试」更糟 —— 他没有任何办法拿回自己买的内容。

**代价**：改动是 `payGate.ts` 里三行的**换位**，`GateResult` 类型和
`describeBlock` 一个字都不用改。但它是行为变更，`payGate` 目前**没有单元测试**
（§W4 11.10 已决定不加测试运行器），所以验证只能靠驱动脚本 ——
判据是：**用真链上那件已购买的内容，在 fork 上把它置为 inactive，
买家打开付费页应当看到「你已经买过了」+ 下载按钮，而不是「该内容已下架」。**
→ **✅ 已于 2026-09-23 实现并验证，见 §12.5。**

### 12.6 已下架付费页的两个问题（2026-09-23，用户看截图提出）

**触发**：用户拿新买家钱包打开已下架的 `/p/<id>`，看到两样不该有的东西 —— ①付款二维码；
②「重新检查」按钮。两问都是对的，而且第 ② 问牵出了一个**影响面大得多的 bug**。

#### 问题 ①：付不了款却还摆着"去付款"的入口

二维码下面的说明是「用手机扫这个码，**在手机上完成付款**」，而 `pay()` 第 214 行
`if (!c.active) revert ContentInactive` —— **付款必定 revert**。摆一个 100% 失败的入口，
比什么都不摆更糟。二维码区块原本**没有任何状态守卫**，所以下架页也在渲染它。

#### 问题 ②：那个按钮点了**什么都不会发生**（真 bug，不是文案问题）

`usePayFlow` 的 `start` 只做 `dispatch({ type: 'start' })`，**没有 refetch 任何链上读**。
闸门拿到的是同一份缓存，于是原样判回 `blocked` —— 状态闪一下 `checking` 又回到原样。

**实测判据（数 RPC 请求数，不看界面）**：点击前后 `5 → 5`，**一个请求都没发**。
界面上"看起来动了一下"具有欺骗性，所以判据必须是请求数。

**为什么这个 bug 比下架严重得多**：下架那一态现在压根不渲染按钮了，所以只影响历史。
真正受害的是**余额不足**：用户看到「USDC 不足」→ 去水龙头领币 → 回来点「重新检查」
→ **什么都不会发生**。他只会以为这个页面坏了。这是演示路径上的高概率动作。

#### 改了什么

| 文件 | 改动 |
|---|---|
| `src/hooks/usePayFlow.ts` | `start` 先 `refetchAll.current()` 再 dispatch —— 六个链上读全部重查。refetch 收起进一个 ref，避免 `start` 每次渲染换身份 |
| `src/pages/PayPage.tsx` | 用 `describeBlock(...).recovery` **一处**判两件事：出路是 `download` 或 `none` → 不渲染主按钮；二维码加 `state.k === 'idle'` 守卫 |

**为什么用 `recovery` 判而不是再写一份 reason 清单**：状态机已经声明了每个拦截态的出路，
两份清单迟早会对不上。`none` 的四个里只有 `content-inactive` 能走到那段 JSX

所以影响面是精确的。

#### ⚠️ 二维码为什么在 `failed` 态也藏（这一条不是顺手）

`receipt-timeout` 意味着**交易很可能已经成功**（收据回来了，但 `purchases` 标记没读到，
见 `usePayFlow` 第 ⑥ 段）。那种时候还摆一个"扫码完成付款"，等于**请用户再付一次**。
宁可少给一个入口。

### 12.7 同一地址拿两份时，累计收入少算一份（2026-09-23，用户报）

**症状**：用户把「协作者」填成了自己的钱包地址。买家付了 0.05 USDC，
但创作者侧的「累计收入」显示 **0.0495**。

#### 先钉死链上事实（这决定了是合约错了还是显示错了）

直接读那笔 `PaymentSplit`：

```
recipients = [0xA0b760…3D63, 0xA0b760…3D63]   ← 同一个地址出现两次
amounts    = [49500, 500]                     ← 0.0495 + 0.0005
合计       = 50000 = 0.05 USDC
```

**合约完全正确**：`pay()`（`CreatorSplitter.sol:230-242`）按 `splits` 逐项算份额，
`_push()`（`:295`）对**每一项**各发一笔 `transfer` —— 同一个地址收到两笔，
合计正好 0.05。合约也**不禁止**重复地址（只校验非空 / 无零地址 / 每项 > 0 / 合计 = 10000）。

**错在显示层**。`useMyContents.ts` 写的是：

```ts
const idx = recipients.findIndex((r) => r.toLowerCase() === address!.toLowerCase())
myShare: amounts[idx] ?? 0n        // ← 只取第一个匹配
```

`findIndex` 只给第一个下标。同一个地址出现两次时，**第二份被静默丢掉**。

#### 为什么这**不是**设计分歧，而是 bug

创建页（`CreatePage.tsx:44-49`）早就写明了这个用法合法：
「`recipients = [A, A, B]` 在合约层面就是"A 拿两份"，完全合法（同一个人的两个角色）」
—— 而且对重复地址**只警告、不拦截**，警告词是
「有重复的收款地址 —— 合约允许，**那个人会拿到两份**」。

所以"两份都算上"是这个产品**白纸黑字承诺过的语义**。统计 hook 违背了它。
（这也是为什么没有停下来问：口径早就定了，只是没执行。）

#### 改了什么

| 文件 | 改动 |
|---|---|
| `src/hooks/useMyContents.ts` | `findIndex` → `forEach` + 累加，`myShare` 汇总**所有**匹配位；`matched` 标志取代 `idx === -1` |

#### 验证表

| # | 断言 | 判据 | 结果 |
|---|---|---|---|
| 0 | 创作者地址在 recipients 里出现 2 次 | 直连 RPC 读 `PaymentSplit` | ✅ |
| 0b | **判别力对照**：旧写法 49500 / 新写法 50000 | 拿同一份真实链上数据把两种写法各跑一遍 | ✅ 差 500 |
| 1 | `/console` 累计收入 = 0.05 | 页面文本 | ✅ |
| 2 | `/dashboard` 累计 = 0.05、单笔 `+0.05`、界面上不出现 0.0495 | 页面文本 | ✅ |

**方法**：`pwshot/split-share.js`。

**第 0b 条是这类"数字对不对"验证的必要一步**：如果两种写法给出同一个数，
那这个脚本证明不了任何东西。**先证明脚本能区分对错，再相信它说"对"。**

⚠️ 排错记录：第一版断言写成 `/\+([\d.]+)/`，抓到 `+0.050` 判成失败 —— 那是**我的正则错**
（金额后面紧跟交易哈希 `0x…`，`[\d.]` 把 `0x` 的 `0` 吃进去了），不是应用错。
改成 `\+(\d+(?:\.\d+)?)(?=0x)`。**假失败和真失败要分清，否则会去"修"一个没坏的东西。**

#### 同一族的另一处——**不是活 bug，记着就行**

`!matched → continue` 会把"我不在收款人里"的那笔销售**整条丢掉**，导致「成交笔数」少算。
但 `CreatePage.tsx:181` 把创作者写死在 `recipients[0]`，所以**经我们 UI 创建的内容
永远命中 `matched`** —— 这条路走不到。合约层允许（它不要求 creator ∈ recipients），
所以哪天有别的创建入口（比如 W7 的 Agent）就得回来看这里。

#### 顺带记进 backlog 的

付费页分账明细里，同一个地址的两行**都标「创作者」**（见 §十二 #8）：
标签逻辑是 `addr === creator ? '创作者' : '协作者'`，地址相同就两行同名。
买家看到两行一模一样的「创作者」，像 bug。**三种改法都说得通，是设计分叉，没有擅自定。**
