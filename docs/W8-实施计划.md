## 〇、先结掉那个必须做的决策点：买家类型**怎么判**

§16.1 第 7 条要求「Agent 这笔购买在 `/dashboard` 中正确显示买家类型为"Agent"」。
但链上**没有**"买家类型"这个字段 —— 两条路走的是**同一个 `PaymentSplit` 事件**
（`shared/abi/creatorSplitter.ts:288`）。所以这一条全部难点就是:**凭什么说这笔是 Agent 买的?**

规格 §9.4 第 706 行给了两条路：

> ① Agent 付款方地址来自已知的演示密钥 / 客户端指纹,维护一个小白名单;
> ② 看板只区分"有钱包签名交互"与"无交互"两类。**MVP 用 ①,简单直接**。

### ⚠️ ② 站不住，而且是**方向性**的错

本项目这个 Agent 要**自己发两笔交易**（`approve` + `pay`）—— 它**有**钱包签名交互。
拿 ② 去判,它会被判成"人类"。**② 这条例子里没有可用的东西**,不要再讨论它。

### ③ 一条规格没写、但确实存在的信号（记录在案）

KV 里的 `payment:${txHash}` **只有 agent 那条路会写** ——
`api/content/[id].ts` 成功时调 `commitPayment`,而 `/api/unlock`（人类门禁）
**从不碰 `payment:*`**（已 grep 核实）。所以"这个 txHash 有没有落定记录"
**答的是**:"这笔内容是不是从 HTTP 402 那条路交付的"。

它有两个优点：**不可伪造**（要写它必须先在链上真付款）、**已经是现成的**
（`server/kv.ts:242` 的 `isPaymentConsumed` 就摆在那儿）。

**但它答的不是我们要问的那个问题**："从 402 交付"≠"agent 买的" —— 人当然也可以 `curl`。
而且它要**新基建**：看板现在是**纯链上**的（`useMyContents` 直接 `getLogs`，
不依赖任何服务端），接它就得新开一个端点、每次渲染多一轮 KV 读。

### ✅ 本包定：用 ① 白名单，并且**把白名单显示在界面上**

三条理由：

1. **与规格一致,且零额外基建。** 看板不用碰服务端 —— `useMyContents.ts:47` 的
   `Sale.payer` 已经有了,`DashboardPage.tsx:205` 已经在渲染 `来自 {shortAddress(s.payer)}`。
   **只差一个徽章**,不是一次架构改动。
2. **演示里 agent 用专属地址**（§一 决策 1）,所以标注**100% 准**,不会误标。
3. **白名单是"身份标注",不是"行为检测"—— 那就把它摊开给人看。**
   界面上直接列出名单内容。一个可审计的名单,比一个来路不明的"自动识别"更可信。

### ⚠️ 必须如实写进 UI 的代价

**一个不在白名单里的 agent 会被标成"人类"。** 这不是 bug,是这条路线的固有边界 ——
所以看板上那句话不能写成"自动识别买家类型",只能写**"按地址白名单判定"**。
这与 §5.2 那条纪律同源:**别把弱检查包装成强保护**。

### 备选（只在时间富余时做）

白名单 **+** KV 那个信号,两个都命中才标 "Agent",否则标"人类"。
成本是多一个端点 + 一次 KV 往返。**它换来的是"不可伪造"这一层**,
对演示没有增量,**明确排在 W11 之后**。

## 一、已定的决策（上游定的，本包照办）

### 决策 1：Agent 用自己的**专属测试地址**

上游依据：开发计划 §十 ——「**另备 2–3 个测试地址轮换**（Agent 脚本、人类买家、创作者各一个更清晰）」。
演示账户见 `contracts/README.md`：创作者 `0xA0b760…3D63`、人类买家 `0x9750Af…B988`。

**为什么必须分开**：Circle faucet 限 **1 USDC / 2 小时 / 地址**，
而现在在架那件演示内容 `0xe2f8dba7…` 的价格是 **0.1 USDC**（链上实测,`price=100000`）。
一次 drip 够 **10 次**付款 —— 看着宽裕,但 agent 脚本**演示现场要反复跑**,
和人类买家挤同一个地址就会互相耗额度,而且是**演示中途**才发现。

⚠️ **记一处上游文档与现状不一致**：开发计划 §R9 写的是「价格锁 **0.2 USDC**」,
而实际建出来的演示内容是 **0.1**。按实际值算额度,别按文档算。

### 决策 2：私钥只走**当前 shell 的环境变量**

依据是 `.env.example` 的原话与方案 §6.2：

> ⚠️ **绝不写进 `.env`** —— 这是部署私钥。只在当前 shell export,用完就关窗口。

三条硬约束,本包一条都不放宽：

- 不进 `.env` / `.env.local`（`vercel dev` 也不读后者,但那是另一回事）
- 不进仓库（`.gitignore` 之外还要靠人不手滑 —— 见 §七 风险）
- **不进前端产物**：`VITE_` 前缀会被**内联进 bundle**,所以 agent 的私钥
  **绝不能**有 `VITE_` 形式的名字
- `.env.example` 只登记**变量名与用法**,值永不出现（与现有那条红线一致）

### 决策 3：脚本落在 `scripts/`，且是 `.mjs`

依据 §W1 的定案：`scripts/` 必须是**第三处** ——
放 `src/` 会打进产物泄漏私钥,放 `api/` 会变成公开接口。

⚠️ **用 `.mjs` 不是随手选的**:`tsconfig.json` 的 `include` 是 `["src", "shared", "vite.config.ts"]`,
`tsconfig.api.json` 是 `["api", "server", "shared"]` —— **`scripts/` 两边都不进**。
`.mjs` 因此**不参与任何一次类型检查**,也就不会某天因为一个 tsconfig 放宽而把
Node 专用的东西（`node:crypto` / `process.env`）混进前端的编译单元。
（W7 已落地的 `scripts/verify-x402.mjs` 是同一条路子。）

### 决策 4：**报价必须从 402 响应里读出来**

§W8 的注意原文：

> 脚本里的"自主决策"要真实 —— **报价是从 402 响应里读出来的,不是硬编码**。
> 硬编码的脚本一看就假,而这是全场最难被复制的一屏,**被怀疑造假就全废**。

这一条是本包的**验收红线**,不是风格偏好。落地到三处（详见 §五）：
金额来自 `accepts[0].maxAmountRequired`、小数位来自 `/api/catalog` 的 `decimals`、
**要买哪一件**由脚本从 catalog 里挑。

### 决策 5：白名单**只有一个来源**，前后端读同一个文件

```
shared/agentAddresses.json     ← 唯一来源（纯数据）
shared/agentAddresses.ts       ← 前端用的带类型再导出（~5 行）
scripts/agent-buy.mjs          ← 直接读那个 .json
```

**为什么费这个劲**:如果脚本里写一份地址、前端里再写一份,
"脚本付的地址"和"看板标的地址"就会**各自漂移** —— 而漂移的症状是
**看板把 agent 标成人类**,恰好是 §16.1 第 7 条要验的那一屏。
两处各写一遍,等于把一条验收项交给"记得同步"。

`resolveJsonModule` 在 `tsconfig.json` 里已经开着（`true`）,前端 import 它不需要改配置;
Node 22+ 用 `import … with { type: 'json' }` 读同一个文件（`engines` 要求 `>=22.12.0`,满足）。

## 三、脚本怎么跑（一条命令，每一步都要看得见）

`开发计划.md:400` 明说：「脚本要**打印每一步**,因为它是演示主角,过程要能被看见。」
所以下面的每一步都有对应的输出。

```
node scripts/agent-buy.mjs                 # 完整跑
node scripts/agent-buy.mjs --dry-run       # 停在付款之前（省额度，见 §七）
node scripts/agent-buy.mjs --content 0xe2f8…   # 指定买哪一件
```

### 流程

| # | 这一步做什么 | 打印什么 | 靠哪条已经存在的东西 |
|---|---|---|---|
| 0 | 自检:环境变量齐不齐、地址与私钥对不对得上、AVAX/USDC 够不够 | 地址、两个余额、缺什么 | viem `getBalance` / `balanceOf` |
| 1 | **发现**:`GET /api/catalog` | 候选清单 + **它挑了哪一件、为什么** | W7 `api/catalog.ts` |
| 2 | **被拦下**:无头 `GET /api/content/:id` → **402** | 原始 402 body 里的 `accepts[0]` | W7 `api/content/[id].ts` |
| 3 | **解析报价**:从 402 里取出 `maxAmountRequired` + `quote` | 金额、`quoteId`、`expiresAt` | 同上 |
| 4 | 读 `allowance`,不够才 `approve` | 「额度够,跳过 approve」或「签第 1 笔」 | 人类路径同一条（`needsApprove`） |
| 5 | `pay(contentId)` | 两笔交易的 `txHash` + explorer 链接 | `CreatorSplitter.pay(bytes32)` |
| 6 | **带 `X-Payment` 重试**同一个 URL → **200** | 签名 URL + 字节数 | W7 `deliverBranch` |
| 7 | **真的下载一次** | 字节数 + `sha256`,`--verify-hash` 时与链上 `contentHash` 比对 | `getContent` 的 `contentHash`（W5 起是真哈希） |
| 8 | 收尾 | `txHash` + explorer 链接 + 最后一行机器可读 | 见下 |

### ⚠️ 第 4 步为什么要判 `allowance`，而不是无脑 approve

和人类路径同一个理由（`usePayFlow` 的 `needsApprove`）：授权额度够就**不该再弹一次**。
对 agent 而言这还多一层意义 —— **少一笔交易就少一次演示现场失败的机会**。
⚠️ 但**不能把"跳过"写死在报告里**:跳过与不跳过的输出必须能区分,
否则"演示跑了 2 笔还是 1 笔"这件事就说不清了。

### ⚠️ 第 6 步的 URL 必须与第 2 步**完全相同**

包括路径。签名覆盖 `contentId`,换一条路径就验不过 —— 那不是 bug,
是"报价绑定内容"在生效（W7 §5.4 第 4 条）。

### 第 8 步的输出格式（与 W7 那个验证脚本对接）

最后一行固定形如,便于直接喂给 `scripts/verify-x402.mjs`：

```
txHash=0xb8bc20f6…
payer=0x<agent>
```

`verify-x402.mjs` 会在链上把 `payer` 发过的、**还没被兑过**的付款扫出来当凭证
（用的是它的**无损探针**）—— 所以 W8 一跑,`W7-实施计划.md` §6.4.4 那几条
"验不了"的自动就有了材料。**两个脚本是配套的。**

### ⚠️ 必须处理的一条失败：`AlreadyPurchased`

合约 `CreatorSplitter.sol:215` 有 `if (purchases[contentId][msg.sender]) revert AlreadyPurchased(...)`
—— **同一个地址买同一件内容第二次必 revert**。而演示现场最可能的操作就是"再跑一遍"。

所以脚本**在发第 5 步之前先读 `purchases(contentId, agent)`**,
已经买过就**直接说明并给出出路**,而不是让钱包弹出来再 revert:

```
这件内容这个地址已经买过了(合约不允许重付)。
→ node scripts/agent-buy.mjs --content <另一件>
→ 或者用 /api/catalog 里其它在架内容
```

⚠️ 注意 `--dry-run` **不覆盖**这种情况:它停在付款前,所以"能不能付"这条它测不出来。
**自检里那次 `purchases` 读必须照做。**

## 四、看板标注怎么实现

改动很小,但有一处**必须小心**：

```ts
// useMyContents.ts —— Sale 加一个字段
isAgent: AGENT_ADDRESSES.includes(log.args.payer!),   // ⚠️ 大小写!
```

⚠️ **比的必须是归一化之后的地址。** `PaymentSplit` 事件里 `payer` 是 `indexed`,
viem 解出来是 **checksum 形态**;而白名单 JSON 里人手写的很可能是**全小写**。
直接 `includes` 会**静默地永不命中** —— 症状正好是"看板把 agent 标成人类",
也就是 §16.1 第 7 条那一屏挂掉。

**做法**:两侧都先 `getAddress(x.toLowerCase())` 再比（`shared/agentPay.ts:282`
对 `payer` 做的就是这件事,理由一模一样）。**别用 `===` 比裸字符串。**

界面上（`DashboardPage.tsx:205` 那一行）：

```
来自 0x9750…B988   [Agent]     ← 白名单命中
来自 0x1234…5678               ← 未命中,不加徽章
```

底部那句解释文字要**换掉**（现在写的是「买家类型标注(人类 / Agent)是 W8」）,
改成如实说明**判定方式**：「Agent 标记按地址白名单判定,名单内容:…」。

⚠️ **分账比例那一半不用做。** §16.1 第 7 条要求的是「**且分账比例与人类购买一致**」
—— 两条路走的是**同一个合约、同一个 `pay()`、同一个 `PaymentSplit` 事件**,
看板渲染的是事件本身。**这件事是结构上就成立的,没有代码要写。**
（这正是方案 §9.4 那句"v2.1 的改动全部落在 HTTP 层、合约零改动"的意思。）

## 五、"自主决策"必须是真的（反造假）—— 验收红线

§W8 那条注意值得单独成一节,因为它是**唯一一条"做对了也看不出来、做假了也看不出来"**的要求。

### 脚本里**不许出现**的三个值

| 值 | 必须来自 | 出处 |
|---|---|---|
| 要付多少钱 | `402` 响应的 `accepts[0].maxAmountRequired` | 不是常量、不是 `catalog` 里的 `price` 字段 |
| 要买哪一件 | `/api/catalog` 的返回,由脚本自己挑 | 不是命令行默认值（可以 `--content` 覆盖,但**默认必须是它自己挑的**） |
| 付款人是本人 | 本地私钥推导出的地址,**再回链上核对** | 不是写死的字符串 |

⚠️ 金额这条最容易写错:`/api/catalog` 里**也有** `price`,而且是同一个值,
所以"从 catalog 读价格"**看起来也对**、测起来也对。但那不是 402 协商的结果 ——
**它绕过了"被拦下 → 读报价 → 按报价付款"这个动作本身**,而那正是这一屏要展示的东西。

### 评委可以自己验的三步（写进 README）

1. 脚本输出里的 `txHash` 贴进 explorer → `PaymentSplit` 事件的 `payer` **就是**脚本自报的地址
2. 那笔交易的 `amounts` 求和 == 该内容当时的链上价格
3. 看板上这一笔带 `[Agent]`,且**分账明细与人类购买那一笔格式完全一样**
