## 零、本轮最重要的一条核实：标题链路的真相

上一版清单把「标题会丢」列成高优先级缺陷。**核实之后要修正：那是错误判断。**

标题**确实**会写进 KV，链路完整：

```
CreatePage 填标题
  → usePublishFlow.publish() 记进 pendingTitle.current
  → 签 Upload EIP-712 授权（含 contentId / uploader / deadline）
  → 直传内容 + 预览图 → createContent 上链 → 等回执
  → publishContentTitle()  →  POST /api/content-meta
  → setContentTitle()      →  KV 键 `meta:<contentId>`
  → GET /api/catalog       →  getContentTitles() 一次 mget 批量读
  → ContentCard 带 `?t=`   →  PayPage 显示标题
```

**但它是「尽力而为」（best-effort），有四条明确会丢标题的路径 —— 全部是有意为之，不是 bug：**

| # | 路径 | 代码位置 | 是否静默 |
|---|---|---|---|
| ① | **5 分钟 `deadline` 过期**。标题只能写在回执之后（之前合约还没有 `creator`，归属检查必回 404），而 `deadline` 是第 1 步签的 | `uploadApi.ts:178-186`、`usePublishFlow.ts:341` | 否，`console.warn` |
| ② | **重试 / `skipUpload` 接不上**（`wire === null`，不重签）| `usePublishFlow.ts:328-332` | 否，`console.warn` |
| ③ | **KV 未配置** → `/api/content-meta` 回 503 | `content-meta.ts:110` | 否，服务端明确拒 |
| ④ | **内容建于该端点之前** | `content-meta.ts:44-46` 明写「正常状态，不是 bug」 | —— |

### ⚠️ 你的演示内容正好踩在 ④ 上

`api/content-meta.ts` 文件头第 44 行直接点名了：**演示内容 `0x6410fb…ef986f` 建于该端点存在之前**，标题只存留在创作者本机 localStorage。

连带后果（这条链路解释了此前截图里看到的「未命名内容」）：

```
catalog 对该内容 title = null
  → ContentCard 渲染 item.title ?? "未命名内容"，且链接不带 ?t=
  → PayPage 读不到 ?t=，退回占位文案「付费内容」
  → BuyerPage 的 purchasePath 同样无 ?t=
```

**修复只需一步，不用改代码**（二选一）：

- **A. 回填**：用创作者钱包对该 `contentId` 重新签一次 `Upload` 授权，调 `POST /api/content-meta` 写标题；或
- **B. 重发**：干脆用当前流程重新发布一件 demo 内容（会自然走完写标题那一步）。

> 推荐 **B**：顺带验证整套发布链路在最新代码下仍然通，一次演示排练。

## 三、答辩话术：四条诚实边界（主动讲，别被问出来）

> 这四条都已在代码 / README 里有标注，主动说出来比藏着体面得多。

**① x402 的形态与实现**

> 「我们复用了 x402 的**交互形态** —— 402 报价、`X-Payment` 头、报价签名，但**没有实现 x402 本身**。真实 x402 用的是 EIP-3009 预授权：买家签一个待广播的代付凭证。我们这里 `X-Payment` 头装的是**已经广播过的交易哈希**，服务端回链上验收据。所以信任模型是反的 —— 我们先付款、后凭证。代码里 `assetTransferMethod` 写的是 `eip3009-or-approve`，`extra` 里我们故意没写 `eip3009`，就是不想让这一点含糊。」

**② 为什么钱是一笔一笔记的分账，而不是先入池**

> 「合约里没有池。`pay()` 内部循环按 bps 直接 `transferFrom` 到 N 个收款地址，余数归最后一个收款人，所以我们能保证 `amounts` 求和恰好等于 `price` —— 服务端那条金额校验就是建立在这个恒等式上的。今天这条校验不可能失败，因为 `createContent` 之后合约没有任何改价入口；留着它是因为『金额不被验证』这件事本身不可接受。」

**③ reorg 保护**

> 「坦白说：确认这一环我们没有 reorg 保护。客户端是轮询 `purchases` 标记，服务端是『收据成功 + `PaymentSplit` 事件在场』，都没有确认数。这是测试网的取舍，上主网前必须改。作为补偿，状态机在不确定时一律**不谎报成功**：`receipt-timeout` 给的是区块浏览器链接，**不给重试按钮**，因为那时候交易很可能已经成了。」

**④ 为什么不算子索引器**

> 「我们刻意没有数据库。合约没有『列出所有内容』的函数，所以列表靠扫 `ContentRegistered` 事件；'我买过什么' 靠扫 `PaymentSplit` 按 payer 过滤。代价是慢一点，好处是**没有任何后台状态下的数据能对不上链**。公共 RPC 对 `getLogs` 有 50k 区块上限，所以我们做了窗口化 —— `shared/blockWindows.ts` 里那三个数字是量出来的，不是抄的。」
