# SplitJar · 收钱罐 —— 一页纸

> **创作者付费内容 + 链上多方分账。人类连钱包付,AI Agent 走 HTTP 402 自助付。**
>
> 线上演示 https://splitjar.vercel.app · Avalanche Fuji 测试网 (43113) · 测试网作品,不涉及真实资金

---

## 一句话

创作者定好**价格**和**分账比例**,上传内容,拿到一个付费页。买家付稳定币,钱按比例**当场直达**各方钱包,内容立即解锁 —— **无平台抽成、无资金池、无托管**。

同一套付费墙同时服务两类买家:**人类**连钱包付,**AI Agent** 收到 402 报价后自己付、自己取内容。

---

## 解决的问题

| 现在的做法 | 代价 |
|---|---|
| 平台代卖(知识星球 / Patreon / 外包站) | 抽成 10–30%,提现周期,账号一封钱货两空 |
| 接单后人工分账 | 协作方要"信任"发起者会转账,还要对账 |
| 内容给 AI Agent 用 | **没有为机器设计的付费入口**:Agent 不会扫码、不会填表、不会注册账号 |

第三条是这次的重点:**Agent 经济缺的不是支付网络,是"机器能自己完成的付款流程"。**

## 怎么做的

```
创作者 ──定价 + N 方分账──▶ /create ──▶ 付费页 /p/:contentId
                                            │
                         ┌──────────────────┴──────────────────┐
                         ▼                                     ▼
                  【人类】扫码打开(钱包浏览器)                   【AI Agent】curl / 脚本
                  连钱包 → approve + pay               GET 拿 402 + 签名报价
                  签名解锁 → 60s 短链下载               自己发交易 → 回传 txHash
                         │                                     │
                         └──────────────────┬──────────────────┘
                                            ▼
                              CreatorSplitter.pay() 一笔付款
                              ──▶ 按链上比例当场分给 N 个收款方
```

**两条路走的是同一个合约函数 `pay(bytes32)`,留下同一个 `PaymentSplit` 事件。**
这不是"两套系统长得像",是**同一条结算路径的两种入口**。

## 四个技术点(都能当场验)

| # | 点 | 怎么验 |
|---|---|---|
| 1 | **一笔付款分给 N 方,钱不经平台** | 看板 `/dashboard` 直接读 `PaymentSplit` 事件渲染 —— 没有自己的数据库 |
| 2 | **Agent 全链路无人干预** | `node scripts/agent-buy.mjs` 一条命令:发现 → 402 → 报价 → 付款 → 取内容 → 比对哈希 |
| 3 | **没付款拿不到内容** | 未付款请求 → `402`;已付款 → 60s 短时效 URL,过期实测 63 秒后 403 |
| 4 | **内容存证** | 下载到的文件 `keccak256` == 链上 `contentHash`,实测 277343 字节逐字节相同 |

**§16.1 Agent 七项验收全绿**:① catalog 可列 ② 402 报价字段完整 ③ 全链路无人干预
④ `txHash` 可在 explorer 当场验证(链上 5 笔)⑤ 同一 `txHash` 第二次 → 409
⑥ 冒用他人 `txHash` → 403 ⑦ 看板标 `[Agent]` 且分账比例与人类一致。逐条实测见 `docs/W9-实施计划.md`。

## 合约(Avalanche Fuji · 43113)

```
CreatorSplitter  0xDe9b3090263e20ebD5b3795F0199B500f6da72f5
USDC             0x5425890298aed601595a70AB815c96711a31Bc65
```

- Solidity + Foundry,**27 个单测全过**(含余数归属、重入、escrow 三分支)
- 部署交易 `0x2d7332bb…552d55`(Snowtrace 可查)
- `evm_version` 锁 `cancun` —— Foundry 默认的 `osaka` 是 Fuji 不支持的,这条是实测踩出来的

## 为什么是 Avalanche

- **Fuji 有官方 Circle USDC**,不用自己发一个测试币充当稳定币
- **出块快(亚秒级)**,付款后内容几乎立刻解锁 —— 这是"付费墙"体验能不能成立的前提
- **gas 便宜**:实测单笔分账钱包实付 1 nAVAX、约 $0.005,占演示定价(0.2 USDC)的 2.5%。
  gas 占成交额 2.5% 意味着**小额付费在商业上是成立的**,这是选链的关键论证

## 诚实边界(我们认为该主动说)

| 边界 | 说明 |
|---|---|
| **x402:复用形态,没实现它** | 报价体、字段命名、`method` 都照 x402 来,但**信任模型相反**:真 x402 的支付头装**未广播的签名授权**(EIP-3009)由 facilitator 代付;我们装的是**已广播交易的哈希**,只去链上查证。而且 x402 的 `exact` scheme **只有单 payee,容纳不下"一笔付款分给 N 方"** —— 那正是本产品的核心。我们不声明"实现了 x402" |
| **没有 reorg 保护** | Agent 路径的校验塌缩成"收据成功 + 日志在场",判据是确定性而非确认数。Fuji 演示可接受,**上主网必须改成等确认数** |
| **门禁信任面在 RPC** | 服务端读链走我们配的 RPC,不是轻客户端证明。RPC 说谎,门禁就判错 |
| **escrow 不是任何情况都拿得到** | 收款方被 Circle 拉黑时,钱会进 `pendingBalance` 但 `withdraw()` 同样取不出来 —— 解封前动不了。界面如实说明,且**不给重试按钮**(重试解决不了拉黑) |
| **存证 ≠ 版权** | `keccak256` 上链只证明"某文件在某时间点已存在且未被修改",**不**证明版权归属,**不是**门禁手段 |
| **`[Agent]` 徽章是白名单判定** | 链上无法区分人类与 Agent(`msg.sender` 都是买家),只能靠地址白名单。**如实说边界,好过含糊地说"能识别"** |

## 三分钟自己验一遍

```bash
# 1. Agent 前四步不花钱:发现 → 402 → 报价
BASE_URL=https://splitjar.vercel.app node scripts/agent-buy.mjs --dry-run

# 2. 真跑一遍(会花 0.2 USDC 测试币)
BASE_URL=https://splitjar.vercel.app node scripts/agent-buy.mjs

# 3. 打开看板看那一笔带 [Agent] 徽章
open https://splitjar.vercel.app/dashboard
```

人类路径:打开 `/explore` 挑一件 → 连钱包 → `approve` + `pay` → 立刻下载。
